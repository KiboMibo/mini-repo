- **Ветка:** `fix/F4-wave4` (от `wave/app-artifactory-w3`)

## Что сделано

Закрыты все четыре важные находки проверочной волны 4. Ничего кроме них не
трогалось; новых зависимостей нет; контракты API не изменились (новый ответ —
существующий код `409 already_exists`, docs/api.md уже его описывает).

### S1 — файл БД читаем любым локальным пользователем

БД хранит bcrypt-хеши и живые сессионные токены, но создавалась 0644 в 0755.

- `internal/store/store.go` — после `Open` + применения схемы `os.Chmod 0600`
  на `apprepo.db`, `-wal`, `-shm` (несуществующие пропускаются);
- `internal/app/app.go` — data-dir и каталог БД создаются `MkdirAll 0700`;
- `deploy/apprepo.service` — `UMask=0077` (страхует файлы, создаваемые
  драйвером в рантайме, где chmod из `Open` уже отработал).

Подтверждено: `internal/store` `TestOpenFilePermissions` (0600 на файлах БД),
`internal/integration` `TestDataDirAndDBPermissions` (0700 на data-dir и 0600
на БД у собранного через `app.New` приложения).

### S2 + Q1 — гонка двух загрузок одной версии

`Stat`+`Rename` в `files.Save` были TOCTOU: проигравший перезаписывал файл
победителя, а его откат удалял чужой файл; наружу уходил 500 с полным путём ФС.

- `internal/files/files.go` — публикация заменена на атомарно-эксклюзивный
  `os.Link(temp, dst)` + `os.Remove(temp)`; `EEXIST` → типизированная
  `ErrFileExists` (без путей в тексте); `Stat` оставлен как быстрый отказ до
  прогона байтов, авторитетен Link;
- `internal/api/api.go` — `files.ErrFileExists` в `putVersion` → `409
  already_exists`, «version already exists»;
- `internal/web/web.go` — `files.ErrFileExists` в `uploadError` → 409, та же
  ветка, что `store.ErrExists`.

Откат `fs.Remove` в обоих хендлерах и раньше вызывался только после успешного
`Save` этого же запроса; после фикса `Save` проигравшего падает до создания
dst — инвариант «откатываем только своё» соблюдён без правок откатов.

Подтверждено: `internal/files` `TestSaveRaceLoserGetsErrFileExists` (dst
появляется во время стриминга → `ErrFileExists`, файл победителя байт-в-байт
цел, temp не течёт), `TestSaveNoOverwrite` (ужесточён до `ErrFileExists`);
`internal/integration` `TestConcurrentPutSameFileGets409` (два конкурентных
PUT одной версии с одним filename: один 201, второй 409 `already_exists`, в
теле нет пути data-dir, файл победителя скачивается байт-в-байт). Прежний
`TestConcurrentPutSameVersionRollsBack` (разные filename, откат по UNIQUE в
БД) остался зелёным без правок.

### S3 — multipart: неограниченное число полей в памяти

- `internal/web/web.go` — не-file части ограничены: максимум 8 полей
  (`maxUploadFields`; форма шлёт 3) по 4 КиБ (`maxFieldBytes`, прежний лимит,
  вынесен в константу); сверх лимита — 400 «too many form fields» без чтения
  файла. Файл — по-прежнему только потоково.

Подтверждено: `internal/web` `TestUploadTooManyFields` (20 полей → 400, файл
не сохранён); существующие тесты загрузки зелёные.

### Q2 — err.Error() внутренних ошибок уходил клиенту, лог пуст

- `internal/api/api.go` — все 500-ветки через `internalErr` (JSON) /
  `plain500` (/download): клиенту фиксированное
  `{"error":"internal","message":"internal error"}` / прежний plain-текст,
  реальная ошибка — в `log` с методом и путём;
- `internal/auth/auth.go` — три 500-ветки middleware получили `log.Printf`
  (тело и раньше было генеричным);
- `internal/web/web.go` — дефолтная ветка `uploadError` больше не отдаёт
  `err.Error()`: текст в лог, клиенту «upload failed» (остальные 500 UI уже
  шли через `serverError` с логом).

Клиентские 4xx-валидации оставлены информативными, как требует находка.
Подтверждено: критерий из S4 «Как проверить» — grep по `internal/api`,
`internal/web`, `internal/auth`: `err.Error()` остался только в
4xx-валидационных ветках; сборка и весь набор тестов зелёные (500 без
fault-injection не триггерится, поэтому отдельного теста нет — честно
отмечаю как непокрытое тестом место).

## Решения и альтернативы

- **`os.Link` вместо `O_EXCL`-копирования:** сохраняет потоковую запись через
  temp с SHA-256 на лету и даёт атомарный эксклюзив одним сисколлом; ошибка
  распознаётся `errors.Is(err, fs.ErrExist)` (LinkError разворачивается до
  EEXIST). Ранний `Stat` оставлен только как дешёвый отказ.
- **Chmod после Open, а не режим при открытии:** у ncruces-драйвера нет
  публичной ручки режима создания файла в DSN; chmod + UMask в юните — ровно
  рекомендованный находкой надёжный вариант.
- **Лимит полей 8/4 КиБ, а не whitelist имён:** количество × размер уже
  ограничивают память константой; whitelist ломал бы будущие поля формы без
  выгоды по безопасности.

## F4b (второй круг sec-ревью)

- **S1-хвост в `user add`:** `cmd/apprepo/main.go` создавал каталог БД с
  `MkdirAll 0o755` в обход S1 — при порядке «user add → serve» data-dir
  (по дефолту он же каталог БД) оставался мир-проходимым. Исправлено на
  0700; других `MkdirAll` вне 0700-корня не найдено (в `internal/files`
  подкаталоги создаются внутри уже закрытого data-dir). Подтверждено:
  `go build ./... && go test ./...` зелёные; эмпирически — `user add` на
  чистом каталоге даёт `700` на data-dir и `600` на `apprepo.db`.

## За рамками / риски

- 500-ветки не покрыты прямым тестом (нужна fault-injection в store/ФС) —
  проверены сборкой, grep-критерием S4 и неизменностью зелёного набора.
- Замечания S5–S8 (Secure-куки, rate limit, CSRF-привязка к сессии,
  управляющие символы в filename) — вне объёма F4, остаются в отчёте R4-sec.
- `-wal`/`-shm`, создаваемые драйвером в рантайме при живом процессе, чинятся
  UMask'ом юнита; при ручном запуске без umask 0077 они наследуют umask
  пользователя (каталог 0700 всё равно закрывает доступ посторонним).
