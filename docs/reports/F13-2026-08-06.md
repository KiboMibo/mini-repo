# F13 — минимальная длина пароля (последнее замечание волны 6)

**Ветка:** `fix/F13-password-policy` (от `wave/app-artifactory-w6`)
**Статус:** готово. `go build ./... && go vet ./... && go test -count=1 ./...` — зелёный целиком, `bash scripts/smoke.sh` — `SMOKE OK`.
**Источник:** `docs/plans/reviews/app-artifactory-R6-sec.md`, замечание **S3-а** («пароль `"x"` принимается с кодом 201»).

## Что сделано

Одна константа и одна ветка `switch` в `naming.ValidatePassword`:

```go
const MinPasswordBytes = 8
…
case len(pw) < MinPasswordBytes:
    return fmt.Errorf("password must be at least %d bytes, got %d", MinPasswordBytes, len(pw))
```

Больше в продуктовом коде не изменено ничего, кроме комментария в
`cmd/apprepo/main.go` (речь уже не только про предел bcrypt). Так вышло потому,
что F12 завела точку политики правильно: `ValidatePassword` — единственное
место, и её уже вызывают все три интерфейса на всех шести путях задания пароля.

| Интерфейс | Где вызывается | Что видит пользователь |
|---|---|---|
| API | `api.hashPassword` (создание, сброс админом, смена своей) | `400 {"error":"validation","message":"password must be at least 8 bytes, got 5"}` |
| UI | `web.createUser`, `web.resetUserPassword`, `web.changeOwnPassword` | `400`, текст на той же форме, страница не теряется |
| CLI | `readPassword` (`user add`, `user password`) | `apprepo: password must be at least 8 bytes, got 5`, **exit 1** |

Ни на одном пути это не `500`: проверено тестами (см. ниже) и живым бинарником
в `scripts/smoke.sh`.

**Почему 8 и почему только длина** — записано комментарием к константе. Коротко:
ограничения частоты входа в сервисе нет (R4-S7 открыто), поэтому единственная
цена перебора — стоимость bcrypt, и 8 байт — та граница, ниже которой bcrypt
перестаёт быть препятствием. Классов символов, словарей и проверки на совпадение
с именем нет намеренно: они гонят пользователя в «Password1!» и требуют списков,
которые кто-то должен обновлять.

**Проверка на пустоту оставлена отдельной веткой.** Формально она избыточна (0 <
8), но её текст `password must not be empty` дословно ждут PoC-тесты волны 6
(`r6_lifecycle_test.go`, четыре места), да и пустое поле формы — другая ошибка
пользователя, чем слишком короткий пароль.

## Ловушка из F12: починена, а не обойдена

F12 отказалась включать минимум, потому что он делает
`TestUsernameHandlingConsistency` — приёмочный тест находки об именах учёток —
**зелёным вхолостую**: подтесты создавали учётки с паролями `"pw"` (2 байта) и
`"bot-pw"` (6), при минимуме 8 оба интерфейса отвечают 400, тест видит
`apiOK == uiOK == false`, выходит по раннему `return` и ни разу не сравнивает
имена.

Ловушка подтвердилась сразу после включения минимума: тест **остался зелёным**,
хотя ничего уже не проверял. Починен подъёмом фикстур, а не ослаблением
проверок.

### Доказательство, что приёмка не потеряна

Прогон после правки — в журнале видны **обе** созданные учётки, то есть обе
ветки дошли до 201/303, ранний `return` не сработал и сравнение имён
состоялось:

```
$ go test -count=1 -run TestUsernameHandlingConsistency -v ./internal/integration/

2026/08/07 14:50:14 web: user "alice" created user "pad-ui" with role developer

```

`created user "pad-api"` + `created user "pad-ui"` — ровно тот признак, которым
пользовалась и F12: без них тест бы вышел на строке `if !apiOK { return }`.

### Чтобы ловушка не вернулась

Литерал в этом тесте заменён на производную от самой политики
(`internal/integration/r6_helpers_test.go`):

```go
var validPass = strings.Repeat("p", naming.MinPasswordBytes)
```

Следующее поднятие минимума автоматически поднимет и фикстуру: подтест не
сможет молча уехать в ранний `return`. Это дешевле любого ассерта и не требует,
чтобы кто-то помнил про связь.

## Проверка, что тесты не позеленели вхолостую

Прямая проверка, которую просила задача: минимум временно возвращён к `1` и
прогнан весь набор.

```
--- FAIL: TestValidatePassword                                  (internal/naming)
--- FAIL: TestUserAddCLI/user_add_short_password_fails           (integration)
--- FAIL: TestUserManagementValidationOverHTTP/ui_смена_своего_пароля… (integration)
все остальные пакеты и тесты — ok
```

Читается так, как и хотелось:

- **упали ровно те три теста, которые политику утверждают** — значит они её
  действительно проверяют, а не проходят при любом значении;
- **все фикстурные тесты остались зелёными** — значит их пароли валидны сами по
  себе, а не «проходят, потому что всё подряд отвечает 400». В частности
  `TestUsernameHandlingConsistency` создаёт учётки и при минимуме 1, и при 8:
  `validPass` годен в обоих случаях.

После проверки минимум возвращён к 8, набор перепрогнан целиком.

## Риски и на что смотреть ревьюеру

1. **Существующие учётки не затронуты.** Проверка стоит только на задании
   нового пароля; вход (`auth.CheckPassword`) её не вызывает. Учётка со старым
   коротким паролем продолжает работать и после обновления — «принудительной
   смены» нет, и это осознанно: иначе обновление выбило бы из установки всех
   разом. Обратная сторона: **S3-а закрыт для новых паролей, но не для уже
   существующих**; если это важно, нужна отдельная задача (флаг «пароль
   просрочен» в схеме) — здесь она не делалась.
2. **Порядок проверок в хендлерах остался прежним** и на него теперь опираются
   тесты: `current_password` проверяется **до** длины нового (иначе смена
   пароля отдавала бы 400 вместо 403 при неверном текущем), `mustUser` —
   **до** пароля (404 на несуществующей учётке, а не 400). При перестановке
   этих строк тесты покраснеют — так и задумано.
3. **`s3cret` больше не встречается** ни в скрипте, ни в документации. Если
   у кого-то есть локальная установка, заведённая по README, её пароль
   политике не соответствует — см. п. 1, она продолжит работать.
4. **Ограничение частоты входа по-прежнему нет** (R4-S7 открыто). Минимальная
   длина ослабляет перебор, но не закрывает его; в комментарии к константе это
   зафиксировано, чтобы 8 байт не приняли за решение задачи о rate limit.
