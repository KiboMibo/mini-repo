# F11 — свести концы волны 6

Ветка: `fix/F11-wave6-loose-ends` (от `wave/app-artifactory-w6`). Remote нет — PR не создавался.

## Что сделано и зачем

Волна 6 (роли и права) делалась тремя параллельными задачами в изоляции, после
чего остались два расхождения: одна и та же операция требовала разных прав в API
и UI, а интеграционный тест CLI фиксировал поведение до введения ролей.

### 1. Закрепление latest — везде `PermVersion`

`internal/api` вешал `POST /api/apps/{name}/latest` на `PermVersion`, `internal/web`
тот же по смыслу `POST /apps/{name}/latest` — на `PermApp`. Приведено к `PermVersion`
по решению командира; обоснование зафиксировано комментарием у маршрута: роль
`developer` и так двигает latest неявно — заливка версии со старшим semver делает
её latest автоматически, так что запрет явного закрепления непоследователен.

Вместе с маршрутом переведена форма выбора latest в шаблоне (`Can.App` → `Can.Version`):
иначе `developer` получил бы право, которого не видит в интерфейсе, — ровно тот
разрыв «кнопка ↔ право», который остальная разметка последовательно избегает.

### 2. Устаревшие подтесты `TestUserAddCLI`

`user_add_duplicate_fails` и `user_add_without_password_non_tty_fails` запускали
`apprepo user add <второй-пользователь>` без `-role` и ждали `exit 1` с
«already exists» / «empty password». Новый CLI требует `-role` для всякого
пользователя, кроме самого первого, и отвечает `exit 2` со справкой раньше, чем
доходит до создания учётки и чтения пароля, — падали оба. Изменение поведения
намеренное, поэтому обновлён тест, а не код: подтесты передают `-role developer`
и снова проверяют ровно то, ради чего писались. Ни один подтест не удалён и не
ослаблен.

Добавлен `user_add_second_without_role_fails` на новое поведение: `exit 2`,
сообщение `-role is required`, и в нём перечислены все роли из `auth.AllRoles()`
(проверяется циклом по списку, а не строкой-константой, — чтобы тест не разъехался
при добавлении роли).

## Сверка остальных пар маршрутов API ↔ UI

Сверены все пары «одна операция — два интерфейса» по `internal/api/api.go` и
`internal/web/web.go`:

| Операция | API | UI | |
|---|---|---|---|
| создать приложение | `POST /api/apps` → `PermApp` | `POST /apps` → `PermApp` | ок |
| правка/переименование | `PATCH /api/apps/{name}` → `PermApp` | `POST /apps/{name}/edit` → `PermApp` | ок |
| удалить приложение | `DELETE /api/apps/{name}` → `PermApp` | `POST /apps/{name}/delete` → `PermApp` | ок |
| залить версию | `PUT /api/apps/{name}/versions/{v}` → `PermVersion` | `POST /apps/{name}/versions` → `PermVersion` | ок |
| удалить версию | `DELETE /api/apps/{name}/versions/{v}` → `PermVersion` | `POST /apps/{name}/versions/{v}/delete` → `PermVersion` | ок |
| закрепить latest | `POST /api/apps/{name}/latest` → `PermVersion` | `POST /apps/{name}/latest` → `PermVersion` | **исправлено этой задачей** |
| список учёток | `GET /api/users` → `PermUserAdmin` | `GET /users` → `PermUserAdmin` | ок |
| создать учётку | `POST /api/users` → `PermUserAdmin` | `POST /users` → `PermUserAdmin` | ок |
| сменить роль / блокировку | `PATCH /api/users/{username}` → `PermUserAdmin` | `POST /users/{id}/role`, `POST /users/{id}/disabled` → `PermUserAdmin` | ок |
| сбросить чужой пароль | `POST /api/users/{username}/password` → `PermUserAdmin` | `POST /users/{id}/password` → `PermUserAdmin` | ок |
| удалить учётку | `DELETE /api/users/{username}` → `PermUserAdmin` | `POST /users/{id}/delete` → `PermUserAdmin` | ок |

Больше расхождений нет. Два места, где права формально не совпадают, но это
намеренная асимметрия «API vs интерфейс», а не расхождение по операции, — оба
уже объяснены комментариями в коде и трогать их не следует:

- **чтение**: `GET /api/apps*` → `PermRead`, а страницы UI (`GET /`, `GET /apps/{name}`)
  → `PermUI`. `deployer` имеет `PermRead` без `PermUI`: он читает и качает через
  API, а в интерфейс не допускается вовсе — это и есть смысл роли.
- **свой пароль**: `POST /api/me/password` — без права вообще, `POST /password`
  в UI — под `PermUI`. Осознанно: `deployer` меняет свой пароль через API, потому
  что в UI его не пускают; в комментарии `api.go` это прямо оговорено.

Смежное наблюдение (не чинил, это задача документации): `docs/api.md` вообще не
описывает требуемые права по маршрутам — раздела о ролях там нет. Стоит учесть в
задаче на docs.

## Как проверено

```
go build ./... && go vet ./... && go test -count=1 ./...   # всё зелёное
bash scripts/smoke.sh                                       # SMOKE OK
```

Прогон `./...` целиком: `cmd/apprepo`, `internal/{api,auth,config,files,integration,naming,store,web}` — ok.
`internal/integration` до правки был красным на двух подтестах `TestUserAddCLI`, после — зелёный.

Подтверждение по пунктам:

- расхождение прав закрыто — `TestRoutePermissionMatrix` в `internal/web/roles_test.go`
  теперь гоняет строку «set latest» с `PermVersion`, то есть требует 303 у
  `developer` и 403 у `deployer`; таблица прав API не менялась и остаётся эталоном;
- кнопка совпадает с правом — `TestButtonsHiddenByRole/developer/apps/demo`
  требует наличия `/apps/demo/latest` в разметке;
- подтесты CLI проверяют дубль и пустой пароль — `user_add_duplicate_fails`,
  `user_add_without_password_non_tty_fails` зелёные с `-role`;
- новое поведение покрыто — `user_add_second_without_role_fails`.

## За рамками

- `docs/api.md` и `README.md` не трогались — документацию делает отдельная задача.
- `internal/api` и `cmd/apprepo` не трогались: по постановке они правильные.

## Риски и на что смотреть ревьюеру

- Правка расширяет права `developer`: он теперь может закреплять latest из UI и
  из API. Это и есть решение командира, но это ослабление, а не ужесточение, —
  если решение пересмотрят, менять придётся оба пакета разом.
- Правка шаблона (`Can.App` → `Can.Version`) выходит за буквальный список файлов
  из постановки («маршруты и тест матрицы»), но лежит внутри `internal/web/**` и
  без неё право у `developer` было бы недостижимо из интерфейса. Отмечено здесь
  явно.
