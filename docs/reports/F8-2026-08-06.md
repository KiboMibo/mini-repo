## Что сделано и зачем

F7 закрыла удаление (`RemoveApp`/`RemoveVersion` через `os.Lstat` убеждаются, что цель —
настоящий каталог), но первопричина — общий `Root` для каталогов приложений и файла БД плюс
путь, собранный из имени, — жила на третьей деструктивной операции. В `RenameApp` проверка
`os.Lstat(dst)` защищала только **приёмник**; источник не проверял никто, и `os.Rename`
переносил объект любого типа. Отсюда эксплуатация в два обычных запроса от любой залогиненной
учётки:

```
POST  /api/apps            {"name":"apprepo.db"}   → 201
PATCH /api/apps/apprepo.db {"name":"moved"}        → 200, файл БД уехал в {data-dir}/moved
```

Сервис продолжал отвечать из открытого дескриптора, `-wal`/`-shm` оставались осиротевшими, а
следующий запуск падал на `apply schema: sqlite3: disk I/O error` — отказ в обслуживании,
который не чинится перезапуском.

### Правка (узкая, симметрична F7)

**`internal/files/files.go`, `RenameApp`.** Перед `os.Rename` вызывается **существующий**
хелпер `isDir` из F7 — второй его копии не появилось:

- источник отсутствует → `(false, nil)` → `nil`: приложение без версий каталога не имеет,
  переименование проходит штатно (поведение не изменилось);
- источник есть, но не каталог (обычный файл; симлинк — `Lstat` не считает его каталогом даже
  при каталоге-цели) → `files.ErrNotDirectory`, на диске ничего не двигается;
- источник — настоящий каталог → `os.Rename` как раньше.

**Порядок проверок сохранён намеренно:** сначала занятый приёмник (`ErrFileExists`), потом тип
источника. Обратный порядок изменил бы существующее поведение случая «у приложения нет
каталога, а новое имя занято соседом»: сейчас это 409, а при проверке источника первой стало бы
тихое 200 с именем `apprepo.db` в БД — то есть отложенная поломка вместо честного отказа.

**`internal/api/api.go` (`updateApp`) и `internal/web/web.go` (`editApp`).** Ветка
`files.ErrNotDirectory` рядом с существующей `files.ErrFileExists`: 409 `already_exists` в API,
страница приложения с баннером 409 в UI (вместо генеричного 500, которым эта ошибка ушла бы в
`serverError`). Путь ФС попадает только в серверный лог, клиенту — фиксированный текст, как и
в `removeErr` из F7. Новых кодов ошибок в `docs/api.md` не появилось.

**Компенсация отрабатывает.** Откат имени в БД стоит в обоих хендлерах **до** разбора ошибки,
поэтому срабатывает и на новом отказе: строка возвращается к прежнему имени, а не остаётся
указывать на несуществующий каталог. Проверено интеграционным тестом (`GET /api/apps/{старое}`
→ 200, `GET /api/apps/{новое}` → 404 после отказа).

## Четвёртого HTTP-достижимого пути с той же первопричиной не найдено

В `internal/files` путь из имени строят ещё две функции — их я проверил специально и **не**
трогал:

- **`Save`** — `os.MkdirAll(filepath.Dir(dst))` + `os.Link`. Если на месте `{Root}/{app}`
  лежит файл БД, `MkdirAll` падает с `ENOTDIR` (500), а `Link` в принципе ничего не
  перезаписывает (`EEXIST` → `ErrFileExists`). Разрушить соседа этим путём нельзя.
- **`Remove`** — `os.Remove` листа `{Root}/{app}/{version}/{filename}` и best-effort прополка
  пустого каталога версии. Цель на три уровня глубже соседей data-dir, и вызывается она только
  как откат собственного `Save`.

Остаточный класс, который рубеж типа цели не закрывает ни здесь, ни в F7: если внутри `Root`
уже лежит **симлинк**, подложенный локально, `Save` может опубликовать файл, а `Path`/download —
прочитать его вне `Root`, потому что резолвятся родительские компоненты. Это тот же
остаточный TOCTOU, который ревьюер круга 1 разобрал и принял: чтобы им воспользоваться, нужен
локальный доступ на запись в data-dir (0700, владелец — пользователь сервиса), а с ним файлы
доступны напрямую. Из HTTP создать симлинк нечем. Отдельной находкой не считаю, но называю
явно, а не молчу.

Итого все три деструктивные операции (`RemoveApp`, `RemoveVersion`, `RenameApp`) теперь решают
по типу цели, а не по её имени; функций, которые касаются ФС по пути из имени без такой
проверки, в `internal/files` не осталось.

## Риски и точки внимания для ревьюера

1. **Порядок `Lstat(dst)` → `isDir(src)`** — намеренный, обоснование выше; при смене порядка
   ломается `TestRenameAppTargetExists*` и появляется тихое 200 для приложения без каталога.
2. **Изменение видимого поведения (аналогично F7):** если администратор сознательно сделал
   `{Root}/{app}` симлинком на другой том, переименование такого приложения теперь отвечает 409
   вместо переезда линка. Место для строчки в README вместе с описанием раскладки каталогов
   (задача не моя, но упомянуть стоит).
3. **N2 остаётся открытым** — я его не трогал: текст 409 у удаления по-прежнему молчит о том,
   что строка в БД уже удалена, и UI на этом пути отвечает `text/plain`. Для *переименования*
   расхождения нет: компенсация полная, и ответ UI — нормальная HTML-страница.
4. `docs/api.md` не менялся: новых кодов ошибок нет, 409 `already_exists` уже описан.
5. `go.mod`/`go.sum` не менялись, новых зависимостей нет.
