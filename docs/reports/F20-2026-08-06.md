# F20 — концы волны 8: платформа в интеграционных тестах и smoke

Ветка `fix/F20-platform-fallout` от `wave/app-artifactory-w8` (T24 + T25 + T26).
Новых зависимостей нет, продуктовый код не менялся ни строкой. Файлы —
`internal/integration/**` и `scripts/smoke.sh`.

## Что сделано и зачем

Волна 8 сделала платформу обязательной там, где её не удаётся определить по
файлу: `?platform=` в API (T25) и `platform_os` в форме UI (T26). Тела
интеграционных тестов и smoke — текстовые заглушки и tar.gz, по которым
определять нечего, поэтому весь пакет `internal/integration` покраснел, а
`scripts/smoke.sh` упал бы на первой же заливке. Хуже: пакет не просто краснел,
а **висел до `panic: test timed out`**.

### 1. Зависание — что это было

`TestConcurrentPutSameVersionRollsBack` (`misc_test.go`) устраивает гонку двух
`PUT` одной версии: «медленный» запрос льёт тело через `io.Pipe` и ждёт, пока
«быстрый» создаст версию целиком. После волны 8 «быстрый» стал получать
`400 platform_required`, `mustPutVersion` делал `t.Fatalf` — и `pw.Close()`
двумя строками ниже уже не выполнялся. Тело медленного запроса оставалось
недописанным, запрос — в полёте, а `httptest.Server.Close()`, зарегистрированный
`newEnv` в `t.Cleanup`, ждёт завершения открытых соединений. Ждал он вечно, и
вместе с ним стоял весь пакет: остальные тесты до конца прогона не доходили,
поэтому реальный масштаб красноты был не виден.

Причина устранена (заливка получила платформу), но **класс отказа сам по себе
опаснее конкретного случая**: любое раннее падение теста, который держит
незакрытое тело запроса, снова подвесит весь пакет — как это уже было после F17
с ломающим `?filename=`. Поэтому у всех трёх таких мест тело закрывается
через `defer`, независимо от того, как тест завершился:

| Место | Как |
|---|---|
| `misc_test.go` ×2 (`TestConcurrentPutSameVersionRollsBack`, `TestConcurrentPutSameFileGets409`) | `defer pw.Close()` |
| `r5_guard_test.go` (`TestRenameWhileUploadIsStreamingObserved`) | `defer pw.Close()` |
| `f10_race_test.go` ×2 (`TestUploadDuringRenameAPI`, `TestUploadDuringRenameUI`) | `unpause := sync.OnceFunc(func() { close(release) })` + `defer unpause()` — канал закрывается и по ходу сценария, обычный `defer close(release)` дал бы панику на повторном закрытии |

`sync.OnceFunc` — stdlib (Go 1.21+), своего примитива не заводилось.

### 2. Новый контракт в тестах

Правило одно: там, где тело не настоящий бинарник, платформа передаётся явно и
равна `any` — текстовая заглушка действительно не зависит от ОС и архитектуры,
и это ровно то значение, которое T25/T26 для такого случая и предусмотрели.
`any` на опознанном бинарнике был бы 409 `platform_mismatch`, но настоящих
бинарников среди тел в `internal/integration` нет.

**Смысл существующих тестов не тронут.** Они как проверяли лимиты, гонки, имена
файлов, права и коды ошибок, так и проверяют; платформа для них — обязательный
реквизит запроса, а не предмет проверки. Ни одно ожидание статуса, ни один
assert не переписан.

Общее правится один раз, ручные сборки — точечно:

| Файл | Что |
|---|---|
| `helpers_test.go` | константа `testPlatform = "any"`; `env.putVersion` дописывает `&platform=`, если тест не задал свой (`strings.Contains(query, "platform=")`); `uploadUI` шлёт `platform_os` |
| `r7_abort_test.go` | `uiUploadBody` — общий сборщик тела формы для обоих тестов лимита, `platform_os` перед частью `file` |
| `edges_test.go` | `uploadRawFilename` (сырой `Content-Disposition`) |
| `f18_upload_after_body_test.go` | список полей формы |
| `f10_race_test.go` | сырой `PUT` и ручной multipart в двух тестах гонки с переименованием |
| `misc_test.go` | два сырых `PUT` через `io.Pipe` |
| `r6_lifecycle_test.go` | две заливки в жизненном цикле учётки |
| `r6_migration_test.go` | заливка мигрированной учёткой |
| `r6_parity_test.go` | `uploadStatus` (UI) и `PUT` (API) в паре «залить версию» |

Порядок частей формы соблюдён везде: `platform_os` вставлен **перед** `file`,
который обязан идти последним (инвариант `CLAUDE.md`, хендлер читает потоково).

### 3. `scripts/smoke.sh`

Заливки текстовых заглушек и архива получили `&platform=any`. Сверх того
добавлен раздел про саму платформу — его не было ни у T25 (только модульные
тесты), ни у T26 (smoke льёт исключительно через API):

- **автоопределение на настоящем бинарнике**: подопытный уже под рукой — это сам
  собранный `apprepo`. Заливается без `?platform=`, в ответе ожидается
  `"platform":"$(go env GOOS)/$(go env GOARCH)"`. Это и есть обещание T25
  «старые CI-скрипты с бинарниками не правятся ни одной строкой», проверенное
  на живом сервисе, а не на крафченом заголовке;
- **отказ архиву без параметра**: `400`, код `platform_required`, текст содержит
  готовую строку `curl` (как у `filename_required` — его читает лог сломавшегося
  пайплайна), каталога версии на диске нет;
- **тот же архив с `?platform=any` → 201** — чтобы отказ читался как «нужен
  параметр», а не «архивы больше не принимаются».

## Асимметрия UI ↔ API (пункт 4 задачи)

**Расхождения нет, продуктовый код править не потребовалось.** Один и тот же
tar.gz без платформы, залитый обоими путями в одном окружении:

| | Статус | Тело | На диске и в БД |
|---|---|---|---|
| API `PUT …?filename=…` | `400` | `{"error":"platform_required", …}` — причина, `any`, словарь значений, готовая строка `curl` | ничего |
| UI `POST /apps/{n}/versions` | `400` | страница с `could not tell from the file which OS and architecture it is built for (archives carry nothing to read)…` | ничего |

Совпадает и класс кода (инвариант «класс кода ответа на одну и ту же ошибку
обязан совпадать в API и UI»), и наблюдаемое состояние: оба откатывают
опубликованный файл, версия не создаётся ни там, ни там. Тексты разные, но это
норма — API пишет для лога CI, UI для человека на странице; так же устроены и
остальные пары в проекте.

Проверено разовым тестом, прогнанным и удалённым (в коммит не пошёл): постоянное
покрытие этих двух отказов уже есть у авторов — `TestPutVersionArchiveNeedsPlatform`
в `internal/api` и `TestUploadArchiveWithoutPlatformRefused` в `internal/web`.
Чего нет — теста именно на **парность** этих двух отказов, по образцу
`TestPermissionParityAPIvsUI`; см. «Что осталось за рамками».

## Найденное сверх списков T25 и T26

T25 и T26 работали каждый из своего worktree и видели каждый свою половину.
Сверх их списков нашлось:

1. **Само зависание** — ни в одном из отчётов его нет: T26 видел «10 падений»,
   потому что до конца прогона пакет не доходил.
2. **`r6_lifecycle_test.go`, `r6_migration_test.go`, `f10_race_test.go` (API-часть),
   `misc_test.go` (два сырых `PUT`)** — заливки мимо `env.putVersion`, собранные
   через `e.api`/`http.NewRequest` руками. В «39 мест через `putVersion`» они не
   попали.
3. **`r7_abort_test.go`** — T26 назвал два теста лимита по именам, но не заметил,
   что тело им обоим собирает общий `uiUploadBody`: это одна правка, а не две.
4. **`r6_parity_test.go`** — сейчас **зелёный по случайности**: API-заливка
   упирается в раннюю проверку дубля (она выше платформы), а тест сравнивает
   только «отказано / не отказано», так что `400` вместо `409` его не роняет.
   Замысел подтеста при этом ломался: «роль с правом получает 409 на занятой
   версии» переставало быть правдой для UI. Платформа добавлена — по той же
   причине, по которой там уже стоял `?filename=`, и с тем же комментарием.
5. **`README.md`, строки ~282 и ~328** — примеры заливки архива без
   `?platform=`, которые сегодня отдают `400`. Файл не мой и не в списке задачи;
   фиксирую для документационной задачи волны. Пример с
   `myapp-linux-amd64` (голый бинарник, строка ~323) корректен и после волны 8.
6. **`CLAUDE.md`** не знает ни про `?platform=`, ни про то, что порядок полей
   формы стал `csrf_token, version, sha256, platform_os, platform_arch, file`
   (инвариант про «`file` последним» перечисляет три поля). Тоже за
   документационной задачей — T26 это уже отмечал.

Места, которые опираются на старый контракт, но остаются корректными и не
тронуты: заливки, отказ которым наступает **до** платформы — негодное или
пустое `?filename=` (`r7_filename_test.go`, `f19_control_filename_test.go`),
превышение лимита (`r7_abort_test.go`), несовпавший `X-Checksum-Sha256`,
403 по роли, multipart без файловой части и с чужим CSRF.

## Как проверено

```
go build ./...                             OK
go vet ./...                               OK
gofmt -l internal/integration              пусто
bash -n scripts/smoke.sh                   OK
go test -count=1 -timeout 900s ./...       все 11 пакетов ok, 2 мин 06 с
bash scripts/smoke.sh                      SMOKE OK, 17 с
```

`internal/integration` — `ok 114.9s`, прогон **завершается сам**, без внешнего
таймаута; до правки тот же прогон упирался в `panic: test timed out`.
Зависание воспроизведено на исходном состоянии ветки прицельно
(`go test -timeout 100s`), стек назвал `TestConcurrentPutSameVersionRollsBack`
в `sync.WaitGroup.Wait` — отсюда и разбор выше.

| Пункт задачи | Чем подтверждён |
|---|---|
| тесты приведены к новому контракту | `go test -count=1 ./internal/integration/...` зелёный |
| зависание починено | тот же прогон завершается за 114.9 с; повторно `./...` целиком за 2 мин 06 с |
| smoke зелёный и знает про платформу | `bash scripts/smoke.sh` → `SMOKE OK`, раздел `== platform: detected on a real binary, demanded from an archive` |
| сверка UI ↔ API | таблица выше; расхождения нет, продуктовый код не тронут |
| поиск мест сверх T25/T26 | шесть находок выше |

## Что осталось за рамками и почему

- **`README.md` и `CLAUDE.md`** — за документационной задачей волны; в задаче
  F20 прямо сказано `docs/` не трогать, кроме своего отчёта. Что именно
  устарело — перечислено выше.
- **`docs/api.md`** — три новых кода ошибок и `PATCH` версии описаны в отчёте
  T25 в готовом для переноса виде; это не моя задача.
- **Тест на парность отказов UI ↔ API по платформе.** Сверка проведена руками и
  зафиксирована в этом отчёте, но постоянного теста, который не даст паре
  разъехаться (как `TestPermissionParityAPIvsUI` для прав), не появилось:
  заводить новый тест в задаче «свести концы» — выход за её рамки. Разумный
  кандидат в бэклог.
- **Настоящий бинарник в интеграционных тестах.** Все тела остались текстовыми
  заглушками с `platform=any`; автоопределение на живом бинарнике проверяется в
  `internal/api` (`TestPutVersionRealBinary`) и теперь в smoke. Дублировать
  третий раз незачем.

## Риски и точки внимания для ревьюера

- **`env.putVersion` подставляет платформу по подстроке `platform=` в query.**
  Это самое дешёвое, что работает, но тест, которому нужен именно запрос **без**
  параметра, обязан идти через `putVersionRaw` (он передаёт query дословно —
  для того и заведён). Сейчас так и есть.
- **Помеченное `any` — не утверждение о содержимом.** В тестах это ровно
  «платформа не проверяется, дайте пройти», и если завтра какой-то из них
  начнёт заливать настоящий бинарник, `any` обернётся 409 `platform_mismatch`.
  Отдельная константа `testPlatform` заведена в том числе поэтому: место, где
  это решение принято, ровно одно.
- **Три `defer`, снимающие зависание, — страховка, а не исправление логики.**
  Тесты и без них проходят; они нужны, чтобы следующее ломающее изменение
  контракта дало красный прогон, а не молчаливый `test timed out`, в котором не
  видно ни одного настоящего падения.
- **Раздел платформы в smoke зависит от `go env`** — как и вся остальная часть
  скрипта, которая начинается с `go build`. Отдельного требования к среде не
  добавилось.
