# T25 — платформа версии в JSON API

Ветка `feat/T25-api-platform` от `wave/app-artifactory-w8`, поверх T24
(`internal/platform`, колонка `versions.platform`, backfill). Только stdlib,
новых зависимостей нет. Файлы — только `internal/api/**`.

## Что сделано и зачем

Платформа появилась в API тремя вещами:

1. **Заливка сама определяет платформу.** `PUT /api/apps/{name}/versions/{version}`
   получил необязательный `?platform=`. Голый бинарник (ELF, Mach-O, PE)
   опознаётся по файлу, и **старые CI-скрипты не правятся ни одной строкой** —
   ровно то, ради чего автоопределение и делалось. Параметр обязателен только
   там, где определять нечего: архив, скрипт, чужая архитектура.
2. **Поле `platform` в объекте версии** — во всех ответах, где этот объект
   отдаётся: `GET /api/apps/{name}` (и `versions[]`, и `latest`),
   `/versions`, `/versions/{v}`, `/latest`, ответ `PUT` и ответ нового `PATCH`.
   Пустая строка — «неизвестно», нормальное состояние (версии до T24, архивы).
3. **Ручная простановка** — `PATCH /api/apps/{name}/versions/{version}` с телом
   `{"platform":"linux/amd64"}` → `200` и объект версии. Пустая строка
   сбрасывает в «неизвестно». Право — `PermVersion`, то же, что у заливки и
   удаления версии: кто выпускает версию, тот и правит её метку. Матрица прав
   не дублируется — маршрут вешается через тот же `handle(...)`.

## Ключевые решения

### Расхождение указанного и определённого — отказ 409 `platform_mismatch`

Как и предполагал постановщик. Если клиент прислал `?platform=windows/amd64`,
а в файле лежит `linux/amd64`, — заливка отклоняется, обоими значениями в
тексте. Молчаливое доверие метке стоит дороже: неверная платформа
обнаруживается не при заливке, а у того, кто скачал артефакт, и разобраться
тогда уже некому. Обратная сторона (ложное срабатывание определения) закрыта
дешёвым выходом, который назван прямо в тексте ошибки: залить **без**
параметра и поправить `PATCH`'ем — это осознанное действие, а не опечатка в
CI-переменной.

`?platform=any` на опознанном бинарнике — то же расхождение и тот же 409: файл
зависит от ОС и архитектуры, что бы ни утверждала метка. `any` для файла,
который определился, — это ровно то враньё, от которого рубеж и ставится;
пометить `any` архив (`Detect` → `""`) по-прежнему можно.

### Пустое значение параметра = параметр не передан

`?platform=` и `?platform=%20` (в CI это `?platform=$VAR` с незаданной
переменной) уходят в автоопределение, а не в «мусор». Для бинарника это `201`,
для архива — внятный `platform_required`; молча неверной метки не возникает ни
в одном из случаев. Урок F18 («незаданная переменная не должна давать 201 с
негодным значением») соблюдён: пустое значение никогда не становится
платформой.

### Порядок: разбор параметра до тела, определение — после публикации

`?platform=` разбирается вместе с остальной валидацией, **выше `fs.Prepare`** —
инвариант «отказ негодному запросу стоит клиенту ноль байтов» (тест меряет
прочитанные байты).

Определение — по файлу, уже опубликованному `Upload.Commit`, но **до строки в
БД**. Причина честная: `files.Upload` не отдаёт наружу путь своего временного
файла, а `internal/files` в этой задаче read-only. Отказ откатывается тем же
`fs.Remove`, что и неудавшаяся вставка в БД: файл снят, каталог версии убран,
временный файл удалён `Commit`'ом, строки в БД нет — тест это проверяет.
Единственный остаток — **пустой каталог приложения**, если версия была первой;
его создаёт публикация, и точно так же он остаётся сегодня при неудачной
вставке в БД. Наружу он не виден ни в API, ни в UI, `RenameApp`/`RemoveApp` с
ним работают штатно.

Если ревьюер предпочитает буквальное «до публикации» — это одна строка в
`internal/files` (`func (u *Upload) TempPath() string { return u.tmp }`) и одна
в `api`; сознательно не сделано, потому что файл чужой, а T26 его не видит.

### Ошибка `Detect` — не отказ

Файл не читается или разборщик паникнул на враждебном заголовке — это
равнозначно «не опознано» (и уходит в лог, потому что в норме такого не
бывает). Заливать из-за этого запрещать нечего: пользователь укажет платформу
руками.

## Новые коды ошибок (для `docs/api.md`)

Подходящих в словаре не нашлось — три новых, все по сложившемуся образцу
(`invalid_filename`/`filename_required`):

| Код | Статус | Когда |
|---|---|---|
| `invalid_platform` | 400 | `?platform=` или `{"platform":…}` не проходит `platform.Parse`; текст перечисляет допустимые значения |
| `platform_required` | 400 | платформа не определилась по файлу и не передана; ничего не сохранено |
| `platform_mismatch` | 409 | переданная платформа противоречит содержимому файла; ничего не сохранено |

«Не передал» и «передал мусор» намеренно разные коды — как у `?filename=`:
чинятся они по-разному, и в логе CI сливаться не должны.

Дословный текст `platform_required` (рассчитан на лог сломавшегося пайплайна и
самодостаточен, как `filename_required`):

```
the platform of the uploaded file could not be detected and no ?platform= was
given; nothing was stored. A bare executable (ELF, Mach-O, PE) is recognised
automatically, an archive is not — name its platform explicitly, or use "any"
when the file does not depend on OS and architecture (a jar, a bundle of
scripts). Accepted: "any", or os/arch where os is one of linux, darwin,
windows, freebsd and arch is one of amd64, arm64, 386, arm, riscv64, ppc64le,
s390x. For example: curl -u $CRED -X PUT
"$BASE/api/apps/myapp/versions/1.0.0?filename=myapp-1.0.0&platform=linux/amd64"
--data-binary @myapp-1.0.0
```

(имя приложения, версия и имя файла подставляются из самого запроса)

Текст `platform_mismatch`:

```
the uploaded file is built for linux/amd64, but ?platform=windows/amd64 was
given; nothing was stored. Upload the matching file, correct the parameter, or
omit it altogether and let the server take the platform from the file; a
detection you disagree with can be overridden afterwards with PATCH
/api/apps/myapp/versions/1.0.0 {"platform":"windows/amd64"}.
```

## Что осталось за рамками

- **`docs/api.md`** — отдельная задача; три новых кода, новый маршрут и
  `?platform=` описаны выше специально в готовом для неё виде.
- **`internal/web`** — T26.
- **Фильтр/поиск по платформе** в API не заявлен и не сделан.
- **`GET /download`** платформу не отдаёт: контракт скачивания не менялся.

## Риски и точки внимания для ревьюера

- **Ломающее изменение контракта заливки для архивов.** Скрипт, который лил
  архив без `?platform=`, теперь получает 400. Это прямое следствие принятого
  решения («указывать обязательно там, где не определилось»), но в release
  notes это обязано быть первой строкой. Бинарники не затронуты.
- **`internal/integration` красный по той же причине** — 39 мест заливают
  текстовые тела через API без `?platform=`; плюс `scripts/smoke.sh`. Файлы не
  мои (T25 владеет только `internal/api/**`), и правка их посреди волны
  столкнулась бы с T26. Лечится добавлением `&platform=any` (или `linux/amd64`
  там, где тело — бинарник) в `env.putVersion`/вызовы — отдельной задачей после
  слияния волны. `./internal/api/...` зелёный.
- **Пустой каталог приложения после отказа** (см. выше) — единственный след на
  диске, поведение то же, что у существующего отката вставки в БД.
- **`any` на опознанном бинарнике — 409.** Если продукт захочет разрешить
  «пометить как переносимое» на заливке, это снятие одной ветки в
  `resolvePlatform`; сейчас выход — `PATCH` после заливки.
- **`SetVersionPlatform` вызывается отдельным запросом после `CreateVersion`**
  (в `store.CreateVersion` платформы нет, `internal/store` read-only). Сбой
  этого `UPDATE` даёт 500 при уже созданной версии с пустой платформой —
  чинится `PATCH`'ем. Класть платформу сразу в `INSERT` — правка `store`,
  разумная в следующей задаче.
