# T21 — управление учётками из CLI

Ветка `feat/T21-cli-users` от `wave/app-artifactory-w6` (волна 6, параллельно с
T19 API и T20 UI). Опирается на роли и store-операции из T18
(`docs/reports/T18-2026-08-06.md`).

## Что сделано и зачем

CLI — единственный путь восстановления доступа, когда в веб-интерфейс войти
некому: забыт пароль последнего админа, все заблокированы, свежая установка.
Поэтому подкоманды `user *` работают напрямую с БД, сессия им не нужна, и
доступен весь набор операций T18: создание с выбором роли, список, смена роли,
сброс пароля, блокировка/разблокировка, удаление.

Роль по умолчанию у `user add` — только для самого первого пользователя, и это
`admin`: установка, чей единственный аккаунт не может заводить пользователей,
непригодна. Начиная со второго `-role` обязателен — иначе легко молча наплодить
лишних админов.

Подкоманды (полный синтаксис):

```
apprepo user add <username> [-role <role>] [flags]
apprepo user list [flags]
apprepo user role <username> <role> [flags]
apprepo user password <username> [flags]
apprepo user disable <username> [flags]
apprepo user enable <username> [flags]
apprepo user delete <username> -yes [flags]
```

`[flags]` — те же флаги конфигурации, что у `serve` (`-data-dir`, `-db`, …):
каждая подкоманда прогоняет остаток аргументов через `config.Load`, как это
делал `user add` раньше. Роли — `deployer, developer, maintainer, admin`;
и в тексте справки, и в сообщениях об ошибке список берётся из
`auth.AllRoles()`, второй копии в коде нет (закреплено тестом).

Пароль для `add`/`password` — из `APPREPO_PASSWORD`, иначе интерактивный ввод
дважды (логика вынесена в `readPassword`, поведение прежнее).

`user delete` требует `-yes`: CLI гоняют из скриптов, где спросить некого, а
удаление необратимо. Без флага — отказ с подсказкой и код 2, БД не тронута.

`store.ErrLastAdmin` (смена роли, блокировка, удаление последнего активного
админа) во всех трёх операциях превращается в
`refused: no active administrator would be left in the system`, код 1; store
делает проверку в той же транзакции, поэтому не изменено ничего.

## Ключевые решения

**Разбор аргументов в две фазы (`cutFlag`, `cutBoolFlag`, `split`).**
`config.Load` парсит своим `FlagSet`, который ругается на неизвестные флаги, а
`flag` останавливается на первом позиционном аргументе — поэтому строку
`user add alice -role admin -db /tmp/x` одним проходом не разобрать.
Собственные флаги подкоманды (`-role`, `-yes`) вырезаются из среза первыми, в
любой позиции и в обеих формах (`-role admin`, `-role=admin`, `--role`),
остаток уходит в `config.Load` без изменений. Отвергнуто: заставить писать
флаги подкоманды строго до имени пользователя (тогда естественное
`user add alice -role admin` падало бы с «flag not defined»); дублировать
флаги конфигурации в собственном `FlagSet` (две копии дефолтов разъедутся);
тащить зависимость-парсер (задача на 30 строк stdlib).

**Флаг в позиции имени — ошибка, а не имя.** `split` отказывается принять
аргумент, начинающийся с `-`, за `<username>`: иначе `user delete -yes` попыталось
бы удалить пользователя с именем `-yes`.

**Коды выхода.** 0 — успех; 1 — ошибка выполнения (нет пользователя, дубль,
`ErrLastAdmin`, пустой пароль, сбой БД); 2 — всё, что относится к разбору
аргументов: неизвестная подкоманда, нехватка позиционных аргументов,
невалидная или отсутствующая роль, отсутствие `-yes`. Отсутствие `-role`
отнесено к 2 сознательно: это неверный вызов, а не сбой, и вместе с сообщением
печатается справка, где написано, когда роль можно опустить.

**Язык сообщений — английский**, как во всём существующем выводе CLI
(`user %q already exists`, `empty password …`). Формулировка `ErrLastAdmin`
передаёт смысл требования «в системе не останется активных администраторов».

**`user list` печатает `text/tabwriter`-таблицу** (имя, роль, заблокирован,
дата создания) из `store.ListUsers`. Хеши паролей не выводятся ни в каком виде.
Пустая БД — только строка заголовка: так вывод остаётся пригодным для `grep`.

**Порядок внутри `add`/`password`:** сначала открывается БД и валидируется
роль, только потом спрашивается пароль — чтобы оператор не набирал пароль
дважды ради ответа «unknown role».

## Как проверено

`go build ./... && go vet ./... && go test -count=1 ./cmd/...` — чисто.
Дополнительно прогнан весь `go test -count=1 -short ./...` — все пакеты `ok`,
включая `internal/integration` (`TestUserAddCLI`, который запускает CLI и
опирается на прежнее поведение `user add`).

Отдельно проверено на втором временном каталоге: `-db /tmp/…/custom/my.db`
создаёт каталог и файл БД с правами `-rw-------`, `add`/`list`/`delete`
работают против него; `user add bob -role nosuchrole` → exit 2 со списком
ролей; `user add bob` дважды → `user "bob" already exists`, exit 1;
`apprepo user`, `apprepo user bogus`, `user role dave` (без роли),
`user delete -yes` (без имени) → exit 2 со справкой.

Критерии приёмки: все шесть подкоманд — прогон выше; уважение `-data-dir`/`-db`
— прогон выше (обе формы); роль по умолчанию для первого и обязательность
флага для второго — прогон выше; `ErrLastAdmin` во всех трёх операциях с
кодом 1 и неизменной БД (последний `user list`) — прогон выше; `-yes` —
прогон выше; справка со списком подкоманд и ролей из `auth.AllRoles()` —
прогон выше плюс `TestRoleNamesCoversAllRoles`; несуществующий пользователь —
`user role nobody admin`; хеши не печатаются — `userList` выводит только
четыре колонки.

## Осталось за рамками

- **Тесты только на разбор аргументов.** Сами подкоманды заканчиваются
  `os.Exit`, поэтому в процессе теста их не вызвать; проверять их надо
  сборкой бинарника, а это интеграционный пакет `internal/integration`,
  который в этой задаче не мой. Функциональная часть покрыта ручным прогоном
  выше; предлагаю в проверочной волне расширить там `TestUserAddCLI` на
  остальные подкоманды.
- **README и `docs/api.md`** не обновлял (не мои файлы в этой задаче).
  Раздел синтаксиса подкоманд из начала отчёта готов к вставке в README, а
  строку `Один бинарник apprepo с подкомандами serve (дефолт) и user add <name>`
  в `CLAUDE.md` стоит обновить при сборке волны.

## Риски и точки внимания

- `cutFlag` — единственный ручной разбор флагов в проекте. Ведёт себя как
  `flag` в спорном случае: `user add eve -role -db /path` возьмёт `-db` за
  значение роли и упадёт с `unknown role "-db"` (exit 2) — сообщение понятное,
  но это стоит держать в голове.
- `openStore` создаёт БД, если её нет (как `store.Open` и раньше в `user add`):
  `user list` с опечаткой в `-db` покажет пустую таблицу и оставит пустой файл,
  а не скажет «нет такой БД». Прежнее поведение сохранено осознанно — `serve`
  и `user add` работают так же.
- Между `CountUsers` и `CreateUser` в `add` нет транзакции: два одновременных
  `user add` на пустой БД могли бы создать двух админов. Для аварийного CLI,
  который запускает человек, признано неважным.
- Пересечение с параллельными задачами: T19/T20 дают те же операции по HTTP;
  общего кода нет, конфликт возможен только в `CLAUDE.md`/`README.md`, которые
  я не трогал.
