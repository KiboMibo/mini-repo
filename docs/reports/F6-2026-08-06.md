# Отчёт F6: падение на открытии БД без имени файла в логе

- **Дата:** 2026-08-06
- **Ветка:** `fix/F6-db-path-diagnostics` (от `develop`)
- **Задача:** второй подряд дефект боевого развёртывания (в плане отсутствует),
  постановка от командира
- **Файлы во владении:** `internal/store/**`, `cmd/apprepo/main.go`,
  `deploy/**`, `README.md`, `CLAUDE.md`, тесты затронутых пакетов

## Инцидент

Сервис под systemd на Debian. В `/etc/apprepo/apprepo.env` два **разных** пути:

```
APPREPO_DATA_DIR=/data/repo/apps
APPREPO_DB=/data/repo/db/apps.db
```

В юните — только `ReadWritePaths=/data/repo/apps`. Неймспейс собирается
успешно (data-dir на месте, `226/NAMESPACE` не возникает), процесс стартует и
падает уже в приложении:

```
apprepo[20278]: apply schema: sqlite3: unable to open database file
Main process exited, code=exited, status=1/FAILURE
```

Каталог `/data/repo/db` и файл `apps.db` существуют и принадлежат `apprepo`,
`ls -l` показывает корректные права — визуально всё в порядке. Настоящая
причина: `ProtectSystem=strict` оставил каталог БД read-only, и SQLite не может
создать `-wal`/`-shm`. Понять по логу, *какой* файл не открылся, невозможно —
пути в сообщении нет. Это второй инцидент на одном и том же месте: T11
задокументировал связку `APPREPO_DATA_DIR` ↔ `ReadWritePaths`, но `APPREPO_DB` —
второй, независимый путь, и о нём в документации не было ни слова.

## Текст ошибки до и после (дословно)

До:

```
apply schema: sqlite3: unable to open database file
```

После:

```
open database /data/repo/db/apps.db: apply schema: sqlite3: unable to open database file (check directory permissions; under systemd also ReadWritePaths=)
```

Оба текста сняты с реального прогона (`store.Open` на пути в недоступном
каталоге), а не составлены по памяти: «до» — из прогона теста на коде без
правки, «после» — из прогона на текущем коде.

## Что сделано

### 1. Путь в ошибку (`internal/store/store.go`)

Обёртка одна, в `store.Open`, — там, где путь известен, и она работает сразу
для обоих вызывающих (`app.New` и `apprepo user add`):

```go
func Open(path string) (_ *Store, err error) {
	defer func() {
		if err != nil {
			err = fmt.Errorf("open database %s: %w"+
				" (check directory permissions; under systemd also ReadWritePaths=)", path, err)
		}
	}()
```

`defer` на именованном возврате, а не три одинаковых обёртки на трёх ветках
выхода (`sql.Open`, `Exec(schema)`, `Chmod`), — чтобы ни одна ветка не осталась
без пути при следующей правке. `%w` сохранён, `errors.Is/As` у вызывающих
продолжают работать.

Подсказка про права короткая и на английском — как и остальные сообщения об
ошибках в проекте (`invalid max-upload value …`, `sha256 mismatch`); в
постановке она была примером на русском, комментарии в коде остались русскими.

### 2. Дубль пути убран (`cmd/apprepo/main.go`)

`userAdd` оборачивал ошибку своей строкой `open database %s: %v` — вместе с
новой обёрткой путь встал бы дважды. Теперь `fatalf("%v", err)`. Проверено
запуском собранного бинарника:

```
apprepo: open database /tmp/f6/dbdir: apply schema: sqlite3: unable to open database file (check directory permissions; under systemd also ReadWritePaths=)
```

Контракт зафиксирован в docstring `Open` («callers must not prepend the path
again») и в инвариантах `CLAUDE.md`, чтобы дубль не вернулся.

### 3. Создание каталога БД — проверено, правка не потребовалась

`app.New` уже делает `MkdirAll` и для `cfg.DataDir`, и для
`filepath.Dir(cfg.DBPath)` — каталог БД вне data-dir создаётся. Ошибка
`os.MkdirAll` — это `*PathError`, она называет путь сама
(`mkdir /data/repo/db: read-only file system`), поэтому дополнительной обёртки
не добавлял: она бы задвоила путь в самом частом случае. Важная деталь:
`MkdirAll` называет тот компонент, который не удалось создать, — при read-only
ФС это ровно каталог БД, а если в пути стоит файл-блокер, то он.

### 4. Документация

- `deploy/apprepo.env.example` — предупреждение у строки `APPREPO_DB`: вынесли
  БД из data-dir — добавьте её каталог в `ReadWritePaths=`.
- `deploy/apprepo.service` — существующий комментарий над `ReadWritePaths=`
  дополнен строкой про `APPREPO_DB` и синтаксисом нескольких путей
  (`ReadWritePaths=/data/repo/apps /data/repo/db`).
- `README.md` — абзац «`APPREPO_DB` — второй независимый путь» рядом с абзацем
  про NAMESPACE из T11: точный лог этого инцидента и объяснение, почему симптом
  обманчив (файл существует и принадлежит сервису, но каталог примонтирован
  read-only). Код-блок юнита в README синхронизирован с `deploy/apprepo.service`
  **машинно**: `diff <(awk '/^```ini$/{f=1;next} /^```$/{f=0} f' README.md)
  deploy/apprepo.service` — пусто.
- `CLAUDE.md` — инвариант про дублирование пути дополнен вторым путём
  (`APPREPO_DB`) и симптомом `status=1/FAILURE`; добавлен инвариант «ошибка
  `store.Open` называет файл, вызывающие путь не дублируют».

Юнит на `StateDirectory` не переводил, дефолтные значения не менял.

## Тесты

- `internal/store/store_test.go` → `TestOpenErrorNamesPath`: каталог 0500
  (`t.TempDir` + `os.Mkdir`), `Open` обязан вернуть ошибку с путём. Под root
  тест пропускается (`os.Geteuid() == 0` — права каталога записи не мешают);
  `t.Cleanup` возвращает права 0700, иначе `t.TempDir` не смог бы убрать за
  собой. В этой песочнице агент — root, поэтому тест **проверен отдельным
  прогоном от непривилегированного пользователя**
  (`setpriv --reuid=65534 … store.test -test.run TestOpenErrorNamesPath`):
  зелёный на исправленном коде и красный на коде без обёртки (
  `err = "apply schema: sqlite3: unable to open database file"; в тексте нет пути …`) —
  то есть тест действительно ловит дефект, а не проходит впустую.
- `internal/integration/edges_test.go` → существующие подтесты `TestAppNewErrors`
  усилены: оба теперь требуют путь в тексте ошибки. Эти два случая (data-dir
  под файлом-блокером; путь БД — каталог) работают и под root, так что в CI
  инвариант остаётся под наблюдением независимо от пользователя.

## Риски и что осталось за рамками

- Сообщение об ошибке стало длиннее и содержит путь к файлу БД. Это серверный
  лог, клиенту наружу оно по-прежнему не уходит (инвариант «внутренние ошибки —
  только в лог, клиенту `internal error`» не затронут: обёртка добавляется в
  `store.Open`, а не в ответах API).
- Подсказка про `ReadWritePaths` появится и в сценариях без systemd (например,
  локальный запуск с неверным `-db`). Текст сформулирован как «check directory
  permissions; under systemd also ReadWritePaths=», так что в не-systemd
  контексте он всё ещё осмысленный, хотя и с лишним хвостом.
- Автоматической проверки «каталог БД доступен на запись» на старте не делал:
  это дублировало бы работу SQLite и уводило бы от честного сообщения драйвера.
- Сам инцидент чинится на стороне пользователя одной строкой юнита:
  `ReadWritePaths=/data/repo/apps /data/repo/db` + `systemctl daemon-reload`.
