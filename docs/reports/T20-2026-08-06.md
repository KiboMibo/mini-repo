# T20 — роли в веб-интерфейсе и экран управления пользователями

Ветка `feat/T20-ui-users` от базы с T18. Слой ролей (`internal/auth`) и
операции над учётками (`internal/store`) взяты готовыми из T18 — здесь только
`internal/web`.

## Что сделано

1. Каждый UI-маршрут закрыт правом через `auth.Require`. Роль `deployer` в
   интерфейс не допускается вовсе и получает страницу-объяснение вместо
   пустого 403.
2. Кнопки и модалки, недоступные роли, не рендерятся: шаблоны спрашивают
   право (`.Can.App`, `.Can.Version`, `.Can.UserAdmin`, `.Can.UI`), а не имя
   роли.
3. Экран `/users` (только `PermUserAdmin`): список, создание, смена роли,
   блокировка/разблокировка, сброс пароля, удаление со строгим подтверждением.
4. Смена своего пароля — модалка в шапке, доступна любой роли с `PermUI`.
5. В шапке — имя, роль, ссылка на `/users` (только админ) и выход.

## Карта маршрутов и прав

| Маршрут | Право | Ответ роли без права |
|---|---|---|
| `GET /login`, `POST /login` | — (публичный) | — |
| `POST /logout` | только сессия | — |
| `GET /` | `PermUI` | 403, страница-объяснение |
| `GET /apps/{name}` | `PermUI` | 403 |
| `POST /password` (свой пароль) | `PermUI` | 403 |
| `POST /apps` | `PermApp` | 403 |
| `POST /apps/{name}/edit` | `PermApp` | 403 |
| `POST /apps/{name}/delete` | `PermApp` | 403 |
| `POST /apps/{name}/latest` | `PermApp` | 403 |
| `POST /apps/{name}/versions` | `PermVersion` | 403 |
| `POST /apps/{name}/versions/{version}/delete` | `PermVersion` | 403 |
| `GET /users` | `PermUserAdmin` | 403 |
| `POST /users` | `PermUserAdmin` | 403 |
| `POST /users/{id}/role` | `PermUserAdmin` | 403 |
| `POST /users/{id}/disabled` | `PermUserAdmin` | 403 |
| `POST /users/{id}/password` | `PermUserAdmin` | 403 |
| `POST /users/{id}/delete` | `PermUserAdmin` | 403 |

Маршрутов интерфейса без проверки прав не осталось. Единственное исключение
сделано осознанно: **`POST /logout` не требует `PermUI`** — иначе `deployer`,
которого интерфейс не пускает, не смог бы погасить свою сессию с той самой
страницы-объяснения (кнопка выхода в шапке отвечала бы 403). Логин публичен по
определению.

## Ключевые решения

### Отказ `deployer`у: почему страница, а не 403 и не редирект

`deployer` логинится успешно — пароль верный, сессия выдаётся. Значит
`RequireSession` его пропускает и редиректить на `/login` не за чем: получился
бы цикл «логин → `/` → логин». Отказ приходит на следующем звене — `PermUI`.

Ответ переопределён механизмом, заложенным в T18: `web.Register` заводит
собственный экземпляр `auth.Auth` с полем `Forbidden`, который рендерит
HTML-страницу вместо JSON API. `Auth` без состояния, поэтому `api.Register`
это не задевает.

```go
ui := &auth.Auth{Store: a.Store, Forbidden: h.forbidden}
guard := func(p auth.Permission, next http.Handler) http.Handler {
	return ui.RequireSession(ui.Require(auth.PermUI, ui.Require(p, next)))
}
```

`guard` — единственный способ повесить UI-маршрут (`form` = `guard` + CSRF), и
он всегда проверяет `PermUI` перед правом операции. Маршрут без права написать
можно только в обход обоих хелперов.

Страница (`templates/forbidden.html`) различает два случая: у роли нет `PermUI`
вовсе (deployer) — объясняет, что учётка машинная, и называет `/api/…` и
`/download/{app}/{version}` с Basic-аутентификацией; право есть, но не на эту
операцию (developer жмёт что-то от maintainer'а) — короткое «роль не позволяет»
и ссылка назад. Форма входа тоже предупреждает про `deployer` заранее.

### Права в шаблоны — правом, а не именем роли

В `view` добавлено поле `Can perms` (`UI`, `Version`, `App`, `UserAdmin`),
которое заполняет `baseView` из `Role.Can`. Сравнения строк роли в разметке нет
нигде: матрица прав живёт в `auth`, и разметка не должна её дублировать.

Скрыто: `New application` (index), `Edit` / `Delete application` / выбор latest
(app), кнопка удаления версии и `Upload version` (app), ссылка `Users` и модалка
смены пароля (layout) — вместе с самими модалками, а не только с кнопками:
`<dialog>` с формой в разметке — это подсказка, что попробовать через curl.

### Смена своего пароля

`store.SetUserPassword` гасит все сессии пользователя, поэтому после успешной
смены страницы всё равно нет — есть только редирект на логин. Сделано
предсказуемым: хендлер сам гасит куку (`LogoutUser`) и уходит на
`/login?m=password-changed`, где показывается зелёный баннер. Сообщения
адресуются **кодом из фиксированного словаря**, а не текстом из URL: свободный
текст на странице входа — готовый инструмент фишинга.

Ошибки: неверный текущий пароль — 401 «the current password is incorrect»,
пустой новый — 400, несовпадение повтора — 400; во всех случаях модалка
рендерится открытой рядом с баннером (механика `.Dialog` из T8/T9/T14).
Админский сброс пароля самому себе идёт по тому же пути на `/login`.

### `ErrLastAdmin` и самоудаление

`store.ErrLastAdmin` — отказ по правилу, а не сбой: 409 с текстом «cannot
demote/block/delete the last administrator — give the admin role to another
account first», а не 500. Самоудаление отсекается **до** проверки последнего
админа (иначе единственный админ получил бы невнятное «последний
администратор» вместо настоящей причины) — 409 «you cannot delete your own
account».

Удаление чужой учётки требует ввода имени точь-в-точь, как удаление приложения.

### Прочее

- `index.html` переведена с `{{if .Error}}` на общую механику `{{if eq .Dialog
  "new-app"}}`: иначе ошибка смены пароля открывала бы заодно и форму создания
  приложения (обе рендерятся на `/`).
- Дублирующийся `id="new-password"` (модалка смены своего пароля в layout и
  форма нового пользователя) разведён — на `/users` они на одной странице.
- Новых зависимостей нет. Логи деструктивных операций над учётками — по
  тому же образцу, что у приложений: только имена, без паролей и хешей.

## Как проверено

```
go build ./...                          OK
go vet ./...                            OK
go test -count=1 ./internal/web/...     ok (11.9s)
go test -count=1 ./...                  ok: api auth config files integration naming store web
gofmt -l internal/web                   пусто
```

| Требование | Чем подтверждено |
|---|---|
| каждая роль × каждый UI-маршрут: код и редирект | `TestRoutePermissionMatrix` — 15 маршрутов × 4 роли = 60 подтестов; у роли без права строго 403 **и** маркер страницы отказа, у роли с правом — ожидаемый код и `Location` |
| выход доступен всем ролям | `TestLogoutAllowedForEveryRole` (303 `/login` для всех четырёх) |
| deployer после логина — страница-объяснение, не цикл | `TestDeployerLandsOnExplanation`: логин 303, затем `GET /` = 403 **без** `Location`, в теле имя, роль, `/api/`, `/download/` |
| у developer'а нет Edit/Delete application, есть загрузка | `TestButtonsHiddenByRole` (нет `/apps/demo/edit`, `/apps/demo/delete`, `/apps/demo/latest`, есть `Upload version`) |
| ссылка на пользователей только у admin | `TestButtonsHiddenByRole` (`href="/users"` есть у admin, нет у developer и maintainer) |
| все новые POST без CSRF → 403 | `TestNewPostsRequireCSRF` — 6 маршрутов × 2 варианта (нет куки / нет поля) |
| последний админ не разжалуется — сообщение, не 500 | `TestLastAdminIsExplained` (понижение и блокировка: 409 + «last administrator», учётка не изменилась), `TestDeleteLastAdminByAnother` |
| самоудаление запрещено | `TestLastAdminIsExplained` (409 «your own account», alice на месте) |
| смена своего пароля | `TestChangeOwnPassword`: неверный текущий — 401 с текстом; повтор не совпал — 400; верный — 303 на `/login?m=password-changed`, старая сессия мертва, баннер на `/login`, вход с новым паролем работает |
| CRUD учёток целиком | `TestUserAdminFlow` (создание, дубль → 409, роль `root` → 400, блокировка, удаление с точным подтверждением) |
| мусор в `{id}` | `TestUnknownUserID` (404, не 500) |

**Тесты проверены на различимость.** Временная подмена
`form(auth.PermApp, h.createApp)` на прежний `RequireSession(csrf(…))` роняет
`TestRoutePermissionMatrix/create_app/{deployer,developer}` (303 вместо 403);
замена `{{if .Can.App}}` на `{{if true}}` в `app.html` роняет
`TestButtonsHiddenByRole/developer/apps/demo`. Обе правки откачены.

## Что осталось за рамками

- **README и `docs/api.md` не тронуты** — по границам задачи. В README раздел
  про UI теперь неполон: нет описания ролей, экрана `/users` и того, что
  `deployer` в интерфейс не заходит. Стоит отдельной задачей приёмочной волны.
- **Валидации имени пользователя нет** — как и в `apprepo user add`: требуется
  только непустая строка после `TrimSpace`. Имя пользователя не попадает ни в
  путь ФС, ни в URL (маршруты идут по `{id}`), поэтому `naming` здесь не нужен;
  если появятся требования к формату — это общее решение для UI, API и CLI.
- **Требований к паролю нет** (только «не пусто») — единая политика паролей
  тоже общая для трёх интерфейсов, вводить её в одном UI смысла нет.
- **Структурной защиты «новый маршрут обязан иметь право» нет.** `guard`/`form`
  делают правильный путь самым коротким, а матричный тест ловит забытое право
  только для маршрутов, перечисленных в его таблице. Новый маршрут нужно
  добавлять и туда — это отмечено комментарием у таблицы.
- Сброс пароля админом не требует ввода текущего пароля админа (это именно
  reset, а не смена своего) — учтено, но повторную аутентификацию для
  чувствительных действий сюда не закладывали.
