# T19 — права по ролям на API и управление пользователями

Ветка `feat/T19-api-roles` от `wave/app-artifactory-w6` (база — merge T18).
Владение: `internal/api/**`. `internal/web/`, `cmd/apprepo/`, `docs/api.md`,
`go.mod` не тронуты (T20/T21 и задача документации).

## Что сделано

1. Каждый маршрут `/api/…` и `/download/…` закрыт правом из матрицы T18 —
   `a.Require(perm, …)` внутри внутреннего `ServeMux`, то есть **после**
   `RequireBasic`, который стоит на всём `/api/`.
2. Добавлено управление учётками через API (`/api/users`, `PermUserAdmin`) и
   работа со своей учёткой (`/api/me`, доступно любой роли).
3. Управление пользователями журналируется тем же способом, что и деструктивные
   операции над приложениями: `api: user %q <действие> user %q`.

## Полная карта маршрутов и прав

| Маршрут | Право | deployer | developer | maintainer | admin |
|---|---|:-:|:-:|:-:|:-:|
| `GET /api/apps` | `PermRead` | ✔ | ✔ | ✔ | ✔ |
| `GET /api/apps/{name}` | `PermRead` | ✔ | ✔ | ✔ | ✔ |

| `GET /download/{name}/{version}` | `PermRead` | ✔ | ✔ | ✔ | ✔ |
| catch-all `/api/` (404 JSON) | `PermRead` | ✔ | ✔ | ✔ | ✔ |
| `PUT /api/apps/{name}/versions/{version}` | `PermVersion` | — | ✔ | ✔ | ✔ |
| `DELETE /api/apps/{name}/versions/{version}` | `PermVersion` | — | ✔ | ✔ | ✔ |

| `POST /api/apps` | `PermApp` | — | — | ✔ | ✔ |

| `GET /api/users` | `PermUserAdmin` | — | — | — | ✔ |
| `POST /api/users` | `PermUserAdmin` | — | — | — | ✔ |
| `PATCH /api/users/{username}` | `PermUserAdmin` | — | — | — | ✔ |
| `POST /api/users/{username}/password` | `PermUserAdmin` | — | — | — | ✔ |
| `DELETE /api/users/{username}` | `PermUserAdmin` | — | — | — | ✔ |
| `GET /api/me` | без права (`RequireBasic`) | ✔ | ✔ | ✔ | ✔ |
| `POST /api/me/password` | без права (`RequireBasic`) | ✔ | ✔ | ✔ | ✔ |

Маршрутов в `internal/api` больше нет: список сверен построчно с `Register`
(`git grep 'handle(\|api.HandleFunc\|mux.Handle' internal/api/api.go`), и тест
`TestRoleMatrix` перечисляет ровно эти строки.

Два решения, требующие взгляда командира:

- **`POST /api/apps/{name}/latest` → `PermVersion`.** В матрице явно названы
  «PUT версии, DELETE версии» и «POST/PATCH/DELETE приложения». Закрепление
  latest не создаёт и не удаляет приложение, зато выбирает, какая **версия**
  считается релизом; кто может удалить версию, тот и так двигает latest.
  Если задумывалось иначе — правка в одну строку `api.go` (и одна строка `perm`
  в таблице теста).
- **catch-all `/api/`** формально не маршрут (JSON-404 на неизвестный путь), но
  закрыт `PermRead` ради «ни одного маршрута без проверки»: у всех ролей право
  есть, поведение не изменилось, а учётка с неизвестной ролью (fail closed)
  получает 403 вместо 404.

## Контракты новых маршрутов

Объект пользователя (**без хеша пароля** — наружу уходит только эта структура):

```json
{"username":"bob","role":"developer","disabled":false,
 "created_at":"2026-08-06T12:00:00Z"}
```

`created_at` приведён к RFC 3339 UTC, как у приложений и версий (в `store` он
строкой `"2006-01-02 15:04:05"`).

| Маршрут | Тело | Успех | Ошибки |
|---|---|---|---|
| `GET /api/users` | — | 200, массив (сортировка по имени) | — |
| `POST /api/users` | `{"username","password","role"}` | 201 + объект | 400 `validation` (пустое имя/пароль, неизвестная роль, битый JSON), 409 `already_exists` |
| `PATCH /api/users/{username}` | `{"role"?,"disabled"?}` | 200 + объект | 404 `not_found`, 400 `validation`, 409 `last_admin` |
| `POST /api/users/{username}/password` | `{"password"}` | 204 | 404 `not_found`, 400 `validation` |
| `DELETE /api/users/{username}` | — | 204 | 404 `not_found`, 409 `self_delete`, 409 `last_admin` |
| `GET /api/me` | — | 200 `{"username","role"}` | — |
| `POST /api/me/password` | `{"current_password","new_password"}` | 204 | 403 `forbidden` (неверный текущий), 400 `validation` (пустой новый) |

Новые коды ошибок: `last_admin` (409) и `self_delete` (409). Лимит тела —
общий `maxJSONBody` (1 MiB) через тот же `http.MaxBytesReader`; формат ошибок —
общий `writeErr`. Пустое тело `PATCH` ничего не меняет (как у `PATCH` приложения).

## Ключевые решения

- **Право вешается на маршрут, а не проверяется внутри хендлера.** Хендлеры
  вообще не знают о ролях, забыть проверку в новом хендлере нельзя — она стоит
  в строке регистрации. Цена: один трёхстрочный хелпер вместо `api.HandleFunc`.
- **`ErrLastAdmin` → 409 `last_admin`, а не 422.** Это конфликт состояния
  установки (единственный живой админ), в одном ряду с `already_exists`;
  клиенту чинить нечего в теле запроса, надо завести второго админа. Сама
  защита — атомарная, в `store` (T18), API её не дублирует.
- **Удаление себя отбивается до `store`** — по пользователю из контекста
  (`auth.CurrentUser`), 409 `self_delete`. Через API `ErrLastAdmin` на `DELETE`
  недостижим (актор — включённый админ, значит админов ≥2, если цель не он сам),
  но обработчик оставлен: он ловит именно этот случай, если проверку «себя»
  когда-нибудь снимут — проверено мутацией, см. ниже.
- **`POST /api/me/password` без `Require`.** Не `PermRead` и не новое право:
  своя учётка — не ресурс с правом доступа. Проверка текущего пароля через
  `auth.CheckPassword` идёт до валидации нового (неверный текущий → 403 даже с
  пустым новым), сессии гасит `store.SetUserPassword`.
- **`created_at` через `time.ParseInLocation` с откатом на сырое значение**:
  нераспознанная строка отдаётся как есть, а не подменяется `0001-01-01`.
- Существующие четыре инлайновых `json.NewDecoder(MaxBytesReader…)` в `api.go`
  на новый `decodeJSON` **не переводились**: помимо косметики это поменяло бы
  код ошибки на пустом теле у `POST /api/apps` и `POST …/latest` (сейчас 400
  `validation`, стало бы 400 `invalid_name`/`invalid_version`). Не тот риск,
  ради которого стоит трогать зелёные маршруты в задаче про права.
- Новых зависимостей нет. Валидации имени пользователя, кроме «непустое», нет:
  в ФС имя не попадает, SQL параметризован, ограничений в `store`/CLI тоже нет.

## Журнал (инвариант «в лог только имена»)

```
api: user "alice" created user "bob" with role "developer"
api: user "alice" changed role of user "bob" from "developer" to "maintainer"
api: user "alice" disabled user "bob"        (и "enabled" при разблокировке)
api: user "alice" reset password of user "bob"
api: user "alice" deleted user "bob"
api: user "bob" changed own password
```

Пароли и хеши не логируются нигде: `hashPassword` их не печатает, в
`userJSON` поля под хеш нет.

```
go build ./...                      OK
go vet ./...                        OK
gofmt -l internal/api               пусто
go test -count=1 ./internal/api/    ok  24.3s
go test -count=1 ./...              ok: api auth config files integration naming store web
bash scripts/smoke.sh               SMOKE OK
```

| Требование задачи | Чем подтверждено |
|---|---|
| каждая роль × каждый маршрут, код успеха против 403 | `TestRoleMatrix` — 4 подтеста (по роли) × 20 маршрутов; ожидание считается из `Role.Can(perm)`, отказ дополнительно проверяется на тело `{"error":"forbidden"}` |
| deployer не заливает версию | `TestRoleMatrix/deployer`: `PUT …/versions/2.0.0` → 403 |
| deployer ничего не может в `/api/users` | `TestRoleMatrix/deployer`: все пять маршрутов `/api/users` → 403 |
| deployer качает и меняет свой пароль | `TestRoleMatrix/deployer`: `GET /download/myapp/1.0.0` → 200, `POST /api/me/password` → 204; отдельно `TestChangeOwnPassword` (старый пароль перестаёт пускать, новый пускает) |
| последнего админа не разжаловать / не заблокировать | `TestLastAdminAndSelfDelete`: `PATCH {"role":"developer"}` и `PATCH {"disabled":true}` → 409 `last_admin`; учётка цела (`GET /api/me` показывает `admin`); после появления второго админа то же понижение проходит, и права уходят вместе с ролью |
| последнего админа не удалить | там же: `DELETE /api/users/alice` → 409; без проверки «себя» store отдаёт `last_admin` (мутационная проверка) |
| удаление себя запрещено | `TestLastAdminAndSelfDelete` → 409 `self_delete` |
| заблокированный не проходит Basic | `TestDisabledUserCannotAuthenticate`: 200 → `PATCH disabled:true` → 401 `unauthorized` → разблокировка → снова 200 |
| в `/api/users` нет хеша | `TestUsersListShape`: в сыром теле нет ни `$2` (префикс bcrypt), ни подстроки `password`; плюс проверка состава полей и формата `created_at` |
| коды ошибок управления учётками | `TestUserValidation`: 409 дубль, 400 роль/пустой пароль/пустое имя/битый JSON, 404 на трёх маршрутах несуществующей учётки, пустой `PATCH` — no-op |
| сброс пароля админом реально работает | `TestAdminResetPassword`: старый пароль → 401, новый → 200 |

Тесты проверены на различимость тремя мутациями (каждая откачена):

1. `PUT …/versions/{version}` с `PermRead` вместо `PermVersion` → падает
   `TestRoleMatrix/deployer` («status = 201, want 403»).
2. Поле `password_hash` в `userJSON` → падает `TestUsersListShape`.
3. Снят блок «нельзя удалить себя» → падает `TestLastAdminAndSelfDelete`
   (приходит `last_admin` вместо `self_delete`).

## Что осталось за рамками

- `docs/api.md` не обновлялся (владелец — отдельная задача). Для неё готовое:
  новые маршруты и их коды — в разделе «Контракты новых маршрутов» выше;
  в таблицу кодов ошибок добавляются `last_admin` (409) и `self_delete` (409);
  403 `forbidden` (`{"error":"forbidden","message":"insufficient permissions"}`)
  становится общим ответом всех маршрутов при нехватке прав, а для
  `/download/…` это единственный не-plain-text ответ кроме 401.
- UI (`internal/web`) и CLI (`cmd/apprepo`) свои части ролей делают в T20/T21;
  ничего из их файлов не тронуто.
- Пагинации в `GET /api/users` нет — учёток в этой установке десятки, `ListUsers`
  и так читает всю таблицу.

## На что смотреть ревьюеру

1. Строки регистрации в `Register` — это и есть вся модель доступа; таблица
   маршрутов выше сверяется с ними глазами за минуту.
2. `POST /api/apps/{name}/latest` = `PermVersion` (см. «два решения» выше).
3. `/api/me/password` намеренно вне `Require` — если UI/CLI захотят повторить
   этот маршрут у себя, проверку текущего пароля надо повторить тоже.
4. Тест матрицы гоняет ~80 запросов с Basic Auth, каждый — bcrypt: пакет `api`
   стал считаться ~24 с вместо ~10 с. Это цена честной проверки прав реальными
   учётками, а не подменой контекста.
