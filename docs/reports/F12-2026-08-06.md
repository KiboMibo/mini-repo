## Находка 1 (test, важная) — имя учётки не нормализуется и не валидируется

**Как закрыта.** Одна функция `naming.NormalizeUsername` в
`internal/naming/naming.go`: обрезает пробелы по краям (`strings.TrimSpace`) и
проверяет остаток по `^[a-zA-Z0-9][a-zA-Z0-9._-]{0,63}$`. Один регексп закрывает
весь список из находки разом — двоеточие, управляющие символы, пробел внутри,
пустую строку, `"admin "`, `"   "`, кириллицу и длину >64.

Вызывается на **всех шести** путях (создание и поиск × три интерфейса):

| | создание | поиск |
|---|---|---|
| API | `api.createUser` | `api.(*server).mustUser` (имя из пути) |
| UI | `web.createUser` | по `id`, имя не участвует |
| CLI | `userAdd` | `mustUser` |

Копий нет: `strings.TrimSpace` из `internal/web/users.go:129` удалён вместе с
импортом `strings`, собственная проверка `username == ""` из
`internal/api/users.go:113` — тоже.

Невалидное имя в пути API даёт **404**, а не 400, — ровно как имя приложения
(`docs/api.md`: «такого приложения не может существовать»). Это же сохраняет
403/404-паритет API и UI, на который смотрит `TestPermissionParityAPIvsUI`.

**Про кириллицу — решено запретить**, вместе со всем не-ASCII. Три причины,
записаны и в комментарии к `userNameRe`:

1. Имя уходит в HTTP Basic, а RFC 7617 не задаёт совместимой кодировки для
   `user:pass` — клиенты шлют её то в latin-1, то в UTF-8. Учётка с не-ASCII
   именем аутентифицируется не отовсюду: та же болезнь, что у двоеточия, только
   тише и невоспроизводимо.
2. Гомоглифы: кириллические `а`, `о`, `е` неотличимы от латинских на глаз — это
   ровно та пара визуально одинаковых учёток, ради которой имя и нормализуется.
   Юникод-нормализация не помогает: NFC разные алфавиты не сводит.
3. Имя ходит в пути URL (`/api/users/{username}`) и в строках журнала.

**Чем подтверждено.**
- `TestUsernameHandlingConsistency` (PoC, не правился) — зелёный, и **не
  вхолостую**: в журнале прогона видно `created user "pad-api"` и
  `created user "pad-ui"` — обе ветки дошли до 201/303 и сравнили сохранённое
  имя, а не разошлись по раннему `return`.
- Новый `internal/api/api_f12_test.go:TestUsernameValidatedOnCreate`: `" ops "`
  → 201 и находится как `ops`; `"  ops"` → 409 (дубль, а не вторая учётка);
  `ci:bot`, `"   "`, `""`, `-lead`, `with space`, `оператор`, 65 символов → 400.
- `internal/naming/naming_test.go:TestNormalizeUsername`.
- CLI проверен руками: `user add "ci:bot"` → `invalid username …`, exit 2;
  `user add "  "` → `username must not be empty`, exit 2; `user add " ops "` →
  `user "ops" created`, и в `user list` лежит `ops`.

## Находка 2 (sec, важная) — CSRF: `/api/` принимает тело HTML-формы

**Выбранный вариант — денилист, а не строгий `application/json`.** Отклоняются
`text/plain` и `multipart/form-data` → **415** `unsupported_media_type`; запрос
без `Content-Type` и с `application/json` работает как прежде.

**Почему не строгий вариант — две причины, вторая решающая:**

1. Пришлось бы синхронно править все `curl -u … -d '{…}'` в `docs/api.md`,
   `README.md` и `scripts/smoke.sh` (задача это разрешает, но это шум в доках).
2. **Строгий вариант невозможен, не правя PoC-тесты, которые править нельзя.**
   Восемь мест в замороженных `internal/integration/r6_*_test.go` шлют JSON-тело
   вообще без заголовка `Content-Type` — `r6_cli_test.go:101`,
   `r6_leaks_test.go:115,117`, `r6_lifecycle_test.go:167,189`,
   `r6_migration_test.go:150`, `r6_parity_test.go:265,294` (хелпер
   `wantStatusAs` заголовков не ставит). Требование `application/json` покрасило
   бы их все.

Денилист при этом закрывает ровно вектор атаки: HTML-форма умеет три enctype,
и валидным JSON становятся только эти два; третий, `urlencoded`,
percent-кодирует `{`, `"` и `:`. Обоснование записано комментарием к `formBody`
в `internal/api/api.go`, как просил ревьюер.

**Где стоит рубеж.** В `decodeJSON` — единственной точке разбора JSON-тела в
пакете. Три хендлера, декодировавших тело напрямую (`createApp`, `updateApp`,
`setLatest`), переведены на `decodeJSON`; это минус 9 строк и гарантия, что на
новом маршруте проверку забыть нельзя. Побочный эффект, который стоит знать
ревьюеру: `POST /api/apps` и `POST /api/apps/{name}/latest` с **пустым** телом
теперь отвечают `400 invalid_name` / `400 invalid_version` вместо
`400 validation` — код ответа тот же, `error` другой; тестами это не покрывалось
и в `docs/api.md` не описано.

**Чем подтверждено** (критерий приёмки ревьюера выполнен целиком):
`internal/api/api_f12_test.go:TestFormBodyRejectedOnUserRoutes` — `POST
/api/users` и `POST /api/users/{u}/password` с `text/plain`,
`text/plain;charset=UTF-8` и `multipart/form-data` → 415, учётка `evil` не
создана (проверено и через `PATCH`, и через список), пароль админа не заменён
(старым паролем всё ещё пускает); те же тела с `application/json` → 201/204;
без заголовка → 201. Плюс `TestFormBodyRejectedOnAppRoutes` и проверка в
`scripts/smoke.sh` на живом бинарнике.

## Находка 3 (qa, важная) — `scripts/smoke.sh` не покрывал волну 6

**Как закрыта.** Три учётки заводятся через CLI (`ci`/deployer, `dev`/developer,
`mnt`/maintainer; `alice` — admin), дальше по одному запрету и одному разрешению
на роль через HTTP:

| Роль | Запрет | Разрешение |
|---|---|---|
| deployer | `PUT` версии → 403, на диске ничего; `GET /` в UI → 403 | логин 303, `GET /download/myapp/1.2.0` → 200 |
| developer | `POST /api/apps` → 403 | `PUT` версии → 201 |
| maintainer | `GET /api/users` → 403 | `POST /api/apps` → 201 |
| admin | — | завёл и удалил учётку, видит её в списке |

Плюс: последнего админа не разжаловать ни через API (409), ни через CLI (exit 1,
и после этого `role` у alice всё ещё `admin`), и тело HTML-формы на
`/api/users` → 415 без создания учётки.

Стиль скрипта не тронут: `set -euo pipefail`, тот же временный каталог, тот же
поиск свободного порта. UI-логин делается двумя запросами (взять `apprepo_csrf`
из заголовка `Set-Cookie`, отправить его же полем формы) — без новых
зависимостей, на `curl` и `sed`.

**Чем подтверждено.** `bash scripts/smoke.sh` → `SMOKE OK`. Отдельно проверено,
что новые проверки **различают**, а не проходят всегда: тем же curl-сценарием
admin получает `GET /` = **200**, а deployer — **403**; CLI-отказ разжаловать
последнего админа печатает `refused: no active administrator would be left in
the system` и выходит с кодом 1 (а не падает по другой причине).

## Минимальная длина пароля — сознательно НЕ введена

Задача просила «заодно ввести минимальную длину пароля». **Не сделано, и это
осознанный отказ, а не пропуск.** Любой минимум выше 2 байт делает
`TestUsernameHandlingConsistency` — приёмочный тест находки 1, который править
нельзя, — **зелёным вхолостую**:

- подтест `api_и_ui_одинаково_нормализуют_имя` создаёт учётку с паролем `"pw"`
  (2 байта). Минимум 8 → оба интерфейса отвечают 400, тест видит
  `apiOK == uiOK == false` и выходит по `if !apiOK { return }`, ни разу не
  сравнив, как имя легло в БД;
- подтест `созданная_учётка_умеет_войти` использует `"bot-pw"` (6 байт) — то же
  самое.

То есть требование «PoC обязаны позеленеть от правки» было бы формально
выполнено, а фактическая приёмка находки 1 — потеряна. Максимум, совместимый с
замороженным набором, — 2 байта, что от нынешнего «непустой» не отличается
ничем осмысленным. Ломаются и другие места (`api_t19_test.go:154`:
`{"username":"bob","password":"x"}` ждёт 409 `already_exists`, а получил бы 400).

Политика длины при этом уже живёт в одном месте — `naming.ValidatePassword`, — и
поднять минимум это одна строка. **Делать это надо одной задачей вместе с
ревизией фикстур** `r6_parity_test.go`, `r6_leaks_test.go`, `api_t19_test.go`,
`web/roles_test.go`. Рекомендация: 8 байт.

## Риски и на что смотреть ревьюеру

1. **Существующие учётки с невалидными именами.** Миграции имён нет. Если в
   боевой БД уже лежит учётка вида `ci:bot` или с кириллицей, она продолжит
   работать в списке (`ListUsers` ничего не проверяет), но управлять ею через
   API и CLI станет нельзя — `mustUser` отвергнет имя. Через UI она управляема,
   там адресация по `id`. Вероятность низкая (такие учётки и раньше не могли
   войти), но перед обновлением стоит глянуть `apprepo user list`.
2. **Пустое тело у `POST /api/apps` и `POST .../latest`** теперь даёт
   `invalid_name`/`invalid_version` вместо `validation` (см. находку 2).
3. **Денилист вместо строгого Content-Type** — точечная мера. Если завтра в
   HTML появится четвёртый enctype или клиент начнёт слать JSON под другим
   типом, список придётся пересмотреть; комментарий в коде это фиксирует.
4. **Минимум длины пароля не введён** — см. отдельный раздел, там же условия,
   при которых его можно поднять.
