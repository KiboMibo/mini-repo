# T12 — Переименование и удаление приложений и версий (слои store и files)

Ветка: `feat/T12-rename-delete` (от `wave/app-artifactory-w5`). Волна 5,
задача вне исходного плана — постановка от пользователя. Remote нет, PR не
создавался.

Решения пользователя, зафиксированные в реализации: удаление жёсткое (никакого
soft-delete), при переименовании каталог на диске переименовывается, старые
ссылки `/download/старое-имя/...` осознанно ломаются (алиасов и редиректов
нет), редактируются имя и описание.

## Реализованные сигнатуры (дословно контракт)

```go
// internal/store
func (s *Store) UpdateApp(id int64, name, description string) error
func (s *Store) DeleteApp(id int64) error
func (s *Store) DeleteVersion(id int64) error // существовал; уточнены контракт и покрытие

// internal/files
func (st *Storage) RenameApp(oldName, newName string) error
func (st *Storage) RemoveApp(app string) error
func (st *Storage) RemoveVersion(app, version string) error
```

Дополнительные детали контракта, на которые может закладываться T13:

- `UpdateApp` валидирует `name` через `naming.ValidateAppName` (ошибка → 400) и
  возвращает `ErrExists`, если имя занято другим приложением; несуществующий
  `id` → ошибка `app %d not found`.
- `DeleteApp` и `DeleteVersion` идемпотентны: удаление отсутствующей строки —
  не ошибка (как и было у `DeleteVersion`).
- `RenameApp` возвращает `files.ErrFileExists`, если целевой каталог уже есть
  (в т.ч. если он пустой); `oldName == newName` — no-op; отсутствие исходного
  каталога (у приложения ещё нет версий) — не ошибка.
- `RemoveApp`/`RemoveVersion` — `os.RemoveAll`, отсутствие каталога не ошибка;
  все ошибки ФС возвращаются как есть, ничего не глушится.

## Порядок операций (БД → ФС) и почему так

Рекомендованный порядок «правка БД в транзакции → операция с ФС → commit»
недостижим внутри заданного контракта: `store` не знает о `files`, а сигнатуры
не принимают ни хука, ни транзакции — оркестрация неизбежно живёт этажом выше
(T13). Поэтому выбран максимально близкий вариант:

1. **Сначала БД, потом диск.** Осиротевшая строка, ведущая на несуществующий
   файл, ломает скачивание и выглядит как порча данных; осиротевший каталог на
   диске — это просто мусор, который видно и который можно снести руками. При
   отказе ФС ошибка возвращается наверх (не глушится), пользователь видит, что
   удаление/переименование не завершилось.
2. **Каждый метод `store` атомарен сам по себе.** `UpdateApp` — один `UPDATE`
   (имя и описание меняются одной строкой), `DeleteApp` — один `DELETE` с
   каскадом по FK. SQLite оборачивает каждый оператор в неявную транзакцию, так
   что явные `BEGIN/COMMIT` вокруг единственного оператора ничего бы не
   добавили, кроме кода. Промежуточного состояния «имя поменялось, описание
   нет» или «приложение удалено, версии остались» не существует.
3. **Коллизия имени ловится до диска.** `UpdateApp` (UNIQUE на `apps.name`)
   вызывается первым, `RenameApp` — только после успеха. `RenameApp` вдобавок
   проверяет целевой каталог сам и делает `os.Rename` (атомарен в пределах ФС),
   ничего не перезаписывая.
4. **Компенсация вместо rollback.** Если `files.RenameApp` упал, T13 возвращает
   имя обратно повторным `UpdateApp(id, oldName, …)` — это описано в doc-комментарии
   `UpdateApp`, чтобы контракт читался по коду, а не по отчёту.

## Изменённые файлы

- `internal/store/store.go` — `UpdateApp`, `DeleteApp`; уточнён doc-комментарий
  `DeleteVersion` (снятие пина через FK, идемпотентность, порядок с `files`).
- `internal/files/files.go` — `RenameApp`, `RemoveApp`, `RemoveVersion`; из
  `validate` выделен `validateAppVersion` (тот же рубеж `naming` для операций
  без имени файла) — дублирования проверок не появилось.
- `internal/store/store_t12_test.go` — новый; хелперы `mustApp`/`mustVersion`
  переиспользованы из `store_r2_test.go`.
- `internal/files/files_t12_test.go` — новый; хелперы `newStorage`/`entries`
  переиспользованы из `files_test.go`.

Схема БД не менялась: `apps.latest_override_version_id REFERENCES versions(id)
ON DELETE SET NULL` и `versions.app_id REFERENCES apps(id) ON DELETE CASCADE`
уже были в `schema.sql`, `PRAGMA foreign_keys(1)` стоит в DSN на каждое
соединение. Снимать пин явно не потребовалось — проверено тестом.

  повторный вызов удаления идемпотентен и добьёт каталог.

## Риски и точки внимания для ревьюера

- Ломающееся поведение: после переименования старые `/download/{old}/...`
  отдают 404. Это осознанное решение пользователя, зафиксировано выше.
- `RenameApp` проверяет целевой каталог `Lstat`'ом, а не атомарно: в stdlib нет
  `RENAME_NOREPLACE`. Гонку двух переименований сериализует UNIQUE на
  `apps.name` в БД, которая по выбранному порядку срабатывает раньше.
- `UpdateApp` валидирует имя, а исторический `CreateApp` — нет (валидация там у
  вызывающего). Расхождение осознанное: не менял поведение существующего
  метода, но новый путь ведёт к переименованию каталога и обязан отсекать
  мусор до записи в БД.
