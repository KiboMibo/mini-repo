вне исходного плана — постановка от пользователя, слои хранения готовы в T12.
Remote нет, PR не создавался. Параллельно шла T14 (веб-UI, `internal/web/`) —
её изменений эта ветка не видит.

Тронуты только свои файлы: `internal/api/api.go`, `internal/api/api_test.go`,
новый `internal/api/api_t13_test.go`. `docs/api.md` намеренно не обновлялся
(документация — отдельная задача), `internal/web/`, `go.mod` не тронуты.

## Реализованные маршруты

| Маршрут | Тело | Успех | Ошибки |
|---|---|---|---|
| `PATCH /api/apps/{name}` | `{"name","description"}`, оба поля необязательны | `200` + объект приложения в формате `GET /api/apps/{name}` (с `versions`, `latest`, `versions_count`) | `400 invalid_name`, `400 validation`, `404 not_found`, `409 already_exists`, `500 internal` |
| `DELETE /api/apps/{name}` | — | `204`, тело пустое | `404 not_found`, `500 internal` |
| `DELETE /api/apps/{name}/versions/{version}` | — | `204`, тело пустое | `400 invalid_version`, `404 not_found`, `500 internal` |

Все три висят на том же `api`-муксе за `json401(a.RequireBasic(...))`, что и
остальной `/api/*`, — отдельной обвязки авторизации не добавлялось. Новых
кодов ошибок нет, лимит тела 1 MiB — общий `maxJSONBody` через
`http.MaxBytesReader`, как у `createApp`/`setLatest`.

Семантика PATCH: поля — `*string`, поэтому «поле отсутствует» отличается от
«поле пустое». Оба поля отсутствуют (`{}` или вовсе пустое тело) — 200 и
никаких изменений; `{"name":""}` — `400 invalid_name` (пустая строка не
проходит `naming.ValidateAppName`); переименование в собственное имя — no-op,
а не конфликт с самим собой.

## Порядок операций и компенсация

**Переименование — БД, потом диск.** Сначала `store.UpdateApp`: занятое имя
ловит UNIQUE на `apps.name`, и в этом случае до диска дело вообще не доходит —
файлы гарантированно не тронуты. Только после успешного UPDATE зовётся
`files.RenameApp`.

Если `RenameApp` упал (например, каталог назначения уже занят посторонним
каталогом, которого нет в БД → `files.ErrFileExists`), хендлер **компенсирует**
до того, как ответить: повторный `store.UpdateApp(a.ID, a.Name, a.Description)`
возвращает и прежнее имя, и прежнее описание. Иначе строка в БД указывала бы на
несуществующий каталог — состояние хуже осиротевшего каталога, и именно это
предписывает доккомментарий `store.UpdateApp`. Ошибка самого отката не может
быть передана клиенту осмысленно, поэтому она уходит в лог
(`api: rollback rename ... failed: ...`), а клиенту отдаётся исходная причина:
`409 already_exists` для `ErrFileExists`, иначе `500 internal`.

**Удаление — БД, потом диск.** `store.DeleteApp` (версии уносит FK
`ON DELETE CASCADE`) / `store.DeleteVersion`, затем `files.RemoveApp` /
`files.RemoveVersion`. Ошибка удаления с диска **не глотается**: пользователь
просил, чтобы файлы реально исчезали, поэтому клиент получает `500 internal`, а
настоящий текст ошибки (путь ФС) пишется в серверный лог — инвариант о
генеричных 500 соблюдён. Снятие `latest_override` при удалении версии делает FK
`ON DELETE SET NULL`, latest пересчитывается на лету — руками ничего не
трогаем.

## Чем подтверждён каждый сценарий

Все проверки диска смотрят в реальный `files.Storage.Root` (`newMuxDir`), а не
только на ответы API.

| Сценарий | Тест |
|---|---|
| Переименование меняет путь скачивания | `TestPatchAppRename`: `/download/oldname/1.0.0` → 404, `/download/newname/1.0.0` и `/latest` отдают исходные байты; каталог `oldname` исчез, `newname/1.0.0/oldname-1.0.0` на месте; в ответе PATCH `download_url` уже новый |
| Переименование в занятое имя → 409, файлы не тронуты | `TestPatchAppNameTaken`: 409 `already_exists`, оба каталога и оба файла на месте, обе загрузки скачиваются, `GET /api/apps/one` по-прежнему `one` |
| Компенсация при неудачном `RenameApp` | `TestPatchAppRenameRollback`: каталог назначения занят посторонним, ответ 409, а `GET /api/apps/app` снова 200 с прежними именем и описанием, `GET /api/apps/squatter` → 404, файл и скачивание живы |
| Удаление версии: файла нет, остальные целы | `TestDeleteVersion`: 204 с пустым телом, каталог `2.0.0` исчез, `1.0.0/myapp-1.0.0` на месте и скачивается, `versions_count` = 1 |
| Удаление версии-latest → latest пересчитался | `TestDeleteLatestVersion`: удаление авто-latest 3.0.0 → latest 2.0.0; закреплённой override-версии 1.0.0 → пин снят, latest снова 2.0.0; последней версии → `GET latest` 404 |
| Удаление приложения: каталог исчез целиком | `TestDeleteApp`: 204 с пустым телом, каталога `doomed` нет, `GET` приложения и `/download` → 404; соседнее приложение и его файл не задеты |
| Удаление несуществующего → 404 | `TestDeleteApp` (повторное удаление и заведомо чужое имя), `TestDeleteVersion` (повторное удаление версии, несуществующее приложение, невалидная версия → 400) |
| Новые маршруты без Basic Auth → 401 | `TestUnauthorizedMutations`: все три маршрута дают 401 с `WWW-Authenticate` и JSON `unauthorized`; после попыток приложение, версия и файл на месте |

Тесты проверены на способность ловить дефект (мутационная проверка, изменения
откачены): снятие компенсации роняет `TestPatchAppRenameRollback` (404 «app not
found» — ровно та порча, от которой она защищает); подмена `files.RemoveApp`,
`files.RemoveVersion` и `files.RenameApp` на no-op роняет `TestDeleteApp`,
`TestDeleteVersion` и `TestPatchAppRename`/`TestPatchAppRenameRollback`
соответственно.

## Что переиспользовано вместо нового кода

- Хелперы `writeErr`/`internalErr`/`writeJSON`, `mustApp`, `maxJSONBody`,
  `appInfo` — как есть, ничего параллельного не заведено.
- Вынесены два хелпера, потому что новые хендлеры повторяли бы существующие
  блоки дословно: `mustVersion` (валидация версии + выборка + 400/404) —
  теперь общий для `getVersion` и `deleteVersion`; `writeAppDetail` (объект
  приложения со списком версий) — общий для `getApp` и `updateApp`, он же
  гарантирует, что PATCH и GET отдают буквально один формат, а не два похожих.
- В тестах `newMux` разделён на `newMux` и `newMuxDir` (второй отдаёт ещё и
  корень файлов); существующие вызовы не менялись.

Новых зависимостей нет. Из stdlib добавлен только `io` — для `errors.Is(err,
io.EOF)`, чтобы PATCH с полностью пустым телом считался пустым патчем, а не
битым JSON.

## Риски и точки внимания для ревьюера

- **`docs/api.md` разошёлся с кодом** — три маршрута описаны только здесь. По
  постановке документацию обновляет отдельная задача; это осознанный, а не
  забытый долг.
- **Переименование не атомарно между БД и ФС.** Между успешным UPDATE и
  `RenameApp` есть окно: параллельное скачивание в этот момент получит 500
  «stored file unavailable». Компенсация закрывает исход «упало», но не окно —
  для однопроцессного сервиса с редкими переименованиями это принято
  сознательно, транзакция поверх ФС потребовала бы блокировки уровня
  приложения.
- **Осиротевший каталог возможен** в обратной ситуации: строки в БД удалены, а
  `RemoveApp` упал. Клиент получит 500 и увидит, что приложение уже исчезло из
  API, но каталог останется на диске. Выбор в пользу этого исхода, а не
  обратного, сделан осознанно (строка без файлов хуже файлов без строки), и
  ошибка видна в логе.
- **Старые ссылки на скачивание ломаются** при переименовании — алиасов и
  редиректов нет, это зафиксированное решение пользователя из T12.
