# F10 — важные находки приёмки волны 5

Ветка `fix/F10-rename-race` от `wave/app-artifactory-w5`. Закрыты три находки
приёмки: гонка «переименование во время загрузки» (В1), несимметричный код
ответа в `web.editApp` (В2), пробел в `scripts/smoke.sh` (В3).

## В1 — гонка «переименование во время загрузки»

**Что было.** `PUT` версии с медленным телом + `PATCH` с переименованием
посередине: `PUT` отвечал 201, файл ложился под СТАРЫМ именем каталога, а
строка в БД принадлежала уже новому. `GET /download/{новое}/{версия}` → 500, в
data-dir оставался лишний каталог со старым именем, который потом блокировал
переименование обратно (409). Чинилось только руками.

**Почему.** Каталог приложения создавался `MkdirAll` внутри `files.Save` уже
после стриминга тела, то есть после того, как переименование успело сдвинуть
и строку, и каталог. Ничто не связывало эти две операции.

**Что сделано.**

1. `files.Save` распался на две фазы:
   - `Prepare` — валидация имён, рубеж по типу каталога, стриминг тела в
     `{Root}/.tmp` с подсчётом SHA-256. Ничего под `{Root}/{app}` не создаётся,
     замок не берётся: тело большого файла льётся минутами.
   - `(*Upload).Commit(check)` — под замком по имени приложения: вызывает
     `check`, повторяет рубеж по типу, `MkdirAll` + эксклюзивный `os.Link`.
     Временный файл убирается в любом исходе.
   `Save` остался тонкой обёрткой `Prepare` + `Commit(nil)` — прежние
   вызывающие (и все тесты волны) не менялись.
2. Тем же замком накрыты операции, двигающие каталог приложения:
   `RenameApp` (оба имени, в отсортированном порядке — иначе встречные
   переименования могли бы взаимно заблокироваться), `RemoveApp`,
   `RemoveVersion`. Они берут замок сами: забыть его на стороне хендлера
   нельзя.
3. `api.putVersion` и `web.saveUpload` передают в `Commit` перепроверку
   `stillNamed`: под замком перечитывается строка по тому имени, с которым
   загрузка начиналась, и сверяется ID. Не совпало — 409
   (`already_exists` в API, страница с текстом в UI), временный файл убран,
   на диске не создано ничего.

**Почему это корректно.** Порядок деструктивных операций в проекте —
БД, затем диск (инвариант из CLAUDE.md). Значит для любого чередования:

- перепроверка увидела старое имя ⇒ переименование строки ещё не прошло ⇒
  публикация происходит до `os.Rename`, и переименование каталога унесёт
  свежий файл вместе с остальным содержимым;
- перепроверка не увидела ⇒ строку уже переименовали ⇒ 409 и чистый диск.

Третьего исхода нет: и перепроверка, и `os.Rename` идут под одним и тем же
замком.

**Где живёт замок и почему.** В `internal/files`, полями `Storage`
(`map[string]*appLock` под общим `sync.Mutex`, счётчик ссылок стирает запись
при последнем разблокировании — карта не растёт). Причины:

- `app.New` отдаёт один и тот же `*files.Storage` и в `api.Register`, и в
  `web.Register` — оба хендлерных пакета получают общий замок бесплатно, без
  правки сигнатур и без риска завести по независимой карте на пакет;
- сериализуется ровно то, чем владеет `files`, — раскладка каталогов внутри
  `Root`; отдельный пакет-хелпер добавил бы имя и зависимость, не добавив
  ничего к смыслу;
- сервис однопроцессный (один бинарник, никакой горизонтальной репликации —
  CLAUDE.md и systemd-юнит), поэтому внутрипроцессного мьютекса достаточно:
  никто вне процесса в data-dir не пишет. Файловые блокировки (`flock`) были
  бы платой за гарантию, которая здесь не нужна.

**Чем подтверждено.** `internal/integration/f10_race_test.go`:

- `TestUploadDuringRenameAPI` / `TestUploadDuringRenameUI` — детерминированный
  репро. Тело останавливается после первых 4 KiB; тест ждёт появления
  temp-файла нужного размера в `.tmp` (временный файл создаётся уже после
  разбора имени приложения и проверки дубля, то есть хендлер гарантированно
  внутри стриминга и ещё не опубликовал файл), проводит переименование
  целиком, отпускает тело. Проверяется: 409; каталога со старым именем нет;
  `.tmp` пуст; каждая строка в БД скачивается с 200 (ни одного 500);
  несозданная версия — 404; переименование обратно проходит.
- `TestUploadsRacingRenameStayConsistent` — то же без синхронизации, шесть
  загрузок и переименование стартуют разом; проверяется инвариант, а не коды.

На коде до фиксации оба детерминированных теста падают ровно как в находке:

## В2 — `files.ErrFileExists` в `web.editApp`

Занятый каталог-приёмник уезжал в 500, тогда как `api.updateApp` для того же
`files.ErrFileExists` отдаёт 409. Добавлена отдельная ветка: 409 со страницей
и текстом «a storage directory named %q already exists — nothing was renamed
on disk», диалог редактирования остаётся открытым, как у прочих ошибок правки.

**Внимание ревьюеру.** Существующий тест волны
`TestEditAppRenameRevertsOnDiskFailure` (`internal/web/web_test.go`) фиксировал
именно код 500 для этого случая — то есть ровно то поведение, которое находка
требует изменить. Утверждение статуса поправлено на 409 (одна строка плюс
комментарий); все остальные проверки теста — откат имени в БД, повторно
открытый диалог, файл на месте — не тронуты. Другого способа закрыть В2 нет.

## В3 — `scripts/smoke.sh`

Сценарий на собранном бинарнике не покрывал ни `PATCH`, ни оба `DELETE`.
Добавлены три блока (стиль скрипта прежний — `set -euo pipefail`, временный
каталог, свободный порт, проверки через коды `curl`):

- переименование: скачивание по новому имени отдаёт тот же SHA-256, старое имя
  → 404, `$DATA/renamed` появился, `$DATA/myapp` исчез;
- удаление версии: 204, `$DATA/renamed/1.2.0` исчез, latest пересчитался на
  1.0.0, скачивание удалённой версии → 404;
- удаление приложения: 204, `test ! -d "$DATA/renamed"`, `GET` → 404.

## Что осталось за рамками

- `docs/api.md` не тронут по условию задачи. Новый повод для `409
  already_exists` на `PUT` (приложение переименовали или удалили во время
  загрузки) там не описан — строчку стоит добавить отдельно.
- Гонка «удаление приложения во время загрузки» закрыта тем же рубежом только
  частично: если перепроверка успела пройти до удаления строки, публикация
  состоится, файл унесёт `RemoveApp`, а вставка версии упадёт на внешнем ключе
  и вернёт 500 вместо 409. Диск при этом остаётся консистентным, лишнего
  каталога не появляется. Отдельной находки на это нет; чинится расширением
  перепроверки на всю вставку (то есть транзакцией), это заметно больше кода.
- `files.Save` в продуктовом коде больше не вызывается (только в тестах волны
  и как удобная обёртка). Удалять не стал: правка существующих тестов волны
  запрещена, а сама обёртка — шесть строк.
