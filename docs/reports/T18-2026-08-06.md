# T18 — роли пользователей и управление учётками (хранение и аутентификация)

Ветка `feat/T18-roles` от `wave/app-artifactory-w6`. Фундамент волны 6: на
сигнатуры отсюда закладываются T19 (API), T20 (UI), T21 (CLI).

## Что сделано

Учётка получает **одну глобальную роль** из четырёх (`deployer`, `developer`,
`maintainer`, `admin`) и флаг `disabled` (блокировка без удаления). Права
фиксированы матрицей: `deployer` только читает и качает и **в веб-интерфейс не
допускается вовсе**; `developer` добавляет версии; `maintainer` — ещё и
приложения; `admin` — ещё и пользователей. Существующие учётки при обновлении
становятся админами, то есть текущее поведение («все равны и могут всё»)
сохраняется.

В объёме на уровне store: список, создание, смена роли, сброс пароля админом и
смена своего пароля (одна операция `SetUserPassword`), блокировка/разблокировка,
удаление. HTTP-хендлеров здесь нет — их делают T19/T20/T21.

## Реализованные сигнатуры (дословно)

```go
// internal/auth
type Role string
const (
	RoleDeployer   Role = "deployer"
	RoleDeveloper  Role = "developer"
	RoleMaintainer Role = "maintainer"
	RoleAdmin      Role = "admin"
)
func AllRoles() []Role
func ParseRole(s string) (Role, error)

type Permission int
const (
	PermRead      Permission = iota
	PermVersion
	PermApp
	PermUserAdmin
	PermUI
)
func (r Role) Can(p Permission) bool
func (a *Auth) Require(p Permission, next http.Handler) http.Handler

type Auth struct {
	Store     *store.Store
	Forbidden http.HandlerFunc // новое поле, см. «Отказ 403»
}

// internal/store
type User struct {
	ID           int64
	Username     string
	PasswordHash string
	Role         string
	Disabled     bool
	CreatedAt    string
}
func (s *Store) CreateUser(username, passwordHash, role string) error
func (s *Store) ListUsers() ([]*User, error)
func (s *Store) GetUserByID(id int64) (*User, error)
func (s *Store) SetUserRole(id int64, role string) error
func (s *Store) SetUserPassword(id int64, passwordHash string) error
func (s *Store) SetUserDisabled(id int64, disabled bool) error
func (s *Store) DeleteUser(id int64) error
func (s *Store) CountAdmins() (int, error)
var ErrLastAdmin = errors.New("last admin")
```

Контракт соблюдён дословно, включая `CreatedAt string` (была `time.Time`;
`User.CreatedAt` нигде за пределами `store` не использовалась, шаблоны UI её не
рендерили). В БД это строка `"2006-01-02 15:04:05"` UTC — годится и для вывода
как есть, и для парсинга.

## Ключевые решения

### Миграция существующей БД

`schema.sql` идемпотентна через `CREATE TABLE IF NOT EXISTS`, но по этой же
причине существующую таблицу она не трогает, а `ALTER TABLE` в SQLite не умеет
`IF NOT EXISTS`. Поэтому в `store.Open` после применения схемы идёт
`migrateUsers`: он читает имена колонок из `pragma_table_info('users')`
(табличная форма `PRAGMA table_info`) и выполняет `ALTER TABLE users ADD COLUMN`
только для недостающих. Существующие строки получают `role='admin'` из
`DEFAULT` — прежнее поведение сохраняется без отдельного `UPDATE`.

Идемпотентность: на таблице, где обе колонки уже есть, выполняется один
`SELECT`. Новая БД создаётся сразу с колонками, миграция для неё — no-op.

Чем подтверждено: `TestMigratePreT18DB` создаёт БД **точно старой схемой**
(сырой `sql.Open` + `CREATE TABLE users` без `role`/`disabled` + `INSERT`),
затем открывает её через новый `Open` **дважды** и проверяет, что пользователь
на месте, хеш пароля цел, `role='admin'`, `Disabled=false`, `CountAdmins()==1`,
и что в мигрированную таблицу вставляются новые пользователи с ролью. Тест
проверен на различимость: если убрать вызов `migrateUsers`, он падает на
`no such column: role`.

### Атомарность защиты последнего админа

`guardLastAdmin` (кого теряем? он вообще админ и незаблокирован? сколько таких
осталось?) и сама запись выполняются в одной транзакции, которую `writeTx`
открывает как `sql.LevelSerializable`. Драйвер `ncruces/go-sqlite3` документирует,
что serializable-транзакция — это всегда `BEGIN IMMEDIATE`: **блокировка на
запись берётся до первого чтения**. Значит, два параллельных понижения
сериализуются, второе видит результат первого и получает `ErrLastAdmin`, а не
читает «админов двое» одновременно с первым.

Deferred-транзакция здесь не годится не теоретически, а на практике: с ней тест
падает уже на первом раунде с `database is locked` (SQLite не даёт поднять
стухший read-snapshot до записи). Это и проверяет `TestLastAdminConcurrent` — 200
раундов «вернуть обоих в админы → одновременно понизить обоих», каждый раунд
требует ровно одного `ErrLastAdmin` и `CountAdmins()==1` на выходе. Тест проверен
на различимость: подмена `LevelSerializable` на `LevelDefault` роняет его.

Заблокированный админ не считается: `CountAdmins` фильтрует `disabled = 0`, иначе
защита пропускала бы блокировку последнего живого админа при наличии
заблокированного.

### Гашение сессий

`SetUserDisabled(true)` и `SetUserPassword` удаляют строки сессий пользователя в
той же транзакции, что и сам `UPDATE`. `DeleteUser` полагается на
`ON DELETE CASCADE` у `sessions.user_id` (`foreign_keys(1)` включён в DSN) — что
каскад действительно срабатывает, проверяется тестом прямым `COUNT(*)` по
`sessions`, а не только через `GetSession`.

Дополнительно `GetSession` джойнит `users` и не отдаёт сессию заблокированного.
Это дублирование осознанное: оно закрывает окно между выдачей сессии и
блокировкой и делает отказ свойством запроса, а не порядка вызовов.

### Отказ 403 и как его переопределить

По умолчанию `Require` отвечает 403 с JSON в общем формате ошибок проекта:
`{"error":"forbidden","message":"insufficient permissions"}` (тем же `jsonError`,
что и 401 у `RequireBasic`).

Переопределение — поле `Auth.Forbidden http.HandlerFunc`. `Auth` не имеет
состояния (только указатель на store), поэтому UI не переопределяет ответ для
API, а заводит собственный экземпляр:

```go
uiAuth := &auth.Auth{Store: a.Store, Forbidden: renderForbiddenPage}
mux.Handle("/apps/", uiAuth.RequireSession(uiAuth.Require(auth.PermUI, h)))
```

### Прочее

- `Require` без `RequireBasic`/`RequireSession` впереди (пользователя в контексте
  нет) отвечает 403, а не пропускает: ошибка сборки маршрутов не должна
  превращаться в дыру.
- Роль **не валидируется в store**: `auth.ParseRole` — единственный вход, а store
  не может импортировать auth (auth уже импортирует store). Неизвестное значение
  роли в БД безопасно: `Role.Can` для него ложь по всем правам, `CountAdmins` его
  не считает — fail closed. Строковая константа `roleAdmin` в store одна, на ней
  держится защита последнего админа.
- Заблокированный неотличим от неверного пароля: проверка `Disabled` стоит
  **после** `CheckPassword`, тайминг-выравнивание для несуществующего
  пользователя (`dummyHash`) не тронуто.
- Новых зависимостей нет.

## Что осталось за рамками / для следующих задач

- **Смена сигнатуры `CreateUser` затронула чужие файлы.** Требование «`go test
  ./internal/...` зелёный» этого не оставляет выбора: `internal/api/api_test.go`,
  `internal/web/web_test.go`, `internal/integration/helpers_test.go` и
  `cmd/apprepo/main.go` иначе не компилируются (`TestUserAddCLI` в
  `internal/integration` собирает `cmd/apprepo`). Правка везде механическая, по
  одной строке — новый аргумент роли `admin`. Ничего кроме этого аргумента в
  чужих файлах не тронуто.
- **T21 (CLI)**: `apprepo user add` пока всегда создаёт админа. Флаг выбора роли,
  подкоманды списка/смены роли/сброса пароля/блокировки/удаления — за T21;
  `store` для них готов. Учесть `ErrLastAdmin` в текстах ошибок.
- **T19 (API)**: `Require` вешать **после** `RequireBasic`; `ErrLastAdmin` →
  409/422 по вкусу контракта API (в `store` он отличим через `errors.Is`);
  «не найден» из `SetUser*` — обычная ошибка с текстом `user not found`,
  для 404 удобнее сначала звать `GetUserByID`.
- **T20 (UI)**: `deployer` в UI не пускать — `Require(PermUI, …)` на всём
  веб-разделе, включая `/login`-редиректы; для человекочитаемого 403 задать
  `Auth.Forbidden` на отдельном экземпляре `Auth` (см. выше).
- Документация (`README`, `docs/api.md`, `CLAUDE.md`) не трогалась — по условию
  задачи её обновляют другие задачи волны.

## На что смотреть ревьюеру

1. `migrateUsers` — единственное место, которое трогает БД пользователя на
   сервере. Тест на старой схеме есть, но обновление боевой БД стоит один раз
   сделать с копией файла рядом.
2. `writeTx` c `sql.LevelSerializable` — вся защита последнего админа держится на
   том, что этот драйвер начинает такую транзакцию как `BEGIN IMMEDIATE`. При
   смене драйвера SQLite это нужно перепроверить (тест поймает).
3. `User.CreatedAt` сменил тип с `time.Time` на `string` — по контракту T18.
   Потребителей у поля не было, но это несовместимое изменение типа.
