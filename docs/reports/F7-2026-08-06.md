# F7 — устранение блокирующей находки волны 5

- **Ветка:** `fix/F7-remove-guard` (от `wave/app-artifactory-w5`, remote нет — не пушилось)
- **Дата:** 2026-08-06
- **Закрывает:** R5-sec **S1** (блокирующая), **S4**, **S3**;
  R5-test находка №1 (та же, что S1)
- **Отложено:** R5-sec S2 (гонка + компенсация частичного сбоя), известная
  шероховатость «переименование во время стриминга загрузки»

## Что сделано и зачем

### S1 (блокирующая) — удаление выходило за пределы каталога приложения

`files.RemoveApp` делал `os.RemoveAll({Root}/{app})`, проверив только имя.
`Storage.Root` — это `cfg.DataDir`, где по умолчанию лежит и файл БД
(`apprepo.db`, `-wal`, `-shm`), и `.tmp`. Имя `apprepo.db` проходит
`naming.ValidateAppName`, поэтому любой залогиненный пользователь двумя
обычными запросами (`POST /api/apps {"name":"apprepo.db"}` → `DELETE
/api/apps/apprepo.db`) получал 204 и уничтожение базы вместе с пользователями и
сессиями; авария всплывала только при рестарте. То же из UI. `RemoveVersion`
дополнительно резолвил симлинк, подложенный на месте `{Root}/{app}`, и удалял
цель снаружи data-dir.

**Правка.** В `internal/files` перед `os.RemoveAll` появился общий рубеж
`isDir`: `os.Lstat` подтверждает, что цель — настоящий каталог. Решает **тип**
цели, а не её имя, поэтому рубеж закрывает и любого будущего соседа в data-dir.

- цель отсутствует → `(false, nil)`, удаление остаётся идемпотентным (приложение
  без версий каталога не имеет);
- цель есть, но не каталог (обычный файл, симлинк — `Lstat` не считает симлинк
  каталогом даже при каталоге-цели) → типизированная `files.ErrNotDirectory`,
  на диске ничего не трогается;
- `RemoveVersion` проверяет **оба** компонента — `{Root}/{app}` и
  `{Root}/{app}/{version}`: `os.RemoveAll` резолвит родительские компоненты
  пути, и без первой проверки симлинк на месте каталога приложения уводил бы
  удаление наружу `Root`.

**Код ответа: 409** (`already_exists`), а не 400 и не 500. Обоснование: запрос
синтаксически корректен и имя валидно — мешает состояние на сервере, где путь
занят чужим объектом. Это ровно та же ситуация, что у `RenameApp` → 
`ErrFileExists` → 409 `already_exists` (`TestRenameOntoAnExistingDirectoryIs409`
эту асимметрию и фиксировал как дефект). Переиспользован существующий код
ошибки `already_exists`: новых кодов в `docs/api.md` не появляется, и
документация остаётся консистентной (её правит отдельная задача). 400 не взят
потому, что клиент ничего не может исправить в запросе; 500 — потому что это не
внутренний сбой, а осознанный отказ. Инвариант о генеричных ответах соблюдён:
путь ФС уходит только в серверный лог, клиенту — фиксированный текст
(проверено тестом `TestDeleteAppNamedLikeANeighbourFile`, который ассертит
отсутствие `e.root` в теле ответа).

**Порядок «БД → ФС» сохранён** (он зафиксирован планом), поэтому к моменту
отказа рубежа строка приложения уже удалена. Это осознанный выбор из двух,
названных ревьюером: мусорная строка `apprepo.db` исчезает (чего пользователь и
хотел), чужой файл цел, а 409 честно сообщает, что каталог на диске не убирали.
Альтернатива «проверять до `store.DeleteApp`» оставила бы неудаляемую навсегда
строку — хуже.

**Сознательно отклонённая альтернатива (структурный вариант из отчёта):**
перенос `Storage.Root` в `{data-dir}/apps` не делался. У пользователя боевое
развёртывание с данными: такой переезд осиротит уже залитые бинарники и требует
миграции. Рубеж по типу цели закрывает все три аспекта S1 (а, б, в) без
изменения раскладки на диске.

### S4 — инвариант «в БД только валидные имена» сделан настоящим

Этот инвариант стал несущим: на него опирается `os.RemoveAll`. При этом
`store.CreateApp` имя не проверял (в отличие от `UpdateApp`), а `api.mustApp`
брал `{name}` из URL и шёл прямо в БД, не вызывая `naming` вовсе.

- `store.CreateApp` теперь валидирует имя симметрично `UpdateApp`;
- `api.mustApp` отвечает 404 на невалидное имя до обращения к БД — как это уже
  делал `web.loadApp`.

Пути создания приложения проверены: API (`api.createApp`, `api.go`) и UI
(`web.createApp`, `web.go`) валидировали имя и раньше, третьего входа нет
(`grep CreateApp` даёт только эти два вызова плюс тесты). Поведение для валидных
имён не изменилось.

### S3 — журнал деструктивных операций

Удаление приложения, удаление версии и переименование теперь пишут по одной
строке в лог: кто (`auth.CurrentUser`), что и с каким исходом — и в API, и в UI.
Для API в `server` добавлено поле `auth *auth.Auth` (только ради `CurrentUser`).
Секретов в строках нет — только имя пользователя, имя приложения и версия.
Пример реального вывода (из прогона `TestStorageInvariantAfterFullWave5Scenario`):

```
api: user "alice" renamed app "one" to "one-renamed"
web: user "alice" renamed app "one-renamed" to "one"
api: user "alice" deleted version two/1.2.0
web: user "alice" deleted version one/1.0.0
api: user "alice" deleted app "two"
web: user "alice" deleted app "test.db": row removed, disk cleanup failed
```

## Отложено (не входило в F7)

- **S2** — гонка «удаление `a` ↔ переименование `b`→`a`» и отсутствие
  компенсации при частичном сбое `RemoveAll`. Требует сериализации операций над
  приложением (замок по имени в `internal/app`), это отдельная задача.
  Замечу, что новый рубеж не ухудшает ситуацию: он только сужает круг того, что
  вообще может быть удалено.
- **Известная шероховатость** «переименование во время стриминга загрузки»
  (`TestRenameWhileUploadIsStreamingObserved` протоколирует её и ничего не
  требует) — без изменений.
- **Документация** (`docs/api.md` про 409 на удалении, `CLAUDE.md` про рубеж) —
  по постановке за отдельной задачей. Кодов ошибок не добавлялось, поэтому
  текущий `docs/api.md` остаётся корректным, но неполным: 409 `already_exists`
  теперь возможен и на `DELETE /api/apps/{name}`.

## Точки внимания для ревьюера

- `isDir` возвращает `(bool, error)`, и вызывающие пишут
  `if ok, err := isDir(p); !ok { return err }` — компактно, но читается не с
  первого взгляда; поведение «нет цели → `(false, nil)` → `return nil`»
  описано комментарием и покрыто `TestRemoveMissingIsNotAnError`.
- Переиспользование кода ошибки `already_exists` для 409 на удалении — выбор в
  пользу неизменности `docs/api.md`; если ревьюер предпочтёт отдельный код
  (`not_a_directory`), это одна строка плюс правка документации.
- 409 приходит уже после удаления строки в БД (см. обоснование в S1) — это
  осознанно, а не недосмотр.
