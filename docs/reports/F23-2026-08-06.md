# F23 — тест синхронности код-блока юнита в README и `deploy/apprepo.service`

- **Дата:** 2026-08-09
- **Ветка:** `fix/F23-unit-readme-sync` (база — `wave/app-artifactory-w8`, `76048c4`). Remote нет, push не делался.
- **Что закрывает:** замечание 1 из `docs/plans/reviews/app-artifactory-R8-qa-round2.md`
  («синхронность README и `deploy/apprepo.service` ничем не проверяется»).
- **Статус:** готово. Весь набор зелёный, `smoke.sh` — `SMOKE OK`. Продакшн-код не тронут.

## Что было не так

В `CLAUDE.md` («Документация») объявлен инвариант: код-блок юнита в разделе README
«Деплой (systemd)» — копия `deploy/apprepo.service` и обязан меняться вместе с ним.
Инвариант держался на аккуратности и при первой же одновременной правке разъехался
(поймано разовым скриптом приёмщика в R8-qa круг 2, тогда же и починено). Расхождение
не ломает сборку и не ловится тестами, а разворачивают сервис по README: сегодня
разъезжается комментарий, завтра `ReadWritePaths=` — и это старт с `status=226/NAMESPACE`.

## Что сделано

`internal/docsync/docsync_test.go` — новый **тестовый пакет без продакшн-кода**:
`TestReadmeUnitMatchesDeployUnit` вырезает из `README.md` код-блок, размеченный как
` ```ini `, и сравнивает построчно с `deploy/apprepo.service`. При расхождении печатает
номер строки и обе версии в кавычках (`strconv.Quote` — иначе разница в хвостовом
пробеле нечитаема), плюс напоминание об инварианте.

Три вещи в реализации сделаны намеренно:

- **Пути от исходника теста, а не от рабочего каталога.** `runtime.Caller(0)` →
  `filepath.Dir` → `../..`. Не через `git rev-parse` (как `repoRoot` в
  `internal/integration`): тот пропускает прогон без `.git`, а для инварианта
  документации пропуск — это молчаливая дыра, ради которой тест и писался.
- **Ровно один блок ` ```ini ` в README.** Если их станет два, тест падает с
  внятным «ожидается ровно один», а не сверяет молча первый попавшийся.
- **Разная длина блоков** даёт `(строки нет)` против реальной строки — видно, что
  строку добавили или потеряли, а не «поменяли».

Правки README и юнита не понадобились: после R8-qa круга 2 блоки совпадают байт в байт.

## Где лежит тест и почему

Существующего места для проверок согласованности файлов репозитория не было:
`internal/integration` — это e2e сервиса (`app.New` → `httptest`, сборка бинарников,
wazero), и файловая сверка документации туда не относится ни по смыслу, ни по цене
(пакет идёт ~140 s). Пакета уровня «репозиторий» не существовало вовсе, класть в
чей-то предметный пакет тест про README — прятать его.

Поэтому заведён `internal/docsync/` — каталог только с тестами (`go build ./...` на нём
проходит, продакшн-кода нет). Это осмысленное место роста: следующие проверки такого
же рода («док против файла, который она цитирует») лягут туда же, а не расползутся.
Пакет добавлен в карту в `CLAUDE.md` — иначе он сразу разошёлся бы с картой, которую
приёмка сверяет глазами.

## Другие пары «файл и его копия в документации»

Искал по репозиторию; чинить в этой задаче ничего из найденного не стал — ни одна пара
не является такой же дешёвой дословной сверкой.

1. **Блок вызова CLI в README (`README.md:229–235`) против `usage()`
   (`cmd/apprepo/main.go:61–67`).** Сейчас совпадают, но не байт в байт: в `usage()`
   строки идут с отступом в 7 пробелов и им предшествует `usage: apprepo [serve] [flags]`,
   которой в README намеренно нет. Инвариант в `CLAUDE.md` не объявлен. Сверка возможна,
   но требует нормализации (срезать отступ, выкинуть первую строку) — то есть проверки
   не «эти байты равны этим», а с правилом внутри, которое само может разъехаться с
   реальностью. Кандидат в отдельную задачу, если решим объявить инвариант.
2. **Схема БД в плане (`docs/plans/2026-08-06-app-artifactory.md`, «Контракты») против
   `internal/store/schema.sql`.** Уже расходятся, и правомерно: план — зафиксированный
   контракт волны 1, а в `schema.sql` с тех пор добавлены `role`/`disabled` (T18) и
   `platform` (T24). Это не копия, а исторический документ; сверять нечего.
3. **`deploy/apprepo.env.example` против таблицы конфигурации в README.** Не копия
   (таблица «флаг → env → дефолт» против файла с комментариями). Сверил вручную состав
   переменных: `APPREPO_ADDR/DATA_DIR/DB/BASE_URL/MAX_UPLOAD` — совпадают между
   env-примером, README и `internal/config`; `APPREPO_PASSWORD` есть только в README,
   что верно (переменная CLI, в env-файле сервиса ей не место).
4. **Таблица «маршрут → право» и коды ошибок в `docs/api.md` против `internal/api`.**
   Сверяются приёмкой вручную (R8-qa: 19 из 19). Автоматическая проверка возможна, но
   это уже не сверка копий, а интроспекция таблицы маршрутов и `writeErr` — отдельная
   задача заметного объёма, не «десяток строк».

## Риски и на что смотреть ревьюеру

- Тест привязан к разметке ` ```ini `: если кто-то сменит язык блока на `systemd` или
  `toml`, тест упадёт с «0 код-блоков ```ini» — сообщение объясняет, что произошло,
  но это именно падение, а не пропуск. Считаю это правильным поведением: молчаливая
  потеря проверки хуже.
- `internal/docsync` — каталог без продакшн-кода. `go build ./...`, `go vet ./...` и
  `go test ./...` его переваривают (проверено); если где-то в CI появится проверка
  вида «в каждом пакете есть не-тестовые файлы», она на нём споткнётся.
