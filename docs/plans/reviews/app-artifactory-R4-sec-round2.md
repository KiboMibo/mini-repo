## Вердикты по исправлениям

### S1 (права на файл БД) — закрыто

- **Что сделано:** `internal/store/store.go:86-93` — chmod 0600 на `apprepo.db`, `-wal`, `-shm` в `Open` (отсутствующий файл пропускается); `internal/app/app.go:27` — каталоги данных 0700; `deploy/apprepo.service` — `UMask=0077`.
- **Проверка:** интеграционный тест `TestDataDirAndDBPermissions` (`internal/integration/misc_test.go:229`) — зелёный. Отдельно проверен худший сценарий вручную (umask 022, чистое закрытие БД удаляет `-wal`, повторное открытие): `-wal` создаётся заново уже во время `Open` (применение PRAGMA/схемы) и попадает под chmod — после повторного открытия и записи все три файла `-rw-------`. То есть фикс держится и вне systemd, без опоры на UMask.
- **Остаток:** каталог, созданный `user add` до первого `serve`, — 0755 (см. R1 ниже); файлы в нём всё равно 0600, токены и хеши закрыты.

### S2 (гонка загрузок одной версии) — закрыто

- **Что сделано:** `internal/files/files.go:98-107` — публикация через `os.Link` (атомарный отказ EEXIST, ничего не перезаписывает) + удаление temp; ранний `Stat` оставлен только как быстрый отказ, авторитетен Link; новая ошибка `ErrFileExists` маппится на 409 `already_exists` в API (`internal/api/api.go:392-395`) и на конфликт-страницу в UI (`internal/web/web.go:385-388`), без путей ФС в ответе.
- **Проверка:** оба сценария гонки покрыты зелёными интеграционными тестами: `TestConcurrentPutSameFileGets409` (`misc_test.go:167`) — одинаковое имя файла: проигравший получает 409 на `Link`, файл победителя цел байт-в-байт и скачивается, ответ не содержит путь ФС; `TestConcurrentPutSameVersionRollsBack` (`misc_test.go:18`) — разные имена файлов: проигравший доходит до UNIQUE в БД, откатывает только *свой* файл, версия победителя скачивается. Плюс юнит `TestSaveRaceLoserGetsErrFileExists` в `internal/files`.
- **Логика подтверждена чтением:** проигравший при ошибке `Save` возвращается до `CreateVersion` и не вызывает `fs.Remove` — файл победителя недостижим для его отката. Обход `Link` на ФС без hardlink-семантики не рассматривался (вне скоупа: `.tmp` и данные на одной ФС по архитектуре temp+rename).

### S3 (память на multipart-полях) — закрыто

- **Что сделано:** `internal/web/web.go:34-37,307-315` — не более 8 не-file частей (`maxUploadFields`), 4 КиБ каждая; превышение → 400 «too many form fields» до сохранения чего-либо.
- **Проверка:** лимит срабатывает до добавления в карту; повторные части с одним именем карту не растят (перезапись по ключу), так что обход через дубли имён невозможен — тело просто дочитывается в пределах `MaxUploadBytes` без накопления в памяти; заголовки отдельной части ограничены самим `mime/multipart` (стандартные лимиты пакета). Память хендлера ограничена константой, не размером тела. Тест на лимит есть в диффе `internal/web/web_test.go`; `go test ./internal/web/` зелёный.

## Новые находки

### R1. `user add` создаёт каталог БД с правами 0755 в обход решения S1

- **Серьёзность:** замечание
- **Где:** `cmd/apprepo/main.go:110` — `os.MkdirAll(filepath.Dir(cfg.DBPath), 0o755)`
- **Кто может:** локальный пользователь хоста
- **Путь:** README (раздел «Сборка и запуск») предписывает `user add` до `serve`; на чистом хосте именно он создаёт data-dir — с 0755. Последующий `app.New` (0700) существующий каталог не пере-chmod-ит (`MkdirAll` — no-op). Файлы БД и артефактов при этом 0600 (S1-фикс в `Open` и `CreateTemp` работают независимо от каталога), поэтому токены/хеши/содержимое бинарников не читаются — но листинг имён приложений, версий и файлов остаётся доступен любому локальному пользователю, и критерий приёмки F-S1 («каталоги ≤ 750») на этом пути не выполняется.
- **Чем грозит:** раскрытие метаданных (какие приложения и версии лежат в репозитории) локальным пользователям; содержимое защищено.
- **Как чинить:** однострочно — `0o700` в `cmd/apprepo/main.go:110` (симметрично `app.New`).
- **Как проверить:** на чистом каталоге `user add` → `stat -c %a` каталога данных = 700; расширить `TestDataDirAndDBPermissions` или добавить проверку в `scripts/smoke.sh` (там `user add` выполняется первым — готовая точка проверки).

## Проверенное и чистое (в рамках диффа F4)

- Ранний `Stat` в `Save` больше не участвует в решении о перезаписи — только быстрый отказ; авторитетна эксклюзивная публикация `Link`.
- Откат `fs.Remove` вызывается только после успешного `Save` того же запроса — сценария «проигравший удаляет чужой файл» больше нет ни в API, ни в UI.
- Новые сообщения об ошибках (409, «upload failed», «too many form fields», `internal error`) не содержат путей ФС и текстов SQLite; тест `TestConcurrentPutSameFileGets409` явно проверяет отсутствие data-dir в теле ответа.
- CSRF-проверка загрузки по-прежнему выполняется до сохранения файла; порядок обработки частей не изменился.
- `go build`, `go vet`, `go test ./...` на `9facb60` — зелёные; smoke-скрипт не менялся.
