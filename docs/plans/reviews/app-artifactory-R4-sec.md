- **Дата:** 2026-08-06
- **Область:** полный код проекта по плану `docs/plans/2026-08-06-app-artifactory.md` — `cmd/`, `internal/` (naming, config, store, files, auth, web, api, app), `deploy/`, `scripts/smoke.sh`
- **Коммит:** `2785500` (ветка `review/R4-sec` = `wave/app-artifactory-w3` с влитым T7)
- **Инструменты:** ручное чтение кода от точек входа; `go build ./... && go vet ./... && go test ./...` — зелёные; эмпирические проверки в песочнице (`mime.FormatMediaType` на враждебных именах, права файла БД через `go test -overlay` без правки репозитория); ручной grep секретов по рабочему дереву

Зависимости оценены вручную, см. «Не проверено».

## Резюме

Блокирующих находок нет — код в целом написан аккуратно: единый рубеж валидации имён не обойдён нигде, все SQL-запросы параметризованы, auth-покрытие маршрутов полное, тайминг-выравнивание и защита от open redirect реализованы. Три важные находки: файл SQLite с bcrypt-хешами и живыми сессионными токенами создаётся мир-читаемым (0644) в мир-проходимом каталоге; гонка двух конкурентных загрузок одной версии может молча подменить и затем удалить файл артефакта, оставив строку в БД; multipart-загрузка позволяет залогиненному пользователю раздуть память сервера до лимита тела (2 GiB по умолчанию). Все три чинятся локально и не требуют останавливать релиз во внутреннем контуре, но F-S1 стоит закрыть до продакшен-деплоя на многопользовательский хост.

**Вердикт:** можно выкатывать; S1 закрыть до деплоя на хост с недоверенными локальными пользователями.

## Находки

### S1. Файл БД с сессионными токенами и хешами паролей читаем любым локальным пользователем

- **Серьёзность:** важная
- **Где:** `internal/store/store.go:71-86` (Open, права наследуются от драйвера/umask), `internal/app/app.go:25` (`MkdirAll(dir, 0o755)`), `deploy/apprepo.service` (нет `UMask=`)
- **Класс:** небезопасные права на файлы (CWE-732)
- **Кто может:** любой локальный пользователь хоста (не root)
- **Путь:** `store.Open` создаёт `{data-dir}/apprepo.db`; проверено эмпирически: при umask 022 файл получает `-rw-r--r--` (0644). Каталог данных создаётся 0755 (`app.go:25`), дефолт `/opt/apps`. Итог: `sessions.token` (живые токены на 7 суток) и `users.password_hash` читаются кем угодно на хосте → готовая кука `apprepo_session` и offline-перебор bcrypt-хешей.
- **Чем грозит:** локальный пользователь входит в UI/API под любым залогиненным пользователем без пароля (токен из БД — это и есть кука); плюс кража хешей. systemd-hardening юнита (`ProtectSystem`, `ProtectHome`) от чтения `/opt/apps` посторонними процессами не защищает.
- **Как чинить:** добавить `UMask=0077` в `[Service]` `deploy/apprepo.service`; в `internal/app/app.go` создавать `cfg.DataDir` и каталог БД с 0750; в README — упомянуть права при ручном запуске. (Файлы артефактов уже 0600 — их создаёт `os.CreateTemp`.)
- **Как проверить:** после `serve` на чистом data-dir `stat -c %a` для `apprepo.db`, `apprepo.db-wal`, `apprepo.db-shm` ≤ 640, для каталога ≤ 750; добавить проверку прав в `scripts/smoke.sh` или интеграционный тест.

### S2. Гонка двух загрузок одной версии: подмена и удаление файла артефакта при живой строке в БД

- **Серьёзность:** важная
- **Класс:** TOCTOU / гонка (CWE-367)
- **Где:** `internal/files/files.go:58` (проверка `os.Stat(dst)`), `files.go:90` (`os.Rename` молча перезаписывает существующий dst), откаты: `internal/api/api.go:393`, `internal/web/web.go:358`
- **Кто может:** любой залогиненный пользователь (в т.ч. случайно — двойной пуш из CI)
- **Путь:** два конкурентных `PUT /api/apps/{name}/versions/{v}` (или UI-загрузки) одной версии → оба проходят раннюю проверку дубля (`api.go:370`) и `Stat` в `Save` до того, как первый сделал `Rename` → оба `Rename` в один dst (второй перезаписывает файл первого) → `CreateVersion` первого успешен, второго — `ErrExists` → откат второго вызывает `fs.Remove` и **удаляет файл, на который уже ссылается строка первого**. Итог: версия в БД есть, файла нет (скачивание — 500), либо промежуточно файл с содержимым проигравшего при sha256 победителя.
- **Чем грозит:** тихая потеря/подмена артефакта — ровно того, что репозиторий бинарников обязан гарантировать; обнаружится только при скачивании.
- **Как чинить:** заменить пару `Stat`+`Rename` на атомарно-эксклюзивную публикацию: `os.Link(tmp.Name(), dst)` (на POSIX падает с `EEXIST`, ничего не перезаписывая) + `os.Remove(tmp.Name())`; ошибку `EEXIST` маппить на «file already exists». Тогда проигравший никогда не касается файла победителя, и его откат `Remove` не нужен (файл не был создан им) — в хендлерах вызывать `fs.Remove` только если `Save` завершился успехом у этого же запроса (текущий код это уже соблюдает — после фикса `Save` у проигравшего вернёт ошибку до создания dst).
- **Как проверить:** добавить тест в `internal/files`, имитирующий гонку (создать dst между `Save`-валидацией и публикацией — с `os.Link` повторный `Save` обязан вернуть ошибку, а существующий файл остаться байт-в-байт нетронутым); плюс интеграционный тест двух параллельных PUT одной версии: ровно один 201, один 409, файл скачивается и совпадает с содержимым победителя.

### S3. Multipart-загрузка: неограниченное число полей формы копится в памяти

- **Серьёзность:** важная
- **Класс:** неконтролируемое потребление памяти (CWE-770)
- **Где:** `internal/web/web.go:296-312` — цикл `NextPart`; каждая не-file часть читается до 4 КиБ (`web.go:306`) и складывается в `fields` без ограничения количества частей
- **Кто может:** любой залогиненный пользователь
- **Путь:** `POST /apps/{name}/versions` с телом из миллионов мелких не-file частей → тело ограничено только `MaxUploadBytes` (2 GiB по умолчанию, `web.go:287`) → карта `fields` и заголовки частей накапливаются в памяти до ~размера тела → OOM, сервис падает (systemd перезапустит, но повторяемо).
- **Чем грозит:** отказ в обслуживании силами одного залогиненного пользователя; лимит 2 GiB задуман для файла на диске, а не для метаданных в памяти.
- **Как чинить:** в цикле принимать только известные имена полей (`csrf_token`, `version`, `sha256`) и ограничить число не-file частей (например, 8), при превышении — 400; неизвестные части дренировать без сохранения (`io.Copy(io.Discard, ...)` с лимитом) или сразу отклонять.
- **Как проверить:** добавить httptest в `internal/web`: запрос с 10⁴ мелких частей получает 400, потребление памяти хендлера не растёт с числом частей (достаточно проверки кода ответа + лимита в реализации).

### S4. Внутренние ошибки уходят клиенту дословно (err.Error() в ответах)

- **Серьёзность:** замечание
- **Где:** `internal/api/api.go:166,181,188,215,232,248,266,275,288` и другие `writeErr(..., "internal", err.Error())`; `internal/web/web.go:380` (`"upload failed: "+err.Error()`)
- **Кто может:** любой залогиненный пользователь (все эти маршруты за auth)
- **Чем грозит:** раскрытие внутренних путей ФС (`/opt/apps/.tmp/upload-…: no space left`, `file /opt/apps/app/1.0.0/x already exists` из `files.go:59`) и текстов ошибок SQLite. Секретов в этих ошибках нет; путь от анонима отсутствует — поэтому не выше замечания.
- **Как чинить:** для 500-х логировать `err` на сервере, клиенту отдавать фиксированное `"internal error"` (как уже сделано в `web.serverError` и в download-хендлере); 4xx-ветки с валидационными сообщениями можно оставить.
- **Как проверить:** grep по `internal/api`, `internal/web`: ни один `writeErr`/`renderApp` со статусом 500 не передаёт `err.Error()` в тело.

### S5. HTTP-упрочнение: куки без Secure, нет защитных заголовков

- **Серьёзность:** замечание (в контексте зафиксированного в плане решения «TLS — на reverse-proxy, README»)
- **Где:** `internal/auth/auth.go:155-164` (кука `apprepo_session`), `internal/web/web.go:75-78` (кука `apprepo_csrf`), `internal/app/app.go` (нет общего middleware заголовков)
- **Аспекты:**
  1. Обе куки без `Secure`: за TLS-прокси браузер всё равно отправит их по http, если сервис случайно окажется доступен в обход прокси. План принимает риск «Basic Auth без TLS» на уровне README (`README.md:36` требование прокси есть), но флаг Secure — дешёвая строка.
  2. Нет `X-Content-Type-Options: nosniff`, `X-Frame-Options: DENY`/CSP на UI-страницах. Заметьте: `Content-Disposition: attachment` на скачивании уже блокирует inline-рендер загруженных файлов — stored-XSS через артефакт не воспроизводится.
- **Как чинить:** добавить `Secure: true` (или конфиг-флаг для http-only дев-окружения) в `sessionCookie` и `ensureCSRF`; middleware в `internal/app` с `nosniff` и `X-Frame-Options: DENY` для UI.
- **Как проверить:** заголовки `Set-Cookie` содержат `Secure`; ответы UI содержат оба защитных заголовка.

### S6. CSRF-токен не привязан к сессии (границы double-submit)

- **Серьёзность:** замечание
- **Где:** `internal/web/web.go:64-98`
- **Что не так:** double-submit сверяет токен только с кукой (`csrfOK`, `web.go:83-87`), кука не привязана к сессии и не ротируется при логине. Атакующему достаточно уметь ставить жертве куку `apprepo_csrf` (контроль поддомена или активный MITM при http) — тогда double-submit обходится. Прямого пути не нашёл: поддоменов у сервиса нет, http закрыт S5/README, а `SameSite=Lax` на сессионной куке сам по себе блокирует кросс-сайтовые POST — защита фактически двухслойная.
- **Как чинить (опционально):** выдавать CSRF-токен, производный от сессии (HMAC от токена сессии), или ротировать `apprepo_csrf` в `LoginUser`.
- **Как проверить:** после логина значение `apprepo_csrf` меняется; POST со старым токеном → 403.

### S7. Нет ограничения частоты на аутентификации

- **Серьёзность:** замечание
- **Где:** `POST /login` (`internal/web/web.go:161`), `RequireBasic` (`internal/auth/auth.go:66`)
- **Что не так:** перебор паролей ничем не ограничен, кроме стоимости bcrypt (~50–100 мс на попытку — это же делает каждый анонимный запрос с кредами амплификатором CPU: аноним без пароля заставляет сервер жечь bcrypt на каждый запрос к `/api/…`). Учётки заводятся только CLI-администратором, пароли не самослужебные — риск умеренный.
- **Как чинить (опционально):** простейший in-memory rate limit по IP/username на неуспешные попытки (например, экспоненциальная задержка после 5 неудач); зафиксировать в README, что fail2ban/прокси-лимиты приветствуются.
- **Как проверить:** 20 подряд неверных паролей с одного IP → задержка или 429.

### S8. ValidateFilename пропускает управляющие символы

- **Серьёзность:** замечание
- **Где:** `internal/naming/naming.go:41-54`
- **Что не так:** имя файла с CR/LF/прочими управляющими символами проходит валидацию. Эксплуатации не нашёл: `mime.FormatMediaType` percent-кодирует CR/LF в `filename*` (проверено эмпирически: `"a\r\nSet-Cookie: x=1"` → `attachment; filename*=utf-8''a%0D%0ASet-Cookie%3A%20x%3D1` — инъекция заголовка невозможна), в HTML имя экранирует `html/template`, в путь ФС сепараторы не проходят. Конструкция опасна при будущем изменении: любой новый вывод имени файла (лог-строки с выравниванием, CSV-экспорт, nginx-заголовки) получит сюрприз.
- **Как чинить:** в `ValidateFilename` отклонять байты < 0x20 и 0x7F.
- **Как проверить:** юнит-тест `ValidateFilename("a\r\nb")` → ошибка.

## Проверенное и чистое

- **Path traversal.** `internal/naming` как единственный рубеж не обойдён нигде: UI-загрузка срезает путь и валидирует basename (`web.go:334-341`); `PUT ?filename=` и дефолтное `{name}-{version}` проходят `ValidateFilename` (`api.go:361-368`); скачивание строит путь только из значений БД, валидированных при вставке; `files.Save`/`Remove` повторно валидируют все три имени и требуют канонический semver (`files.go:35-47`), так что даже прямой вызов в обход хендлеров не выйдет из `{Root}`. Кейс `%2F` в path-параметрах ServeMux гасится валидацией/поиском в БД (несуществующее имя → 404).
- **Auth-покрытие маршрутов.** Открыты только `GET /healthz`, `GET /login`, `POST /login` — по плану. Все `/api/` и `GET /download/…` за `RequireBasic` (включая catch-all внутри `/api/`, `api.go:45-48`), весь остальной UI за `RequireSession` (`web.go:52-61`). Забытых маршрутов нет; `HEAD` на download покрыт паттерном GET.
- **SQL-инъекции.** Все запросы в `internal/store` (включая `user_by_id.go`) параметризованы; конкатенируются только константные списки колонок.
- **Тайминг существования пользователя.** При отсутствии пользователя прогоняется bcrypt по фиктивному хешу той же стоимости (`auth.go:48-61`); ветки login и Basic идут через общий `authenticate`, сообщение об ошибке одно для обоих случаев.
- **Сессии.** Токен — 32 байта `crypto/rand` hex (`store.go:138-151`); на каждый логин выпускается новый токен (фиксация невозможна); просроченная сессия удаляется при чтении; logout удаляет строку и гасит куку. Кука: HttpOnly, SameSite=Lax, Path=/, 7 суток — по контракту (кроме Secure, см. S5).
- **Open redirect в `next`.** `safeNext` (`auth.go:115-121`) и `sanitizeNext` (`web.go:144-150`) допускают только относительный путь с одинарным `/`, режут `//`, `/\` и бэкслеши; `javascript:`/абсолютные URL не проходят. Значение рендерится через `html/template` — XSS через `next` нет.
- **CSRF.** Все меняющие состояние UI-маршруты защищены: обычные формы — middleware `csrf` (сравнение `subtle.ConstantTimeCompare`), multipart — проверка до сохранения файла и до рендера ошибок; POST без токена → 403 (покрыто тестами `internal/web/web_test.go`). Плюс SameSite=Lax как второй слой. Границы модели — S6.
- **Content-Disposition.** `mime.FormatMediaType` (`api.go:456-457`) корректно квотит `"`/`;` и percent-кодирует не-ASCII и управляющие символы — инъекция заголовка не воспроизводится (проверено на враждебных именах).
- **XSS в шаблонах.** Везде `html/template`, `template.HTML` не используется; описания, имена, ошибки экранируются автоэкранированием.
- **Лимиты тела.** Multipart и `PUT` — `MaxBytesReader(cfg.MaxUploadBytes)` (`web.go:287`, `api.go:377`) с корректным маппингом на 413; JSON — 1 МиБ (`api.go:22,201,308`); urlencoded-формы (login и пр.) ограничены встроенным 10 МиБ-капом `ParseForm`. Ранняя проверка дубля версии до прогона байтов есть в обоих путях загрузки.
- **Секреты в коде/логах.** В рабочем дереве секретов нет (ручной grep); `s3cret` в `scripts/smoke.sh` и пароли в тестах — фикстуры; пароль для `user add` берётся из env/терминала и не логируется; сессионные токены и хеши в логи не попадают; 500-е в UI и download отвечают фиксированным текстом (в API — см. S4).
- **Хранение паролей.** bcrypt, дефолтная стоимость 10, через `x/crypto/bcrypt` (`auth.go:31-39`).
- **systemd unit.** `NoNewPrivileges`, `ProtectSystem=strict`, `ProtectHome`, `PrivateTmp`, выделенный пользователь, `ReadWritePaths=/opt/apps` — приличный базовый hardening (недостаёт `UMask` — S1); в env-файле секретов нет.
- **Сборка и тесты.** `go build`, `go vet`, `go test ./...` — без ошибок на ревьюируемом коммите.

### F-S4…S8 (замечания, по усмотрению F4)

## Не проверено
