## Находки

### 1. API не нормализует имя учётки, UI нормализует — одно имя заводит две учётки — важная

- **Где:** `internal/api/users.go:111-114` (проверка только на пустую строку) против
  `internal/web/users.go:129` (`strings.TrimSpace`).
- **Чем грозит:** админ создаёт учётку `" ops "` (лишний пробел от копипасты) — через
  UI получает `ops`, через API получает `" ops "`. Обе существуют одновременно, в
  списке выглядят одинаково, а `PATCH /api/users/ops` попадёт только в одну из них.
  Дальше «я же заблокировал этого пользователя, а он всё ещё заходит». Это ровно тот
  класс расхождения «одна операция — два интерфейса», ради которого волну сводила F11.
- **Предлагается:** одна функция нормализации и валидации имени, вызываемая из
  `api.createUser`, `web.createUser` и `cmd/apprepo.userAdd`. Где именно она живёт —
  дело исправляющего; тест не фиксирует ни место, ни текст сообщения, ему достаточно,
  чтобы оба интерфейса вели себя одинаково.
- **Тест:** `TestUsernameHandlingConsistency/api_и_ui_одинаково_нормализуют_имя` (падает)

### 2. Имя учётки нигде не валидируется: `ci:bot` создаётся, но войти ею нельзя — важная

- **Где:** `internal/api/users.go:111-114`, `internal/web/users.go:129`,
  `internal/store/store.go:201` (`CreateUser` принимает любую строку),
  `cmd/apprepo/main.go:275` (`userAdd` — тоже).
- **Чем грозит:** HTTP Basic кодирует `user:password`, поэтому двоеточие в имени
  делает учётку неаутентифицируемой: `Authorization: Basic base64("ci:bot:pw")`
  разбирается как пользователь `ci` с паролем `bot:pw`. Сервер отвечает 201 Created
  и никак не предупреждает. Для роли `deployer` — машинной учётки, у которой нет
  доступа в UI, — это учётка, мёртвая с рождения: единственный способ ею
  воспользоваться закрыт. Проверено также, что без валидации проходят имена длиной
  300 байт, `<script>` (в HTML экранируется корректно) и имена, различающиеся только
  регистром (`Alice` и `alice` — разные учётки, поскольку `UNIQUE` в SQLite
  регистрозависим).
- **Предлагается:** отвергать имя с двоеточием и управляющими символами и ограничить
  длину — там же, где нормализация из находки 1. Тест сформулирован «либо отказ на
  входе (400), либо созданная учётка работоспособна», так что исправление свободно
  выбрать любой из двух вариантов.
- **Тест:** `TestUsernameHandlingConsistency/созданная_учётка_умеет_войти` (падает)

### 3. Ветка «последний админ» при удалении учётки в UI недостижима через HTTP — замечание

- **Где:** `internal/web/users.go:235-237` (и симметрично `internal/api/users.go`:
  `store.ErrLastAdmin` от `DeleteUser`).
- **Чем грозит:** ничем прямо сейчас — проверка самоудаления стоит раньше и
  перехватывает единственный путь, которым можно было бы дойти до `ErrLastAdmin`
  на удалении. Но это значит, что защита «последнего админа от удаления» через HTTP
  проверяется не тем кодом, которым кажется, а через `self_delete`; если когда-нибудь
  снимут запрет самоудаления, поведение изменится молча. Через CLI ветка достижима и
  протестирована (`TestCLIAccountsVisibleOverHTTP/CLI_защищает_последнего_админа`).
- **Предлагается:** ничего не менять; знать при следующей правке этих обработчиков.

### 4. Заблокированный админ не считается активным — намеренно, но легко потерять — замечание

- **Где:** `internal/store/store.go:240-247` (`CountAdmins` фильтрует `disabled = 0`)
  и `guardLastAdmin` (заблокированного админа не защищает).
- **Чем грозит:** ничем: поведение последовательное и правильное — заблокированный
  админ установку не спасёт, поэтому его можно удалить и он не мешает защите
  оставшегося. Отмечаю потому, что это неочевидно и теперь зафиксировано тестом
  (`TestLastAdminProtectedOverUI/защита_держится_после_блокировки_второго_админа`).

## Допущения

Вызов делегированный, спрашивать было некого; решения приняты так:

1. **Границы работы.** Матрицы «роль × маршрут» внутри `internal/api` и
   `internal/web` уже написаны исполнителями T19/T20 и являются эталоном для своего
   пакета — я их не дублировал. Мой табличный тест проверяет другое утверждение:
   что два интерфейса согласованы между собой на собранном приложении. Он
   переживёт переезд любой из внутренних матриц.
2. **`deployer` исключён из сверки API↔UI.** У роли нет `PermUI` вовсе, поэтому её
   отказ в интерфейсе при разрешении в API — не расхождение, а смысл роли (так же
   решила F11). Она проверяется отдельным подтестом: вход проходит, любая страница
   отдаёт 403 с объяснением «пользуйтесь API», чтение и скачивание работают, запись
   и смена своего пароля — только через API.
3. **«Последнего админа нельзя удалить» через HTTP не проверяется напрямую** —
   такого пути нет: удалить может только админ, и единственный сценарий, ведущий к
   `ErrLastAdmin`, — удаление себя, которое отсекается раньше как `self_delete`.
   Проверено то, что достижимо: `self_delete` через API и UI (в том числе при двух
   админах) и отказ CLI на всех трёх операциях над последним админом. См. замечание 3.
4. **Сценарий встречной гонки.** «Два одновременных запроса на разжалование двух
   последних админов» реализован как взаимное разжалование: запрос A от `alice`
   разжалует `bob`, запрос B от `bob` разжалует `alice`. Это единственная форма, где
   оба запроса аутентифицированы админом и обе цели — последние админы; вариант с
   третьим админом-инициатором конфликта не создаёт. Инвариант проверяется по БД
   (`CountAdmins() >= 1`), а не по ответам, плюс отдельно требуется, чтобы оба
   запроса не завершились успехом. 5 раундов, каждый на своём окружении.
5. **Проверка утечек в журнал** использует `log.SetOutput` — пакет `log` глобален,
   поэтому такие тесты не помечены `t.Parallel` (в этом пакете `t.Parallel` не
   используется вовсе). Вывод восстанавливается в `os.Stderr` через `t.Cleanup`.
6. **Покрытие CLI** измерено инструментированным бинарником и слито с основным
   профилем — иначе метрика по волне занижена почти на 15 пунктов из-за того, что
   подкоманды тестируются как подпроцесс. Способ подсчёта описан в разделе
   «Покрытие»; число по `main.go` — нижняя оценка. Инструментирование сделано
   ad-hoc для отчёта и в тесты не закоммичено: постоянная поддержка `GOCOVERDIR` в
   `r6_cli_test.go` — решение о CI, а не моё.
7. **Красные тесты оставлены красными.** Маркером «известный дефект» не помечал:
   параллельные задачи волны (R6-sec, R6-qa) на CI не завязаны, общий прогон никого
   не блокирует, а скрытый пропуск потерялся бы.
8. **`internal/api/users.go` и `internal/web/users.go` были бы удобнее с общей
   функцией нормализации имени** — сейчас проверки разъезжаются просто потому, что
   написаны в двух местах. Это наблюдение о дизайне, а не требование; вынесено в
   находку 1 как предложение.
