## Вердикты по исправлениям

### S1 (важная) — НЕ закрыто

**Что сделано и работает.** `formBody` (`internal/api/api.go:114-124`) разбирает
заголовок через `mime.ParseMediaType` и отбивает `text/plain` и
`multipart/form-data` с 415. Разбор устойчив к обычным попыткам обхода —
**проверено**, все дают 415:

| `Content-Type` | ответ |
|---|---|
| `text/plain` | 415 |
| `text/plain; charset=utf-8` | 415 |
| `TEXT/PLAIN` | 415 |
| `Text/Plain; Charset=UTF-8` | 415 |
| `  text/plain  ` (пробелы) | 415 |
| `multipart/form-data; boundary=x` | 415 |
| `MULTIPART/FORM-DATA; boundary=x` | 415 |

Точка входа действительно одна: `decodeJSON` (`internal/api/users.go:42-52`) —
единственный `json.NewDecoder` в пакете, и `formBody` стоит первой строкой в
нём; три хендлера, декодировавших напрямую, переведены на него. Забыть рубеж на
новом маршруте нельзя. Вектор круга 1 закрыт: `POST /api/users` с `text/plain`
→ 415, учётка не создаётся; то же для `multipart`, `POST /api/apps`,
`PATCH /api/apps/{name}`, `POST /api/apps/{name}/latest`.

**Чего не хватает.** `formBody` возвращает `false` (пропустить), когда
`ParseMediaType` вернул ошибку, — то есть когда заголовка **нет** или он не
разбирается. Комментарий в коде объясняет это как «форма такого не пришлёт», и
для `<form>` это правда. Но угроза в круге 1 формулировалась не через `<form>`,
а через «кросс-сайтовый запрос, который браузер отправит с кэшированными
Basic-кредами и без preflight». Множество `Content-Type`, достижимых без
preflight, — это `{отсутствует, text/plain, application/x-www-form-urlencoded,
multipart/form-data}`. Два из них закрыты, `urlencoded` валидным JSON стать не
может (проверено в круге 1), а **отсутствующий — пропускается**.

Отсутствующий `Content-Type` получается тривиально: у `Blob` с пустым `type`
тело не порождает заголовка, автор-заголовков нет → запрос остаётся «простым»,
preflight не делается, `credentials: 'include'` прикладывает кэш HTTP-аутентификации:

```js
navigator.sendBeacon('https://repo.example/api/users',
  new Blob([JSON.stringify({username:'evil',password:'pw123456',role:'admin'})], {type:''}))
```

**Проверено на поднятом приложении:**

- `POST /api/users` **без заголовка `Content-Type`**, тело — чистый JSON → **201**,
  в БД появляется учётка `evilblob` с ролью **`admin`**;
- `POST /api/users/alice/password` без заголовка, тело `{"password":"hijacked1"}`
  → **204**, пароль администратора заменён (проверено `CheckPassword`);
- `Content-Type: ` (пустая строка) → 201, админ создан;
- `text/plain;;;`, `text/plain; charset`, `garbage`, `/` (неразбираемые) → 201,
  админ создан — рубеж падает **открыто**, а не закрыто.

Неразбираемые значения браузером cross-site не достижимы (такой `Content-Type`
не входит в CORS-safelist, значит будет preflight, а его сервис не пройдёт),
поэтому сами по себе они не путь атаки — но «ошибка разбора → пропустить» в
защитном рубеже стоит поменять заодно.

- **Серьёзность:** важная — та же, что в круге 1, и по той же причине: условие
  (в браузере администратора лежат Basic-креды к этому origin) я по-прежнему
  подтвердил только по коду (ссылка на `/download` из UI, тот же realm), а не
  замером в браузере.
- **Кто может:** внешний сайт, на который заманили администратора.
- **Чем грозит:** без изменений — создание учётки `admin` либо смена пароля
  любому пользователю, то есть полный захват установки.

**Почему возражение против строгого варианта не работает.**
`docs/reports/F12-2026-08-06.md:74-76` отвергает строгий `Content-Type` так:
«Восемь мест в замороженных `internal/integration/r6_*_test.go` шлют JSON-тело
вообще без заголовка `Content-Type` — `r6_cli_test.go:101`, …». Это неверно:
все девять таких мест вызывают `e.wantStatusAs`, а тот
(`internal/integration/r6_helpers_test.go:99`) передаёт `jsonHdr`, то есть
`Content-Type: application/json`. **Замороженные `r6_*`-тесты трогать не нужно
вообще** — проверено экспериментом.

Реальная цена измерена: временно переписал `formBody` на «нет заголовка или он
не разбирается → 415» и прогнал весь набор.

- `scripts/smoke.sh` — **OK** (документированные `curl -u … -d '{…}'` шлют
  `application/x-www-form-urlencoded`, он остаётся разрешённым);
- `internal/integration` (в т.ч. все `r6_*`) — **зелёный, ни одной правки**;
- падают только юнит-тесты `internal/api`, потому что их локальные хелперы не
  ставят заголовок: `do` (`internal/api/api_test.go:58`), `doAs`
  (`api_t19_test.go:106`) и хелперы в `api_f12_test.go`, `api_t13_test.go`.
  Добавление одной строки в `do` («тело есть → `application/json`») убрало
  большую часть падений сразу; остаток — те же 3–4 общих хелпера.
- Отдельный случай, который надо учесть в самом рубеже: `PATCH /api/apps/{name}`
  с **пустым** телом — легальная операция («ничего не менять»), и её нельзя
  отбивать по отсутствию `Content-Type`. Проверку стоит выполнять только при
  непустом теле (`r.ContentLength != 0`).

**Как чинить:** в `formBody` считать «заголовок отсутствует или не разбирается»
отказом (415), а не пропуском, — при непустом теле запроса. Денилист по
`text/plain`/`multipart/form-data` при этом можно оставить как есть: вместе они
дают ровно нужное покрытие, а `application/x-www-form-urlencoded` и
`application/json` продолжают работать, так что ни доки, ни smoke править не
надо.

**Как проверить:**
- `POST /api/users` без заголовка `Content-Type` с телом
  `{"username":"evil","password":"pw123456","role":"admin"}` → **415**,
  учётка не создаётся;
- `POST /api/users/{u}/password` без заголовка → **415**, пароль не меняется;
- `Content-Type: text/plain;;;` и `garbage` → **415**;
- `application/json` и `application/x-www-form-urlencoded` → как раньше;
- `PATCH /api/apps/{name}` с пустым телом → **200**, не 415;
- `bash scripts/smoke.sh` — OK; `go test ./...` — зелёный.

### S3 (замечание круга 1) — закрыто

Проверено прогонами по всем трём интерфейсам.

**Имя учётки.** `naming.NormalizeUsername` (`internal/naming/naming.go:58-67`) —
обрезка пробелов плюс `^[a-zA-Z0-9][a-zA-Z0-9._-]{0,63}$`. Отвергаются (проверено):

которых замечание и заводилось. Отдельный запрет двоеточия с объяснением про
HTTP Basic — хорошее решение: учётка с `:` в имени не смогла бы войти никогда.

**Нормализация на пути поиска, а не только создания** — то, что просили
проверить особо. Работает во всех трёх:

- API: `mustUser` (`internal/api/users.go:90-93`) нормализует `r.PathValue`.
  Проверено: создание `"  ops  "` → 201 с `"username":"ops"`;
  `PATCH /api/users/ops` → 200, `/api/users/%20ops%20` → 200,
  `/api/users/ops%20` → 200, `/api/users/OPS` → 404 (регистр значим и при
  создании — согласовано).
- CLI: `mustUser` (`cmd/apprepo/main.go:215`) нормализует. Проверено на
  собранном бинарнике: `user add "  ops  "` → создаёт `ops`;
  `user role "  ops  " maintainer` → находит `ops`; `user role OPS` → not found.
  Сообщения об успехе печатают `u.Username`, а не введённую строку.
- UI: `createUser` (`internal/web/users.go:144`) нормализует; операции над
  чужими учётками адресуются числовым `{id}`, так что имени в пути нет вовсе.

Невалидное имя в пути API даёт **404**, а не 400, и тем же телом, что и
«не найдено», — перечисления учёток по коду ответа не появилось.

**Пароль.** `naming.ValidatePassword` (`naming.go:70-80`), 8..72 байта.
Проверено через API: 7 → 400 `password must be at least 8 bytes, got 7`;
8 → 201; 72 → 201; 73 → **400** `password must be at most 72 bytes, got 73`
(было 500 — S3-б закрыто); пустой → 400. `POST /api/me/password` с новым

exit 1, `password must be at least 8 bytes, got 5`. UI: та же
`ValidatePassword` в `createUser`, `resetUserPassword`, `changeOwnPassword`.

паролей это типовой способ запереть людей снаружи. `ValidatePassword` стоит

учётка со старым 3-символьным паролем входит по Basic (`GET /api/apps` → 200) и
через UI (`POST /login` → 303).

## Новые находки

### N1. Учётки со старыми именами не управляются ни из API, ни из CLI

- **Серьёзность:** замечание
- **Где:** `internal/api/users.go:90-93` (`mustUser` нормализует имя из пути),
  `cmd/apprepo/main.go:212-220` (то же в CLI), при том что
  `internal/auth/auth.go:57` (`authenticate` → `GetUser`) имя **не** нормализует
- **Кто может:** не нарушитель — это состояние установки, обновлённой с версии
  до F12
- **Что не так:** нормализация применена и на поиске (это правильно и я это
  засчитал выше), но в БД, пережившей обновление, лежат имена, которые
  `NormalizeUsername` теперь отвергает: до F12 API принимал `аlice`, `admin `,
  `a:b` — я это показал в круге 1. Такая строка остаётся полностью рабочей
  учётной записью, а адресовать её из API и CLI больше нельзя.
  **Проверено:** легаси-учётка `аlice` (кириллическая `а`) с ролью `admin`
  входит по Basic и получает `GET /api/users` → **200**, то есть это живой
  администратор; при этом `DELETE /api/users/<кириллица>` → **404**
  (`NormalizeUsername` отвергла имя до похода в БД), а CLI на
  `user role|disable|delete` отвечает
  `apprepo: invalid username "аlice": must match …` и завершается с кодом 1.
  Для `admin ` эффект другой, но с тем же итогом: имя нормализуется в `admin`,
  и операция уходит **не на ту** строку (или в 404, если `admin` не заведён).
- **Чем грозит:** в круге 1 именно такая учётка описывалась как способ
  закрепления — визуальный двойник, который переживает беглый просмотр списка.
  Теперь он вдобавок не убирается штатным путём; CLI, который в проекте
  объявлен «аварийной дверью» в установку, куда некому войти
  (`cmd/apprepo/main.go:13-14`, CLAUDE.md), такую учётку не видит вообще.
  Отдельный оттенок: если легаси-имя `admin ` соседствует с обычным `admin`,
  админская операция по имени `admin ` молча попадёт в `admin`.
- **Что смягчает (проверено, поэтому замечание, а не выше):** веб-интерфейс
  адресует учётки числовым `{id}`, имя в путь не входит, поэтому убрать легаси-
  учётку можно. Проверено: страница `/users` показывает `аlice`;
  `POST /users/{id}/delete` с подтверждением именем → 303, учётка удалена;
  `POST /users/{id}/role` легаси-учётке `admin ` → 303, роль сменилась. Вход в
  UI тоже работает: `loginPost` передаёт имя в `LoginUser` без нормализации,
  так что легаси-админ может войти и разобраться сам.
- **Как чинить (варианты, по возрастанию цены):**
  1. одноразовая проверка при старте: пройти `ListUsers`, прогнать имена через
     `NormalizeUsername` и написать в лог предупреждение со списком тех, что не
     проходят («N accounts have legacy names, manage them in the web UI»); плюс
     абзац в README про обновление;
  2. в API и CLI при неудачной нормализации делать второй поиск по **сырой**
     строке и, если такая учётка есть, разрешать над ней операции удаления и
     блокировки (создание — только по новым правилам);
  3. миграция имён при старте — не рекомендую: переименование ломает
     Basic-креды CI, которые уже прописаны в чужих пайплайнах, и делает это
     молча.
- **Как проверить:** на БД с учёткой `аlice` (заведённой мимо хендлеров) старт
  сервиса пишет в журнал строку про легаси-имена; `apprepo user list` их
  показывает (уже показывает); выбранный из вариантов путь удаления работает.

## Проверенное и чистое (в рамках круга 2)

- **Единственная точка разбора JSON.** `grep` по не-тестовому коду: `json.NewDecoder`
  в `internal/api` ровно один — внутри `decodeJSON`, и `formBody` стоит перед
  ним. Все семь вызовов `decodeJSON` (`users.go:128,176,217,275`,
  `api.go:333,378,532`) проходят рубеж.
- **`PUT /api/apps/{name}/versions/{version}`** тела через `decodeJSON` не
  читает и рубежа не требует: метод `PUT` не входит в CORS-safelist, поэтому
  кросс-сайтом без preflight не достижим, а preflight сервис не проходит.
- **Пустое тело.** `decodeJSON` по-прежнему трактует `io.EOF` как «нечего
  менять», так что `PATCH /api/apps/{name}` без тела работает — перевод трёх
  хендлеров на общий разбор поведение не изменил (`go test ./...` зелёный).
- **Политика пароля не создала оракула.** В `changeOwnPassword`
  (`web/users.go:27-36`) `switch` проверяет текущий пароль **первым**, и только
  потом длину нового: по коду ответа нельзя узнать про чужую учётку ничего, чего
  нельзя было раньше.
- **Хеши по-прежнему не утекают.** `userJSON` не изменилась; `apprepo user list`
  печатает username/role/disabled/created; страница `/users` рендерит имена
  через `html/template` (легаси-имя `аlice` отрисовалось как текст).
- **Тексты ошибок валидации** (`invalid username %q: must match …`,
  `password must be at least 8 bytes, got 7`) внутренних деталей не раскрывают:
  это 4xx-валидации, которые проект оставляет информативными сознательно.
- **`store.ErrNoUser`** — новая ошибка, но не новый канал: она отдаётся как 404
  там, где раньше был 500, и только для учётки, которую вызывающий уже нашёл.
- **Зависимости.** `git diff 286a01f..HEAD -- go.mod go.sum` пуст.
- **Сборка и тесты.** `go vet ./...` чисто, `go test ./...` все пакеты зелёные,
  `bash scripts/smoke.sh` — OK (прогонял и на исходном коде, и под временным
  экспериментом).
