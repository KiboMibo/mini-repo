## Резюме

Все пять пунктов круга 1 действительно исправлены, и исправлены по существу, а не
формально: бюджет чтения работает, определение переехало до публикации, FIFO больше не
вешает старт, fat Mach-O опознаётся, UI и API отвечают одинаково. Блокирующей S1 больше
нет — измерено.

Но у выбранного бюджета оказалась цена, которую F21 не заметила, потому что проверяла его
не на том формате. **`1 MiB` — не тот масштаб для Mach-O и PE:** их разборщики читают
таблицу символов, а она составляет ~5 % от размера файла. Обычный `go build cmd/compile`
под darwin (28 МБ) и под windows (29 МБ), а также настоящий universal binary теперь
**не определяются вовсе** и, по правилу волны 8 «платформа обязательна», получают
`400 platform_required` — то есть ровно тот сценарий, ради которого автоопределение и
делалось, сломан начиная примерно с 20 МБ. До F21 эти же файлы определялись правильно.
Это новая важная находка N1.

Три вердикта из пяти — «закрыто», один — «закрыто с новой находкой», один (S4) — «закрыто
частично»: fat-бинарник опознаётся, пока он маленький, и упирается в тот же бюджет, когда
настоящий.

| Пункт круга 1 | Вердикт |
|---|---|
| S1 — неограниченный разбор, OOM | **закрыто**, но выбранная граница даёт N1 |
| S2 — определение по опубликованному файлу | **закрыто** |
| S3 — рубеж типа файла после `os.Open` (FIFO) | **закрыто** |
| S4 — universal binary отклоняется | **закрыто для файлов до ~10 МБ на срез**, для настоящих крупных — нет (N1) |
| Паритет UI/API (R8-test) | **закрыто** |

Новых находок три: одна важная (N1) и два замечания (N2, N3). Блокирующих нет.

## Вердикт по каждому пункту

### S1 — закрыто (проверено измерением)

`budgeted()` оборачивает все четыре вызова разборщиков, отдельным бюджетом на попытку;
отказ выдаётся **до** обращения к нижележащему чтению, что важно, потому что `saferio`
выделяет буфер под запрошенный кусок заранее. Мимо бюджета разборщик не вызывается нигде:
`grep` по `elf.NewFile|macho.NewFile|macho.NewFatFile|pe.NewFile` в не-тестовом коде даёт
ровно четыре строки, все в `detect`, все в обёртке.

Те же образцы, что в круге 1, плюс девять новых (гигантский `phnum`, `phnum×phentsize`
на 3,6 МБ, секции ровно на бюджет, fat Mach-O с `nfat_arch = 0x7fffffff` и правдоподобными
заголовками срезов, fat64, PE с `e_lfanew` за пределами файла, с `e_lfanew` на самого
себя, с `NumberOfSymbols = 0xffffffff`, с таблицей строк на 4 ГБ):

| | круг 1 | круг 2 |
|---|---|---|
| ELF, расширенная нумерация секций, 256 MiB | 8,1 с / 1099 MiB | **10 мс / 11,1 MiB** |
| ELF, `shstrtab` во весь файл, 256 MiB | 6,1 с / 547 MiB | **8 мс / 10,1 MiB** |
| ELF, `phnum=phentsize=0xffff`, 64 MiB | — | 3 мс / 10,6 MiB |
| Mach-O fat, `nfat_arch=0x7fffffff`, 64 MiB | — | 11 мс / 10,1 MiB |
| PE, `NumberOfSymbols=0xffffffff`, 64 MiB | — | 64 мс / 11,4 MiB |
| PE, таблица строк 4 ГБ, 64 MiB | — | 4 мс / 10,1 MiB |

Худший случай из двадцати — 64 мс и 11,4 MiB; пик RSS всего прогона — 22 MiB.
Потолок объясним и предсказуем: `saferio` держит фиксированный буфер в 10 MiB на попытку,
поэтому «~11 MiB на один разбор» — это и есть новая верхняя граница.

Фаззинг `Detect` (корпус из враждебных образцов и настоящих бинарников, 359 279
исполнений за 90 с, сторож на 10 с внутри каждого прогона) — ни паники, ни зависания,
ни превышения времени.

`MemoryMax=1G` и `GOMEMLIMIT=768MiB` в юните на месте — второй рубеж, как и просили;
про его новое взаимодействие с числом одновременных заливок см. N2.

### S2 — закрыто

`Detect` теперь вызывается по `up.Path()` **до** `Commit` в обоих интерфейсах
(`internal/api/api.go:655`, `internal/web/web.go:602`), окно `Commit → CreateVersion`
больше не содержит разбора вообще. Проверено сквозным сценарием: `PUT` 16 MiB архива без
`?platform=` → `400`, и в data-dir после отказа нет ничего, кроме пустого `.tmp` и файлов
БД — ни каталога приложения, ни каталога версии, ни файла. В круге 1 на этом же сценарии
файл сначала публиковался и потом удалялся.

`Upload.Path()` новых возможностей не открывает — проверено:

- путь целиком серверный (`os.CreateTemp(filepath.Join(Root, ".tmp"), "upload-*")`),
  пользовательский ввод в него не попадает ни в каком виде, traversal неоткуда взяться;
- файл `0600` (умолчание `CreateTemp`) внутри `.tmp` внутри data-dir с правами `0700`
  из `app.New` — чужому локальному пользователю он и раньше был недоступен, и остался;
- у каждого `Upload` свой временный файл, чужой прочитать нельзя;
- значение уходит ровно в один вызов — аргументом `platform.Detect`; больше `Path()`
  нигде не используется;
- утечки временного файла нет: на всех путях после `Prepare` вызывается ровно одно из
  `Commit` (удаляет `u.tmp` через `defer`) или `Discard`, включая ветки отказа по
  «нечего определять» и по расхождению; неудача уборки логируется
  (`api.rollbackFile`, `web.discardUpload`) — пункт-замечание круга 1 про молчащий
  `fs.Remove` в API тоже закрыт.

### S3 — закрыто

`os.OpenFile(path, os.O_RDONLY|syscall.O_NONBLOCK, 0)` — FIFO теперь отдаёт
`("", nil)` мгновенно вместо вечного ожидания писателя (проверено на том же наборе:
FIFO, каталог, симлинк на каталог, на `/dev/zero`, наружу data-dir, битая ссылка).
Следование за симлинком оставлено осознанно и объяснено комментарием — это законный выбор,
раз по HTTP симлинк в data-dir не создаётся. Утверждение в отчёте T24 больше не
расходится с кодом, и тесты на FIFO появились на обоих уровнях
(`internal/platform/fifo_unix_test.go`, `internal/app/fifo_unix_test.go`).

### S4 — закрыто частично

`macho.NewFatFile` стоит перед `macho.NewFile`, значение `Universal` заведено рядом с
`Any`, вне `knownArch`. Собранный руками universal binary из двух настоящих срезов
(3,1 МБ) определяется как `darwin/universal`; заливка проходит `201`, значение видно на
странице приложения, переживает сохранение диалога без изменений (`303`) и принимается
`PATCH`'ем. Одиночный срез в fat-обёртке разворачивается в обычную пару — разумно.

Но настоящий universal binary из двух обычных `go build cmd/compile` (55,6 МБ) —
`400 platform_required`: `NewFatFile` разбирает каждый срез как Mach-O, и **срезы делят
один бюджет**, поэтому порог на срез примерно вдвое ниже, чем у одиночного файла. Это тот
же корень, что и N1, и чинится вместе с ним.

### Паритет UI и API — закрыто

Проверено одним и тем же файлом через оба интерфейса:

| Сценарий | API | UI |
|---|---|---|
| linux-бинарник + заявленная `windows/amd64` | `409 platform_mismatch`, в тексте оба значения | `409`, в тексте `built for linux/amd64` |
| архив без платформы | `400 platform_required` | `400` |

Класс кода совпадает, определённое значение названо в обоих текстах. Возврат уже
заполненных полей формы (`view.Upload`) значения из чужого запроса не подмешивает —
поля берутся из `fields` того же разбора multipart и уезжают в шаблон через
`html/template`.

## Новые находки

### N1. Бюджет в 1 MiB рассчитан по ELF, а Mach-O и PE читают ~5 % файла: настоящие бинарники крупнее ~20 МБ перестали определяться

- **Серьёзность:** важная
- **Где:** `internal/platform/platform.go:126` (`detectBudget = 1 << 20`), следствия —
  `internal/api/api.go:736` (`platform_required`), `internal/web/web.go:611–616`
- **Класс:** отказ в обслуживании легитимного запроса из-за слишком узкого рубежа
  (регрессия функции, введённая исправлением)
- **Кто задевает:** всех, кто заливает сборки под macOS и Windows; ELF не задет
- **Путь:** `PUT …?filename=…` без `?platform=` (или форма UI на «detect automatically»)
  → `Detect` → `macho.NewFile`/`pe.NewFile` читают таблицу символов → бюджет исчерпан →
  формат «не опознан» → правило волны 8 «платформа обязательна» → `400 platform_required`.

`debug/elf.NewFile` символы не читает — его объём чтения постоянен (2455 байт и для
1,5 МБ, и для 28 МБ). `debug/macho` и `debug/pe` читают таблицы символов и строк, и это
линейно по размеру файла. Замерено на настоящих `go build` (счётчик на `io.ReaderAt`,
без бюджета):

| Файл | Размер | Прочитано | Доля | Вердикт круга 2 |
|---|---:|---:|---:|---|
| `cmd/link` darwin/amd64 | 8,6 МБ | 338 240 | 3,94 % | `darwin/amd64` |
| `cmd/vet` darwin/amd64 | 10,0 МБ | 442 240 | 4,40 % | `darwin/amd64` |
| `cmd/pprof` darwin/amd64 | 18,6 МБ | 971 616 | 5,22 % | `darwin/amd64` |
| **`cmd/go` darwin/amd64** | **19,4 МБ** | **1 012 360** | **5,22 %** | `darwin/amd64` (96,6 % бюджета) |
| **`cmd/compile` darwin/amd64** | **28,4 МБ** | **1 391 568** | **4,90 %** | **`""` → 400** |
| `cmd/compile` darwin/arm64 | 27,2 МБ | 1 389 952 | 5,11 % | **`""` → 400** |
| `cmd/go` windows/amd64 | 19,9 МБ | 1 028 364 | 5,18 % | `windows/amd64` |
| **`cmd/compile` windows/amd64** | **29,1 МБ** | **1 452 006** | **4,99 %** | **`""` → 400** |
| universal (два среза `cmd/compile`) | 55,6 МБ | — | — | **`""` → 400** |
| `cmd/compile` linux/amd64 | 28,3 МБ | 2 455 | 0,01 % | `linux/amd64` |

Порог — около **20 МБ** для одиночного Mach-O и PE и примерно вдвое меньше на срез для
fat. `go build cmd/go` проходит с запасом в 3,4 % — то есть на грани: одна лишняя
зависимость в чужом проекте переводит сборку через порог, и это выглядит как случайный
отказ. Проверено не только в лаборатории, но и через настоящий сервер: `PUT` каждого
из этих файлов без `?platform=` даёт `201` с правильной платформой для linux и `400
platform_required` для darwin/windows/universal. **До F21 те же файлы определялись
правильно** (прогнал их старой копией `platform.go`: `darwin/amd64` за 12 мс,
`darwin/arm64` за 9 мс, `windows/amd64` за 29 мс) — это регрессия, а не давняя дыра.

**Почему это прошло мимо зелёного набора.** Единственный тест бюджета на настоящем файле —
`TestDetectRealBinaryFitsBudget` (`internal/platform/platform_test.go:512`) — берёт
`os.Executable()`, то есть тестовый бинарник хоста, и **пропускает себя, если хост не ELF**
(`t.Skipf("хост не ELF: %v", err)`). Отсюда и цифра «1624 байта» в отчёте F21: это ELF.
Интеграционные `TestRealBinariesDetectedViaAPI/UI` кросс-собирают `tinyMain` — программу
на полторы страницы, около 1,5 МБ, то есть ~72 КБ чтения. Ни один тест не берёт
Mach-O или PE такого размера, какой лежит в артефакт-репозитории. Обоснование бюджета в
`docs/reports/F21-2026-08-06.md:36–40` («darwin/windows — до 72 KB, запас 14 раз»)
опирается на мои же цифры круга 1, а они были сняты на файлах в 1,5 МБ — это не потолок,
а 5 % от того конкретного размера.

- **Чем грозит:** обещание волны 8 «CI-скрипты с бинарниками не правятся ни одной
  строкой» перестаёт выполняться для macOS и Windows; пайплайны ломаются на `400` при
  переходе через ничем не обозначенный порог. Предсказуемая реакция — либо поднять
  бюджет (и вернуть S1, потому что бомба масштабируется тем же множителем), либо
  прописать в CI `?platform=any` для всего подряд (и обесценить колонку, ради которой
  волна затевалась).
- **Как чинить.** Поднимать бюджет — тупик: и потребность настоящего файла, и стоимость
  бомбы линейны по размеру, так что любая граница отделяет одно от другого только
  случайно. Правильный ход — **не звать полные разборщики вообще**: всё, что код берёт
  из результата, лежит в первых байтах и читается напрямую, за постоянное время:
  - ELF — `e_ident[EI_CLASS]`, `e_ident[EI_DATA]`, `e_ident[EI_OSABI]` (байты 4, 5, 7) и
    `e_machine` (смещение 0x12);
  - Mach-O — магия и `cputype` (смещения 0 и 4);
  - fat Mach-O — магия, `nfat_arch` (смещение 4) и `cputype` каждого среза (8 + 20·i);
  - PE — `e_lfanew` (0x3c) и `Machine` (`e_lfanew`+4).

  Таблицы секций, загрузочные команды и таблицы символов, из-за которых и возникает и
  бомба, и порог, не дают коду ни одного используемого поля. Ручной разбор заголовка —
  порядка сорока строк, O(1) по размеру файла, и он снимает и S1, и N1 разом; бюджет
  тогда можно оставить как страховку или убрать вместе с `debug/*`.
  Промежуточный вариант, если расставаться с `debug/*` не хочется: сначала пробовать
  ручной разбор заголовка, а в `debug/*` под бюджетом уходить только когда заголовок
  не опознан.
- **Как проверить:** тест, который кросс-собирает **крупный** бинарник (`go build
  cmd/compile` под darwin/amd64, darwin/arm64, windows/amd64 — по 27–29 МБ) и требует
  правильной платформы; тест на universal binary, собранный из двух таких срезов;
  существующий `TestDetectRealBinaryFitsBudget` не должен пропускать себя молча —
  либо он проверяет все три формата, либо его `t.Skipf` заменяется на явный
  `t.Log` + отдельный тест на Mach-O/PE. Обе бомбы из `TestDetectBudgetOnHostileELF`
  обязаны остаться в пределах прежних миллисекунд и мегабайтов.

### N2. `MemoryMax=1G` появился, а ограничения на число одновременных разборов — нет

- **Серьёзность:** замечание
- **Где:** `deploy/apprepo.service:15–22`, `internal/platform/platform.go:126`
- **Класс:** взаимодействие нового жёсткого потолка памяти с неограниченной
  параллельностью
- **Кто может:** учётка с `PermVersion`
- **Путь:** N одновременных заливок → N одновременных `Detect` → каждый до ~11 MiB
  (фиксированный буфер `saferio` в 10 MiB на попытку) → cgroup-лимит.

Замер (одновременные `Detect` PE-бомбы, `VmHWM` монотонен, база теста 274 MiB):
1 → 274, 16 → 274, 64 → 605, 128 → 915 MiB, то есть примерно **+5 MiB на параллельный
разбор** сверх базы. Порядка сотни одновременных заливок подводят процесс к `MemoryMax=1G`,
и тогда его убивает уже cgroup, а не ядро — с `Restart=on-failure` это рестарт, а не
свопящаяся машина, то есть ровно то, ради чего лимит и ставили, но отказ в обслуживании
на время рестарта остаётся.

Это не возврат S1: цена одного запроса упала с «4,5 × размера файла, без потолка» до
плоских ~5–11 MiB, и без бюджета те же 128 запросов означали бы сотни гигабайт. Отдельно
подчёркиваю: **общее отсутствие ограничения частоты — давняя отложенная находка R6, и её
статус я не пересматриваю**; новое здесь только то, что F21 ввела жёсткий потолок памяти,
не связав его ни с чем, что ограничивало бы число одновременных разборов.

- **Как чинить:** семафор на `platform.Detect` (столько же, сколько ядер, или просто
  8–16) — три строки, и потолок памяти становится расчётным: `параллелизм × 11 MiB`.
  Как минимум — назвать эту зависимость в комментарии к `MemoryMax` рядом с «поднимаешь
  один — поднимай и второй».
- **Как проверить:** тест, который запускает 128 одновременных `Detect` враждебного файла
  и требует, чтобы прирост `VmHWM` не превышал заданного потолка.

### N3. `darwin/universal` вписан в разметку строкой и не назван в тексте ошибки `Parse`

- **Серьёзность:** замечание
- **Где:** `internal/web/templates/app.html:51` и `:109` (литерал `darwin/universal`
  в двух `<select>`), `internal/platform/platform.go:70` (текст ошибки `Parse`)
- **Класс:** дублирование словаря вопреки собственному инварианту; неполное сообщение
- **Кто может:** —

T26 сознательно не перечисляла платформы в разметке, и комментарий там до сих пор
объясняет почему: «копия разъехалась бы с тем, что принимает `platform.Parse`». Значение
`Universal` теперь стоит в шаблоне **двумя литералами** — единственное значение словаря,
которого нет ни в `KnownOS()`, ни в `KnownArch()`, ни в какой-либо другой функции,
отдающей его шаблону. Переименование или отмена константы разметку молча не тронет.

Рядом — вторая половина: `Parse` принимает `darwin/universal` (проверено:
`"DARWIN/UNIVERSAL"` и `" darwin/universal\n"` тоже, канонизация работает), но в тексте
ошибки перечисляет только `any`. Тот же комментарий к `Parse` обещает, что «текст ошибки
перечисляет допустимые значения» — теперь это неправда, и пользователь, набравший
`universal` или `darwin/fat`, получает список, в котором нужного ему значения нет.

- **Как чинить:** отдавать особые значения в шаблон из пакета (`platform.Special()` или
  просто добавить `Universal` в то, чем уже наполняется `view`), а в текст ошибки
  подставить оба особых значения вместо одного.
- **Как проверить:** в `internal/web/templates/` нет литерала `darwin/universal`;
  тест на текст ошибки `Parse` требует упоминания обоих особых значений.

## Проверенное и чистое

- **Пятисекундный потолок backfill — не тихая деградация.** Замерил стоимость одного
  `Detect`: неопознаваемый архив — 103 000 файлов/с (то есть в бюджет влезает ~514 000
  версий), худшая враждебная бомба из набора — ~2 100 за бюджет. Сценарий, которого я
  опасался (неопознаваемые версии в голове обхода съедают бюджет и навсегда закрывают
  дорогу тем, что за ними), требует полумиллиона неразрешимых версий: обход
  детерминирован (`ListApps` → `ListVersions`), успешно определённые из выборки уходят,
  а неразрешимые остаются постоянным префиксом — но при такой скорости упереться в это
  нереально. Формулировка в логе «the rest is left for the next start» для
  принципиально неопознаваемых строк строго говоря неточна (следующий старт остановится
  там же), но при измеренных скоростях последствий у этого нет. Отдельно: `firstErr`
  в ветке `ranOut` в лог не попадает — косметика.
  Оговорка: замеры на локальном диске с прогретым кешем; на холодном хранилище цену
  задаёт ввод-вывод, а не разбор.
- **Незакрытая версия остаётся с пустой платформой и чинится руками** — `PATCH` или
  диалог на странице приложения; ни один путь чтения пустую платформу не ломает.
- **Мимо бюджета разборщик не вызывается.** Все четыре вызова `debug/*` — внутри
  `detect`, каждый в своей обёртке; `platform.Detect` зовут ровно три места
  (`api.resolvePlatform`, `web.saveUpload`, `app.backfillPlatforms`).
- **Каждой попытке — свой бюджет**, поэтому промах на чужом формате не съедает лимит
  следующего; суммарный потолок одного `Detect` — четыре попытки, наблюдаемый пик 11,4 MiB.
- **Фаззинг** `Detect` (359 279 исполнений) — ни паники, ни зависания, ни превышения
  сторожевого таймера в 10 с.
- **`recover` на границе** остался на месте и выше всех разборщиков.
- **Спецфайлы:** каталог, симлинк на каталог, симлинк на `/dev/zero`, битая ссылка, FIFO —
  все мгновенно и без разбора.
- **Экранирование и коды** новых текстов: сообщения об отказе по платформе в UI уезжают
  через `html/template`; возврат заполненных полей формы (`view.Upload`) — тоже.
- **Права и рубежи не тронуты:** F21 не меняла ни `Register`, ни матрицу прав, ни
  `decodeJSON`; полный набор тестов, включая существующие проверки прав, CSRF и
  `Content-Type`, зелёный.
- **Один пограничный случай бюджета в ELF, практического значения не имеющий:**
  формально валидный ELF amd64 с 16 000 секций (1,02 МБ таблицы) в бюджет не влезает и
  даёт `""`. У настоящих сборок секций порядка тридцати, так что это упражнение, а не
  находка; чинится тем же ручным разбором заголовка, что и N1.
