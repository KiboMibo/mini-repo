### Повторная приёмка по изменённым местам

**Рубеж `Content-Type` (F14).** `POST /api/apps` с телом и разными заголовками:

| `Content-Type` | Код |
|---|---|
| заголовка нет вовсе | **415** |
| `text/plain` | **415** |
| `text/plain;charset=UTF-8` | **415** |
| `application/x-www-form-urlencoded` | **415** |
| `multipart/form-data; boundary=x` | **415** |
| `garbage`, `/`, `text/plain;;;` | **415** |
| `application/json` | 201 |
| `application/json; charset=utf-8` | 201 |
| `APPLICATION/JSON` | 201 |

Тело отказа — `{"error":"unsupported_media_type","message":"request body must be
sent with Content-Type: application/json"}`. 415 подтверждён на всех JSON-маршрутах:
`POST /api/apps`, `PATCH /api/apps/{n}`, `POST /api/apps/{n}/latest`,
`POST /api/users`, `POST /api/users/{u}/password`, `POST /api/me/password`.

Исключения работают как заявлено: `PATCH /api/apps/{n}` и `PATCH /api/users/{u}`
**без тела** — 200 без всякого заголовка; `PUT` версии с `--data-binary` **без**
`Content-Type` и с `text/plain` — 201 в обоих случаях (тело сырое, рубежа там
нет). Последнее в `docs/api.md` сказано не было — дописал: для CI это ровно тот
вопрос, из-за которого обновление могло бы встать.

**Политика пароля (F13).** 7 байт → `400 validation` «password must be at least
8 bytes, got 7»; 8 байт → 201; 72 байта → 201; 73 байта → `400` «password must
be at most 72 bytes, got 73»; пусто → `400` «password must not be empty».
Одинаково на `POST /api/users`, `POST /api/users/{u}/password`,
`POST /api/me/password`; в UI — те же тексты на формах (создание, сброс чужого,
смена своего: «the new password must be at least 8 bytes, got 7»); в CLI —
`apprepo: password must be at least 8 bytes, got 7`, **exit 1**, учётка не
создаётся. Совпадает с README (там про exit 1 сказано) и с api.md.

**Имя учётки (F12).** Обрезка: `" ops "` заводится как `ops` и находится по
`ops`; повтор `"  ops"` — `409 already_exists`, второй учётки не появляется; CLI
`user role "  ops  " maintainer` находит ту же строку. Отвергаются `ci:bot`,
`оператор`, `with space`, `""`, `"   "`, 65 байт — `400 validation` с текстом
`invalid username …: must match ^[a-zA-Z0-9][a-zA-Z0-9._-]{0,63}$`. То же в UI и
в CLI (`apprepo user add "ci:bot"`). Негодное имя **в пути** (`PATCH
/api/users/ci:bot`, `…/оператор`, `…/with%20space`) — `404 not_found`, а не 400;
в `docs/api.md` этого правила не было, дописал по образцу имени приложения.

**Код `invalid_password` (F12).** Неверный `current_password` →
`403 {"error":"invalid_password","message":"current password is incorrect"}`;
нехватка права → `403 {"error":"forbidden","message":"insufficient permissions"}`;
короткий новый пароль → `400 validation`. Ровно как в api.md.

**Старые имена (F14/F15).** В базу вписаны напрямую `"admin "`, `"аlice"`,
`"ci:bot"`. `apprepo user list` печатает таблицу в stdout, предупреждение — в
stderr (парсеры таблицы не ломаются), имена в кавычках; журнал при старте
`serve` печатает то же предупреждение; на `/users` каждая такая строка помечена
значком `legacy name "…"` и над таблицей появляется абзац-пояснение. В здоровой
установке ни того, ни другого нет — проверено на чистой базе. Отбор совпадает у
CLI и UI (обе стороны зовут `naming.LegacyUsername`). Текст предупреждения
дословно совпадает с приведённым в README.

**Миграция (без изменений, перепроверена).** Пре-T18 база (без `role`/`disabled`,
три учётки, одно приложение): колонки досозданы при первом открытии, все учётки
стали `admin`, приложение на месте, повторный запуск ничего не меняет. Учётки со
старыми именами после миграции сразу попадают в предупреждение — то есть сценарий
из README «обновились → посмотрели список → разобрали старые имена» работает
буквально.

## Находки

### Блокирующие

Нет.

### Важные

1. **Примеры curl были невоспроизводимы: `CRED=alice:secret`** —
   `docs/api.md` (строка «Далее `BASE=…`, `CRED=alice:secret`»),
   `README.md` (блок «Примеры curl»)
   Что не так: после F13 пароль короче 8 байт завести нельзя, а во всех
   примерах стоял `alice:secret` — шесть байт. Вдобавок пример
   `POST /api/me/password` в README посылал `"current_password":"secret-pass"`,
   то есть не тот пароль, что объявлен в `CRED` двадцатью строками выше.
   Чем грозит: читатель заводит `alice` с паролем `secret`, получает отказ, и
   первое же знакомство с сервисом — «в документации команды не работают».
   Ровно тот случай, когда устаревший пример вреднее отсутствующего.
   Предлагается / сделано: `CRED=alice:s3cret-pass` в обоих документах, пример
   смены пароля приведён к нему же, к строке с `CRED` добавлено пояснение,
   почему пароль такой длины. Все примеры прогнаны заново (таблица выше).

2. **Предупреждение о старых именах обещает больше, чем есть: учётка с
   двоеточием войти по Basic не может** — `cmd/apprepo/main.go`
   (`legacyNameWarning`), `internal/web/templates/users.html` (абзац-пояснение)
   Что не так: текст говорит про все такие учётки «they still work and can sign
   in». Проверено на живом сервисе: `"admin "` и `"аlice"` действительно входят
   и по Basic (`GET /api/me` → 200), и в UI; а `"ci:bot"` по Basic получает
   **401** — HTTP Basic кодирует пару как `user:password`, поэтому сервер читает
   имя как `ci` с паролем `bot:…`. Это ровно то, о чём предупреждает комментарий
   в `internal/naming/naming.go` («учётка с двоеточием в имени не может войти
   никогда»), но в текст предупреждения оно не попало.
   Чем грозит: администратор читает «работает, войти может» и откладывает
   разбор, а за такой учёткой уже стоит сломанный пайплайн. Если её роль —
   `deployer` (в UI не пускают по роли, по Basic не пускает протокол), учётка
   мертва полностью, и никакого сигнала об этом оператор не получает.
   Предлагается: в `legacyNameWarning` и в тексте на `/users` разделить два
   случая — имена с пробелами и не-ASCII остаются рабочими, имя с двоеточием по
   Basic не аутентифицируется вовсе и разбирается первым. Продуктовый код не
   правил (не моя зона); в `README.md` разница уже описана, там же оговорено,
   что формулировка сервиса неточна.

### Замечания

- `cmd/apprepo/main.go:mustUser` — сообщение печатает исходную строку, а не
  нормализованную: `apprepo user role "admin " developer` отвечает
  `user "admin " not found`, хотя искал `"admin"`. Оператор, разбирающий старые
  имена, читает это как «строки нет вовсе», хотя строка есть и видна в
  `user list`. Косметика, но именно в том сценарии, ради которого писалось
  предупреждение.
- Форма входа (`auth.authenticate`) имя не нормализует — намеренно и правильно
  (иначе учётки со старыми именами перестали бы входить), но нигде не записано.
  Зафиксировал инвариантом в `CLAUDE.md`, чтобы «для единообразия» не добавили
  нормализацию и туда: это молча выкинет из системы всех легаси-пользователей.
- `internal/web/templates/users.html:30` — дата создания по-прежнему сырой
  строкой из SQLite против форматированной на странице приложения (замечание из
  круга 1, не закрывалось и не блокирует).
