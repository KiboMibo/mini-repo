## Резюме

Система ролей проверена не по отчётам, а на собранном бинарнике: поднят сервис
на временном data-dir, заведены четыре учётки — по одной на роль — и каждая
матрица «роль × маршрут» пройдена руками через curl, отдельно по API и
отдельно по UI-формам (сессия + CSRF). **Расхождений между заявленной моделью
прав и фактическим поведением не найдено ни одного.** Все ключевые сценарии
приёмки — `deployer` не в интерфейсе, но качает и меняет пароль по API; `admin`
управляет учётками; последний админ защищён; блокировка закрывает доступ
мгновенно — воспроизведены с ожидаемыми кодами ответов. `go test -count=1 ./...`
и `scripts/smoke.sh` зелёные.

Блокирующих находок нет. Главное, на что стоит посмотреть: `scripts/smoke.sh`
не проверяет волну 6 вовсе — сквозной прогон на собранном бинарнике останется
зелёным, даже если разграничение прав сломается целиком.

Документация приведена в соответствие с кодом: в `docs/api.md` не было раздела
о правах вообще, README утверждал, что учётки заводятся только через CLI,
CLAUDE.md знал лишь про подкоманду `user add`.

### Отдельные сценарии приёмки

**`deployer` не пускается в интерфейс, но качает и меняет пароль по API.**
Логин проходит (303, сессия создаётся) — и это правильно: `RequireSession`
редиректить не на что. Любая страница отвечает `403` со страницей-объяснением
(`Not available for your role`, `<title>Not available — apprepo`), где прямо
написано, что роль даёт доступ только к `/api/…` и `/download/…`. При этом:

- `GET /download/demo/1.0.0` и `/download/demo/latest` — `200`, файл отдаётся;
- `POST /api/me/password` с верным `current_password` — `204`; после смены
  старый пароль даёт `401`, новый — `200`; скачивание с новым паролем — `200`;
- `POST /password` в UI — `403` (у роли нет `PermUI`). То есть для `deployer`
  смена пароля возможна **только** через API — задокументировано.
- `POST /logout` — `303`: выход намеренно оставлен без `PermUI`, иначе с
  страницы-объяснения нельзя было бы погасить сессию.

**`admin` управляет учётками.** Полный цикл на живом сервисе, по API и в UI:
создание (`201`, в ответе нет и не может быть хеша пароля), список (`200`,
сортировка по имени), смена роли (`200`), сброс пароля (`204` — старый пароль
сразу `401`, новый `200`), блокировка/разблокировка (`200`), удаление (`204`).
В UI то же самое: `Set` роли, `Block`/`Unblock`, `Reset password`, `Delete` со
строгим подтверждением вводом имени (без подтверждения — `400`, ничего не
удаляется), `New user`. Ошибки: неизвестная роль — `400 validation` со списком
допустимых, дубль — `409 already_exists`, несуществующий пользователь —
`404 not_found`, битый JSON — `400 validation`.

**Последнего админа не разжаловать.** При единственном активном админе:

| Операция | API | UI | CLI |
|---|---|---|---|
| разжаловать | `409 last_admin` | `409` + «cannot demote the last administrator» | `refused: no active administrator…`, exit 1 |
| заблокировать | `409 last_admin` | `409` + «cannot block…» | `refused: …`, exit 1 |
| удалить | — (перекрыто `self_delete`) | — (перекрыто) | `refused: …`, exit 1 |

Удаление своей учётки — `409 self_delete` независимо от числа админов; в UI
кнопка `Delete` для своей строки не рисуется вовсе (`{{if ne $u.ID $.User.ID}}`),
а прямой POST отвечает `409`. Понизить **себя** при втором активном админе
можно (`200`) — и сразу после этого `GET /api/users` даёт `403`, то есть роль
действительно перечитывается. Проверено, что заблокированный админ не считается
активным. После восстановления второго админа разжалование проходит (`200`).

**Блокировка мгновенно закрывает доступ.** У `dev` была живая UI-сессия
(`GET /` → 200). Сразу после `PATCH /api/users/dev {"disabled":true}` (`200`):

- `GET /` с той же кукой → `303` на `/login?next=%2F` (сессия удалена);
- `GET /api/me` по Basic Auth → `401`;
- `GET /download/demo/latest` → `401`.

После разблокировки Basic Auth снова `200`, но старая сессия не воскресает —
нужен повторный вход. То же поведение из UI (`POST /users/{id}/disabled`).

**Роль читается из БД на каждом запросе.** На одной и той же сессии без
перелогина: `developer` получает `403` на `POST /apps`; админ повышает его до
`maintainer` — тот же запрос той же сессией даёт `303`; понижение до `deployer`
— `GET /` немедленно `403`. Кеша роли в сессии нет.

**Смена своего пароля в UI** (`developer`): `POST /password` → `303` на
`/login?m=password-changed`, старая сессия мертва (`303`), старый пароль по API
`401`, новый `200`, на `/login` показывается notice «Your password has been
changed. Please log in again.». Неверный текущий пароль — `401` с текстом на
странице, несовпадение повтора — `400`.

**Миграция существующей установки.** Собрана БД по схеме до T18 (таблица
`users` без `role`/`disabled`, два пользователя, одно приложение), затем
открыта текущим бинарником:

- колонки `role`, `disabled` досозданы автоматически при первом же открытии
  БД (достаточно `apprepo user list`, отдельной команды миграции не нужно);
- обе существующие учётки получили `role=admin`, `disabled=no`;
- повторный запуск ничего не меняет — миграция идемпотентна;
- приложение `legacyapp` и его метаданные на месте;
- сервис на мигрированной БД поднимается, мигрированная учётка реально
  работает как админ (`GET /api/users` → `200`).

**CLI.** Все семь подкоманд прогнаны: `add` (первый — `admin` без `-role`;
второй без `-role` — exit 2 со справкой и списком ролей), `list` (таблица
без хешей), `role`, `password`, `disable`, `enable`, `delete` (без `-yes` —
отказ). Синтаксис в README сверен с `usage()` и диспетчером в
`cmd/apprepo/main.go`, а не с отчётом T21.

## Находки

### Важные

1. **`scripts/smoke.sh` не покрывает волну 6 ни одной проверкой** —
   `scripts/smoke.sh`
   Что не так: сквозной сценарий заводит одного пользователя (`user add alice`,
   он же `admin`) и проверяет только операции с приложениями и версиями. Ни
   одного `403`, ни одной второй учётки, ни одной проверки управления
   пользователями. Между тем это единственная проверка, которая гоняет
   **собранный бинарник**, а не `httptest`.
   Чем грозит: разграничение прав может сломаться целиком (например, кто-то
   повесит новый маршрут мимо `Require`, или матрица `rolePerms` разъедется), а
   smoke останется зелёным и пропустит это в релиз. Ровно та ситуация, ради
   которой smoke и существует.
   Предлагается: добавить в конец сценария короткий блок — завести
   `deployer`-учётку и админскую вторую, проверить: `deployer` получает `403`
   на `PUT` версии и `200` на `/download`; `deployer` получает `403` на `GET /`;
   `admin` создаёт и блокирует учётку, заблокированная даёт `401`; разжалование
   последнего админа даёт `409`. Это ~20 строк в стиле существующих проверок.

### Замечания

- `internal/api/users.go:259` — `POST /api/me/password` при неверном
  `current_password` отвечает кодом `forbidden` (403) — тем же, что и нехватка
  права. Скрипт в CI по коду не отличит «пароль неверный» от «роль урезали»,
  различается только `message`. Менять контракт в рамках QA не стал —
  расхождение явно оговорено в `docs/api.md`.
- Нигде нет требований к паролю, кроме непустоты: `POST /api/users` с
  `"password":"a"` возвращает `201`, и такой учёткой можно войти. Одинаково в
  API (`internal/api/users.go:52`), UI (`internal/web/users.go:137`) и CLI
  (`cmd/apprepo/main.go:readPassword`). Если политика паролей нужна, её место —
  одна общая функция рядом с `auth.HashPassword`, иначе три копии разъедутся.
- `internal/web/templates/users.html:30` — дата создания печатается сырой
  строкой из SQLite (`2026-08-07 13:25:23`), тогда как на странице приложения
  соседняя колонка форматируется (`{{.V.CreatedAt.Format "2006-01-02 15:04"}}`),
  а API отдаёт RFC 3339. Причина техническая: `store.User.CreatedAt` — `string`,
  а `store.Version.CreatedAt` — `time.Time`. Косметика.
- `internal/store/store.go:355` (`affected`) — если пользователя удалят между
  `mustUser` и записью, `PATCH /api/users/{u}` и
  `POST /api/users/{u}/password` вернут `500`, а не `404`: «user not found» из
  `affected` — обычная ошибка, и `userWriteErr` уводит её в `internalErr`.
  Окно узкое (две операции админа одновременно), данные не портятся.
- `internal/web/users.go:24` — `changeOwnPassword` разыменовывает
  `h.auth.CurrentUser(r)` без проверки на `nil`, тогда как соседние
  `api.getMe`/`api.changeMyPassword` такую проверку делают. Сейчас безопасно
  (маршрут висит под `guard`, то есть за `RequireSession`), но если маршрут
  когда-нибудь перевесят — это паника, а не 500.

   релиза. Без этого сквозной прогон не удержит разграничение прав.
