## Резюме

Волна 5 впервые даёт коду право удалять и переименовывать по путям, построенным из
пользовательского ввода, и рубеж `internal/naming` в целом держит: `..`, `/`, `.`, пустое
имя, `latest`, `%2F` в path-параметре, неканонический semver — всё отвергается на всех трёх
входах (UI-форма, JSON API, path-параметры), валидация идёт до касания ФС, и `files`
дублирует её у себя.

Дыра ровно одна и она структурная: каталоги приложений и **файл БД лежат в одном каталоге**,
а `files.RemoveApp` делает `os.RemoveAll` по любому имени, прошедшему регулярку. Имя
приложения `apprepo.db` регулярку проходит. Любой залогиненный пользователь двумя обычными
запросами (`POST /api/apps` + `DELETE /api/apps/apprepo.db`) удаляет боевую БД — вместе с
таблицами `users` и `sessions`; сервис при этом отвечает 204 и продолжает работать на уже
открытом дескрипторе, так что до перезапуска никто ничего не замечает. Воспроизведено на
всех трёх путях вызова (API, UI-форма, `-wal`-файл). Это одна находка с одним исправлением;
всё остальное — три замечания об упрочнении и целостности.

**Вердикт: выкатывать нельзя до закрытия S1.** Правка локальна (одна функция в
`internal/files` + опционально раскладка каталогов), риска для остального кода волны нет.

## Находки

### S1. Удаление приложения выходит за пределы своего каталога: сносится файл БД (и цель симлинка)

- **Серьёзность:** блокирующая (аспект «б» ниже — замечание)
- **Класс:** удаление по неконтролируемому пути / выход за пределы каталога (CWE-22, CWE-73)
- **Где:**
  - `internal/files/files.go:167-172` — `RemoveApp`: `os.RemoveAll(filepath.Join(st.Root, app))`
    без проверки, что цель вообще каталог приложения;
  - `internal/files/files.go:176-181` — `RemoveVersion`: `os.RemoveAll(filepath.Join(st.Root, app, version))`
    — компонент `app` резолвится как обычный путь, включая симлинки;
  - вызовы: `internal/api/api.go:345` (`DELETE /api/apps/{name}`), `internal/web/web.go:509`
    (`POST /apps/{name}/delete`), `internal/api/api.go:367` и `internal/web/web.go:539`
    (удаление версии);
  - причина коллизии имён: `internal/config/config.go:46-48` — дефолт `DBPath =
    {data-dir}/apprepo.db`, `internal/app/app.go:36` — `files.Storage{Root: cfg.DataDir}`,
    то есть каталоги приложений и файлы БД делят одно пространство имён;
  - валидатор, который эту коллизию пропускает: `internal/naming/naming.go:15`
    (`^[a-zA-Z0-9][a-zA-Z0-9._-]{0,63}$` — `apprepo.db`, `apprepo.db-wal`, `apprepo.db-shm`
    подходят под регулярку).

**Аспект (а) — блокирующий: удаление файла БД через имя приложения.**

- **Кто может:** любой пользователь с учёткой (сессия UI или Basic для API) — то есть
  весь круг пользователей сервиса; аноним не может (все маршруты за middleware).
- **Путь:**
  `POST /api/apps {"name":"apprepo.db"}` → 201 (регулярка пройдена, каталог на диске ещё не
  создаётся) → `DELETE /api/apps/apprepo.db` → `api.deleteApp` (`api.go:336`) →
  `store.DeleteApp` (строка удалена) → `files.RemoveApp("apprepo.db")` →
  `os.RemoveAll({data-dir}/apprepo.db)` → **файл БД удалён**, ответ 204.
  Тот же результат через UI-форму (`POST /apps/apprepo.db/delete` с валидным CSRF и
  `confirm=apprepo.db`) и для `apprepo.db-wal` (удаление WAL живой SQLite-БД).
- **Чем грозит:** необратимая потеря всей метаданной базы: `apps`, `versions`, а также
  `users` (все учётки, заводимые только администратором через CLI) и `sessions`. Бинарники
  остаются на диске осиротевшими — по ним нельзя восстановить ни версии, ни sha256, ни
  latest-override. Отдельно скверно, что **отказ тихий**: проверено — после удаления файла
  сервис продолжает отвечать 200 из открытого дескриптора, ошибок в лог не пишет, авария
  проявляется только при следующем перезапуске (или при открытии нового соединения пулом —
  тогда SQLite создаст пустой файл без схемы). Удаление `-wal` у живой БД — прямая угроза
  целостности незакоммиченных транзакций.
- **Про модель доверия (честно):** учётки заводит администратор хоста, ролей нет, и
  такой пользователь и так может удалить каждое приложение и каждую версию. Повышения
  привилегий между пользователями здесь нет — есть выход за границу объекта: операция
  «удалить одно приложение» уничтожает состояние аутентификации сервиса и весь каталог.
  Уровень «блокирующая» поставлен за это: подтверждённая деструктивная запись вне
  предназначенного пространства имён, необратимая, тихая, достижимая с трёх независимых
  входов, в коде, который волна и добавила. Если командир решит, что круг пользователей
  достаточно доверенный, находка понижается до важной — но откладывать её как «упрочнение»
  нельзя: исправление стоит несколько строк.

**Аспект (б) — замечание: `RemoveVersion` идёт по симлинку наружу data-dir.**

- **Кто может:** только тот, кто уже может писать в data-dir (каталог 0700, владелец —
  пользователь сервиса). Пути от HTTP-поверхности нет: сервис симлинков не создаёт.
  Поэтому — замечание, а не находка уровня выше.
- **Что проверено эмпирически (Go 1.24.7):** `os.RemoveAll` **не** идёт по симлинку,
  который сам является удаляемым листом, и не идёт по симлинкам *внутри* удаляемого
  дерева (снимается только сам линк) — то есть `RemoveApp` безопасен. Но родительские
  компоненты пути резолвятся обычным образом: если на месте `{data-dir}/{app}` лежит
  симлинк наружу, то `RemoveVersion(app, "1.0.0")` удаляет `{цель-симлинка}/1.0.0`.
  Подтверждено прямым вызовом `Storage.RemoveVersion` — валидация имён проходит,
  каталог за пределами `Root` исчезает.
- **Чем грозит:** усиление последствий локальной компрометации; чинится тем же
  изменением, что и (а), поэтому находка не разнесена.

**Аспект (в) — замечание: `.tmp` защищён только запретом ведущей точки.**
`files.Save` использует `{Root}/.tmp` (`files.go:77`); от коллизии с именем приложения его
спасает единственный символ в регулярке `naming.go:15` (первый символ обязан быть
буквенно-цифровым). Это та же причина — общий плоский namespace — и тот же фикс.

- **Как чинить (два уровня, первый обязателен):**
  1. **Рубеж в `internal/files`:** перед `os.RemoveAll` убедиться, что цель — обычный
     каталог, полученный `os.Lstat` (а не файл и не симлинк), и что для `RemoveVersion`
     это верно и для компонента `{Root}/{app}`. Отсутствующая цель по-прежнему не ошибка
     (приложение без версий). Это закрывает и (а), и (б), и любой будущий сосед в data-dir.
  2. **Устранить сам класс коллизии:** хранить приложения в отдельном поддереве —
     `Storage{Root: filepath.Join(cfg.DataDir, "apps")}` в `internal/app/app.go:36`, — тогда
     пространство имён приложений физически не пересекается ни с БД, ни с `.tmp`, и аспекты
     (а)/(в) исчезают, а не отбиваются проверкой. Проект до релиза, миграция — перенос
     существующих каталогов; если решение принимается, его надо зафиксировать в плане и
     `CLAUDE.md` (раздел «Инварианты» описывает раскладку `{Root}/{app}/{version}/{file}`).
  Вариант «занести `filepath.Base(cfg.DBPath)` в список зарезервированных имён» **не
  рекомендую**: он завязывает `naming` на конфиг, ломается при `-db` вне data-dir и не
  закрывает (б).
  Замечание к порядку операций: хендлеры удаляют строку в БД до вызова `files`, поэтому
  новый отказ рубежа 1 придёт уже после удаления строки. При выборе только варианта 1
  стоит либо проверять цель до `store.DeleteApp`, либо принять осиротевший файл БД в
  каталоге и осознанно это описать.
- **Как проверить (тестов на это сейчас нет — `TestT12TraversalRejected`,
  `internal/files/files_t12_test.go:151`, покрывает только `..`, `/`, `.`, пустое имя и
  `latest`, но не соседей внутри `Root` и не симлинки):**
  - юнит в `internal/files`: `RemoveApp` по имени, за которым лежит обычный файл, файл не
    удаляет (возвращает ошибку либо no-op — по выбранному варианту);
  - юнит в `internal/files`: `{Root}/{app}` — симлинк на каталог снаружи; `RemoveVersion`
    цель снаружи не трогает;
  - интеграционный тест в `internal/integration`: создать приложение с именем
    `filepath.Base(cfg.DBPath)` и удалить его через API и через UI — файл `cfg.DBPath`
    остаётся на месте, последующие запросы к `/api/apps` работают.
- **Как воспроизвести (сделано в этом ревью, PoC — во временном каталоге, не в репозитории):**
  тест в пакете `internal/integration` поверх `newEnv`: `createApp("apprepo.db")` →
  `DELETE /api/apps/apprepo.db` → 204 → `os.Stat(e.cfg.DBPath)` → `no such file or directory`.
  Аналогично для `apprepo.db-wal` и для UI-формы (303, файл БД исчез). Прогонялось через
  `go test -overlay=…`, рабочее дерево не менялось.

### S2. Гонка «удаление приложения ↔ переименование в его имя» уничтожает чужие файлы

- **Серьёзность:** замечание
- **Класс:** TOCTOU между БД и ФС (CWE-367)
- **Где:** `internal/api/api.go:336-350` (`deleteApp`: `store.DeleteApp` → `files.RemoveApp`),
  `internal/api/api.go:309-327` и `internal/web/web.go:469-488` (`UpdateApp` → `RenameApp`),
  `internal/web/web.go:505-512`
- **Кто может:** любой залогиненный пользователь; в том числе непреднамеренно — два
  параллельных CI-джоба
- **Путь:** приложение `a` без версий (каталога на диске нет), приложение `b` с версиями.
  Поток 1: `DELETE /api/apps/a` — строка удалена, до `files.RemoveApp("a")` ещё не дошли.
  Поток 2: `PATCH /api/apps/b {"name":"a"}` — UNIQUE свободен, строка переименована;
  `RenameApp("b","a")` видит, что `{Root}/a` не существует, и переносит каталог `b` → `a`.
  Поток 1 продолжает: `RemoveApp("a")` → `os.RemoveAll({Root}/a)` — **удалены файлы
  приложения, которое теперь называется `a` и живо в БД**. Итог: строки версий есть,
  файлов нет, скачивание отдаёт 500 (`api.go:576-580`).
  Симметричный, менее разрушительный вариант — когда у `a` каталог был: `RenameApp`
  упирается в существующий `{Root}/a`, отдаёт `ErrFileExists`, откат имени срабатывает
  (проверено: `PATCH` → 409 `app directory already exists`, строка возвращается на место).
- **Чем грозит:** тихая потеря артефактов и рассинхрон БД/ФС. Прямого выигрыша атакующему
  не даёт (он и так может удалить `b` напрямую), поэтому уровень — замечание; но окно
  подтверждается только рассуждением по коду, воспроизвести гонку я не пытался.
- **Сопутствующий аспект той же природы (замечание):** частичный сбой не компенсируется.
  Если `RemoveApp`/`RemoveVersion` упадёт на полпути (ENOSPC, EIO, права), строка в БД уже
  удалена, часть файлов — тоже, клиент получает 500, а состояние остаётся расщеплённым и
  чинится только руками. Для переименования компенсация есть и покрыта тестами
  (`api_t13_test.go:94`, `web_test.go:662`), для удаления — нет; ни лога «что осталось»,
  ни повторной попытки.
- **Как чинить:** сериализовать операции над одним приложением (мьютекс по имени/ID в
  `internal/app` или SQLite-транзакция, удерживаемая на время работы с ФС), а в удалении —
  логировать оставшийся на диске путь при ошибке `RemoveAll`, чтобы состояние было
  восстановимо. Минимальный вариант: удалять каталог **до** строки нельзя (нарушит
  зафиксированный в плане порядок «БД → ФС»), поэтому именно сериализация.
- **Как проверить:** тест с двумя параллельными запросами (delete `a` / rename `b`→`a`),
  многократный прогон под `-race`: после любой чередовки не бывает состояния «строки
  версий есть, каталога нет».

### S3. Деструктивные операции не оставляют следа в журнале

- **Серьёзность:** замечание
- **Класс:** недостаточное журналирование событий (CWE-778)
- **Где:** `internal/api/api.go:336-372`, `internal/web/web.go:494-544` — в успешных ветках
  удаления приложения, удаления версии и переименования нет ни одного `log.*`; проверено
  grep-ом по волне: новые лог-строки есть только в ветках ошибок отката
  (`api.go:319`, `web.go:479,483`)
- **Кто может:** релевантно для любого пользователя — вопрос не в атаке, а в разборе после
- **Чем грозит:** после инцидента (в том числе после S1) невозможно установить, кто и когда
  удалил приложение или версию: ни в БД (строка удалена каскадом), ни в логе следа нет.
  Пользователь известен — `auth.CurrentUser(r)` уже лежит в контексте запроса, — но нигде
  не используется при записи.
- **Как чинить:** одна строка `log.Printf` на каждую успешную деструктивную операцию с
  именем пользователя, приложением и версией. Секретов в этих полях нет; пароли, хеши и
  токены сессий писать нельзя (инвариант `CLAUDE.md`).
- **Как проверить:** после `DELETE /api/apps/x` и `POST /apps/x/delete` в серверном логе
  есть запись с именем пользователя и приложения; в логе нет ни токена сессии, ни пароля.

### S4. `store.CreateApp` не валидирует имя, хотя от этого теперь зависит удаление с диска

- **Серьёзность:** замечание
- **Класс:** несогласованная валидация на доверенной границе (CWE-20)
- **Где:** `internal/store/store.go:221-228` (`CreateApp` — вставляет `name` как есть) против
  `internal/store/store.go:268-272` (`UpdateApp` — вызывает `naming.ValidateAppName`);
  `internal/api/api.go:175-186` (`mustApp` берёт `r.PathValue("name")` и идёт прямо в
  `GetApp`, без `naming`)
- **Кто может:** пути от внешнего ввода сейчас нет — оба вызывающих `CreateApp`
  (`api.go:254`, `web.go:230`) валидируют имя до вызова, а `mustApp` защищён тем, что в
  таблице лежат только валидные имена
- **Чем грозит:** до волны 5 нарушение этого инварианта означало бы кривой путь при чтении;
  теперь оно означает `os.RemoveAll` по этому пути. `api.mustApp` — единственный вход, где
  имя из URL не проходит `naming` вовсе (UI-аналог `web.loadApp`, `web.go:246-251`,
  проверку делает), и держится он исключительно на том, что `CreateApp` никто не вызовет
  без валидации. Это не уязвимость сегодня, а мина под будущее изменение — ровно та
  категория, что и S8 прошлого круга.
- **Как чинить:** симметрично `UpdateApp` — вызвать `naming.ValidateAppName` в
  `store.CreateApp`; в `api.mustApp` валидировать `r.PathValue("name")` до похода в БД
  (невалидное имя → 404, как в `web.loadApp`).
- **Как проверить:** юнит `store.CreateApp("../x", "")` → ошибка; `GET /api/apps/..%2Fx` →
  404 без обращения к БД (существующие тесты API остаются зелёными).

## Проверенное и чистое

- **Рубеж `naming` на всех входах деструктивных операций.** Проверено эмпирически через
  API: имена `.`, `..`, `.tmp`, `/`, пустая строка, `latest`, `a/b` отвергаются с 400 на
  создании и не могут появиться в БД; `%2F` в path-параметре ServeMux даёт имя, которого
  нет в таблице, → 404. Регулярка `naming.go:15` заякорена, и в Go `$` без флага `m`
  означает конец текста — трюк с завершающим `\n` не проходит; NUL и управляющие символы
  не входят в класс символов. Версия обязана быть каноническим semver, `files`
  дополнительно требует `canon == version` (`files.go:56-58`), поэтому `1.0.0/../..`
  отбивается дважды. Удалить корень data-dir пустым именем нельзя: пустая строка не
  проходит регулярку, и `filepath.Join(Root, "")` недостижим.
- **Валидация до касания ФС.** Во всех четырёх хендлерах порядок «проверить → БД → ФС»
  соблюдён: `web.loadApp` валидирует имя до `GetApp`; `naming.ValidateVersion` вызывается
  до `GetVersion` и до `RemoveVersion`; `files.RemoveApp/RemoveVersion/RenameApp`
  валидируют повторно первым делом (`files.go:139-146,168-170,177-179`).
- **Переименование ничего не перезаписывает.** `RenameApp` отказывается, если цель
  существует (`files.go:152-156`), и это проверено на живом сервисе: `PATCH` с
  переименованием в `apprepo.db` даёт 409 и откатывает строку — ни файл БД, ни чужой
  каталог не пострадали, в том числе в случае «у приложения ещё нет каталога».
- **Авторизация новых маршрутов.** Перечислены все `mux.Handle*` в проекте: три новых
  UI-маршрута (`web.go:67-70`) обёрнуты `RequireSession(csrf(...))`, два новых API-маршрута
  (`api.go:40-41,45`) зарегистрированы во вложенном `api`-муксе, который целиком висит за
  `json401(a.RequireBasic(...))` (`api.go:53`). Маршрутов мимо middleware нет; открыты
  по-прежнему только `GET /healthz`, `GET /login`, `POST /login`. Покрыто тестом
  `TestUnauthorizedMutations` (`internal/api/api_t13_test.go:242`) и `TestEditDeleteCSRF`
  (`internal/web/web_test.go:620`).
- **CSRF на новых POST.** Все три новых UI-маршрута идут через middleware `csrf`
  (`web.go:99-107`, сравнение `subtle.ConstantTimeCompare`). Обход через `multipart` или
  `text/plain` не работает: `ParseForm` в этих случаях не наполняет `PostForm`, токен
  пустой → 403. Шаблон кладёт `csrf_token` во все три новые формы (`app.html`).
- **Подтверждение удаления приложения.** `web.go:499` сравнивает `confirm` с `app.Name`
  строгим `!=`; обойти пустым значением, другим Content-Type или отсутствием поля нельзя
  (`PostFormValue` вернёт `""`). Это UX-барьер, а не граница безопасности, и как барьер он
  корректен; в API подтверждения нет — так и задумано контрактом.
- **Компенсация при неудачном переименовании.** И в API (`api.go:317-327`), и в UI
  (`web.go:478-488`) сбой `RenameApp` откатывает строку обратно вместе с описанием, а
  неудачу отката пишет в лог отдельной строкой. Покрыто `TestPatchAppRenameRollback` и
  `TestEditAppRenameRevertsOnDiskFailure`.
- **Утечка внутренних текстов ошибок.** Инвариант о генеричных 500 в волне не нарушен:
  все новые 500-ветки идут через `internalErr` (`api.go:73-76`) и `web.serverError`
  (`web.go:149-152`) — путь ФС попадает только в серверный лог. Обёртки вида
  `fmt.Errorf("remove files of app %s: %w", …)` (`web.go:510,540`) уходят именно в лог, а
  клиент получает фиксированное «internal server error» — проверено чтением `serverError`.
  В теле ответов остались только 4xx с пользовательским вводом (`invalid_name`,
  `invalid_version`), как и решено в круге 2.
- **Секреты в логах.** Новые `log.Printf` волны (три штуки) содержат только имена
  приложений и текст ошибки; паролей, хешей, токенов сессий и Basic-кредов в них нет.
- **XSS в новом шаблоне.** `app.html` использует только автоэкранирование `html/template`,
  `template.HTML` не появился; подстановки в `onclick="…getElementById('del-{{.V.Version}}')"`
  и в `action="/apps/{{$.App.Name}}/…"` идут в JS- и URL-контексты, которые `html/template`
  экранирует сам, а значения к тому же ограничены каноническим semver и регуляркой имени.
  Тексты ошибок (`err.Error()` от `naming`) рендерятся через `{{.Error}}` в
  `layout.html` — экранируются.
- **Удаление версии во время скачивания.** `api.download` открывает файл (`api.go:576`) и
  отдаёт его через `http.ServeContent` из уже открытого дескриптора; на Linux `unlink`
  параллельного удаления не рвёт активную отдачу — скачивание завершится целым файлом.
  Гонка «удаление версии ↔ загрузка той же версии» безопасна: публикация файла — это
  эксклюзивный `os.Link` (фикс S2 прошлого круга), а `RemoveVersion` работает по каталогу
  версии; худший исход — 409 или 404 у одной из сторон, перезаписи нет.
- **Каскады в БД.** `DeleteApp` опирается на `ON DELETE CASCADE` для `versions` и
  `ON DELETE SET NULL` для `apps.latest_override_version_id` (`schema.sql`), PRAGMA
  `foreign_keys(1)` включена в DSN (`store.go:87`) — висячих ссылок после удаления не
  остаётся; покрыто `TestDeleteVersionClearsOverride`.
- **SQL.** Все запросы волны параметризованы (`store.go:275,289,402`), конкатенируются
  только константные списки колонок.
- **Зависимости.** `git diff develop..HEAD -- go.mod go.sum` пуст — новых зависимостей и
  смены версий волна не вносит.
- **Сборка и тесты.** `go build ./...`, `go vet ./...`, `go test ./...` на `4cbec24` —
  зелёные (восемь пакетов с тестами, `cmd/apprepo` и `internal/app` тестов не имеют).
