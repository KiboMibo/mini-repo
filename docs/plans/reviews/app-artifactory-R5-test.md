## Находки

### 1. Удаление приложения с именем файла БД сносит саму БД — блокирующая

- **Где:** `internal/files/files.go:174-180` (`RemoveApp`), вызывается из
  `internal/api/api.go:345` (`deleteApp`) и `internal/web/web.go:509` (`deleteApp`)
- **Суть:** `RemoveApp` проверяет только `naming.ValidateAppName(app)` и сразу
  делает `os.RemoveAll(filepath.Join(st.Root, app))`. Регулярка имени
  (`^[a-zA-Z0-9][a-zA-Z0-9._-]{0,63}$`) разрешает точку и дефис, а `Storage.Root`
  в `app.New` — это `cfg.DataDir`, где по дефолту (`DBPath = {data-dir}/apprepo.db`)
  лежит и сама база. Приложение можно создать с именем `apprepo.db`,
  `apprepo.db-wal` или `apprepo.db-shm` — и удалить.
- **Чем грозит:** тихая полная потеря данных. `DELETE /api/apps/apprepo.db`
  отвечает **204**, файл БД отвязывается. Работающий процесс держит открытый
  inode и продолжает отвечать как ни в чём не бывало — расхождение
  обнаружится только при рестарте, когда `store.Open` создаст пустую базу:
  исчезнут все пользователи, сессии, приложения и версии, при том что бинарники
  останутся лежать на диске сиротами. Тот же путь доступен из UI
  (`POST /apps/apprepo.db/delete` с корректным `confirm`). Для эксплуатации
  достаточно обычной учётки — отдельных прав на это нет.
- **Асимметрия, подтверждающая, что это недосмотр, а не решение:**
  соседний `RenameApp` (`files.go:150-153`) ровно от этого и защищается —
  `os.Lstat(dst)` и отказ `ErrFileExists`. Переименование в `apprepo.db` честно
  отдаёт 409 (`TestRenameOntoAnExistingDirectoryIs409`), удаление — нет.
- **Предлагается:** в `RemoveApp` перед `os.RemoveAll` убедиться, что путь либо
  не существует, либо является каталогом:

  ```go
  p := filepath.Join(st.Root, app)
  if fi, err := os.Lstat(p); err == nil && !fi.IsDir() {
      return fmt.Errorf("refusing to remove %s: not an app directory", p)
  }
  return os.RemoveAll(p)
  ```

  Этого достаточно, чтобы закрыть потерю данных, и весь набор становится зелёным
  (проверено на копии). Дополнительно стоит обдумать: (а) при таком отказе строка
  приложения из БД уже удалена — хендлер ответит 500, а приложение из БД пропадёт,
  так что запрет разумно поднять выше, до `store.DeleteApp`; (б) более
  фундаментальное — не держать БД внутри корня файлового хранилища либо
  запрещать имена, совпадающие с содержимым data-dir, ещё на создании
  приложения (`POST /api/apps`).
- **Тест:** `internal/integration/r5_guard_test.go` →
  `TestDeleteAppNamedLikeTheDatabaseFile` (падает, 2 подтеста)

### 2. Переименование во время стриминга загрузки оставляет строку без файла — важная

- **Где:** `internal/api/api.go:474-533` (`putVersion`) против
  `internal/api/api.go:288-331` (`updateApp`)
- **Суть:** `putVersion` резолвит приложение (`mustApp`) в начале запроса и
  дальше пользуется снимком `a.Name`. Если переименование проходит, пока
  `files.Save` ещё читает тело, `Save` после дочитывания делает
  `os.MkdirAll` по **старому** имени (пересоздавая только что переехавший
  каталог) и публикует туда файл, а `CreateVersion` пишет строку для
  приложения, которое уже называется по-новому.
- **Чем грозит:** нарушается главный инвариант хранилища — строка в БД
  указывает на несуществующий файл. `GET /download/{new}/{version}` отдаёт 500,
  на диске остаётся осиротевший каталог со старым именем. Данные не портятся,
  но версия становится нескачиваемой и чинится только руками.
- **Статус:** фиксирую как **наблюдение, а не как требование** — исполнители
  T12–T14 честно отметили эту гонку как известную шероховатость, и тест её не
  требует, а протоколирует. В отчёт вынесено потому, что теперь есть
  детерминированное воспроизведение: тест синхронизируется на появлении
  временного файла в `{data-dir}/.tmp` (а не на `sleep`), поэтому чередование
  повторяется стабильно — в 3 из 3 прогонов ровно 1 висячая строка и 1
  осиротевший каталог.
- **Предлагается:** решать не в рамках волны 5. Варианты для отдельной задачи:
  перечитывать имя приложения по `a.ID` после `Save` и до `CreateVersion`
  (и переносить файл, если имя уехало), либо брать на время загрузки
  разделяемую блокировку по `app_id`, которую переименование берёт
  эксклюзивно.
- **Тест:** `internal/integration/r5_guard_test.go` →
  `TestRenameWhileUploadIsStreamingObserved` (проходит, поведение в логе);
  «естественная» версия той же гонки — `TestConcurrentRenameAndUploadObserved`
  (в 12 прогонах висячих строк не дала: окно слишком узкое на маленьком теле)

### 3. Пустой каталог приложения остаётся после удаления последней версии — замечание

- **Где:** `internal/files/files.go:182-189` (`RemoveVersion`)
- **Суть:** `Remove` (откат неудачной вставки) подчищает опустевший каталог
  версии (`files.go:128`), а `RemoveVersion` каталог приложения не подчищает.
  После удаления единственной версии на диске остаётся пустой `{data-dir}/{app}/`.
- **Чем грозит:** ничем содержательным — приложение живо, инвариант не нарушен,
  каталог для живого приложения даже уместен. Отмечаю ради полноты картины:
  раскладка на диске после удаления последней версии не совпадает с раскладкой
  до первой загрузки (там каталога ещё нет), и тесты, которые это сравнивают,
  об этом должны знать.
- **Предлагается:** ничего не делать либо привести к одному поведению при
  следующем касании файла.
- **Тест:** зафиксировано в `TestDeleteLastVersionLeavesAppAlive` (проходит;
  проверяется исчезновение каталога версии, каталог приложения не требуется)

## Допущения

Вызов делегированный, спрашивать некого — решения приняты самостоятельно:

1. **Дефект оставлен красным, а не помечен `t.Skip`.** По умолчанию скилла
   красный набор — это и есть сообщение «есть незакрытый дефект». Общего CI,
   который бы блокировал соседние задачи, здесь нет (remote нет, R5-sec пишет
   только отчёт), поэтому прятать падение не за чем.
2. **Гонка «переименование + загрузка» оформлена как наблюдение** (находка 2,
   тест проходит) — согласно постановке задачи и отчётам T12–T14, где она
   отмечена как известная шероховатость. Если это считать требованием, статус
   не изменится: он и так `FAIL` из-за находки 1.
3. **Приемлемым исходом гонки «удаление + скачивание»** считал любой из
   200 / 404 / 500 при условии, что нет паники, обрыва соединения и
   недочитанного тела. Наблюдалось 200 и 404 (200 — чтение уже отвязанного
   inode, что для POSIX нормально).
4. **Инвариант хранилища проверяю только в одну сторону как требование**
   («нет строк без файлов»). Обратное направление — «нет файлов без строк» —
   проверяю как наблюдение (`orphanDirs`), потому что осиротевший каталог
   безвреден и авторы волны сознательно предпочли его висячей строке
   (комментарии в `api.go:288-296` и `web.go:454-457`).
5. **Пустой каталог приложения после удаления последней версии** признан
   допустимым (находка 3, замечание) — приложение живо, каталог для него уместен.
6. **Порог покрытия 80% взят (82.5%)**, недобранные 17.5% — исключительно
   500-ветки, недостижимые без внедрения отказа в продакшн-код. Натягивать
   их тестами-пустышками не стал; полный перечень с причинами — в разделе
   «Покрытие».
7. **Имя `apprepo.db` для приложения** считаю достижимым в проде, а не
   искусственным: `POST /api/apps` его принимает, а дефолтная конфигурация
   (`DBPath = {data-dir}/apprepo.db`, `Storage.Root = DataDir`) — та, что
   описана в `CLAUDE.md` и `deploy/apprepo.env.example`. Если БД вынесена за
   data-dir через `APPREPO_DB`, конкретно этот вектор закрывается, но
   `RemoveApp` остаётся без проверки типа пути — тест в этом случае сам себя
   скипает (`t.Skipf`).
