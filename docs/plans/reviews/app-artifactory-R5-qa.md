### Важные

**В1. Переименование во время загрузки оставляет строку версии без файла** —
`internal/api/api.go:522-589` (`putVersion`), тот же дефект в
`internal/web/web.go:379-416` (`saveUpload`).

*Что не так.* `putVersion` захватывает `a.Name` в начале запроса и передаёт это
имя в `files.Save`. Если `PATCH` с переименованием проходит, пока `Save` ещё
стримит тело, `Save` заново создаёт `MkdirAll` каталог под **старым** именем и
публикует файл туда, а `CreateVersion` вставляет строку приложению, которое уже
называется по-новому. Рубеж F9 здесь не помогает: он проверяет тип каталога
один раз, до чтения байтов, когда старый каталог ещё на месте.

*Воспроизведено на живом сервисе, детерминированно:* `PUT …/slow/versions/2.0.0`
с `--limit-rate 40k` (400 КБ), через 2 с — `PATCH slow → slow2`. Итог:
`PUT` → `201` с `download_url`, указывающим на несуществующее уже `/download/slow/2.0.0`;
`GET /api/apps/slow2/versions` показывает `2.0.0`; файл лежит в `data/slow/2.0.0/`,
а `GET /download/slow2/2.0.0` отдаёт **`500`**.

*Чем грозит.* Нарушен инвариант, который волна декларирует явно («строка,
указывающая на несуществующий каталог, хуже осиротевшего каталога», `api.go:311-313`):
получается ровно висячая строка. Версия видна в списке и в UI, но не
скачивается — постоянный `500` до ручного вмешательства. Побочно в data-dir
остаётся лишний каталог со старым именем, который затем **блокирует
переименование обратно в это имя** (`409 already_exists` — проверил). Чинится
только руками: удалить версию, залить заново (проверил — помогает), затем
убрать осиротевший каталог с диска.

*Предлагается.* Отдельной задачей вне волны 5 (как и рекомендовал R5-test):
перечитывать имя приложения по `a.ID` после `Save` и до `CreateVersion` и
переносить файл, либо ввести блокировку по `app_id` — разделяемую на загрузку,
эксклюзивную на переименование. До исправления ограничение задокументировано в
`docs/api.md` (врезка в разделе `PATCH /api/apps/{name}`).

*Статус.* Не регрессия волны, а известная находка R5-test (`findings[1]`,
`internal/integration/r5_guard_test.go › TestRenameWhileUploadIsStreamingObserved`),
принятая как наблюдение. Подтверждаю: дефект реальный и достижим по HTTP
обычной учёткой. Волну не блокирую — окно узкое и требует конкурентности, — но
из «отложенных» этот пункт терять нельзя.

**В2. На одну и ту же ошибку UI отвечает 500, а API — 409** —
`internal/web/web.go:507-524` (`editApp`).

*Что не так.* `files.ErrFileExists` (каталог с целевым именем уже есть на диске,
но строки в БД нет) в API разобран отдельной веткой и даёт `409 already_exists`
«app directory already exists» (`api.go:352-355`). В UI такой же случай
проваливается в общий хвост и даёт `500` «could not rename files on disk, the
application was left unchanged». `files.ErrNotDirectory` при этом в UI разобран
корректно — пропущена только одна из двух ветвей.

*Воспроизведено:* каталог `data/ghost/` без строки в БД (ровно то, что остаётся
после В1 или после `DELETE`, где чистка диска не удалась), затем переименование
`movable` → `ghost`: API — `409`, UI — `500`. Откат имени в БД в обоих случаях
отработал, данные целы.

*Чем грозит.* Пользовательская коллизия, которую человек может разрешить сам,
выглядит как отказ сервера: 5xx в мониторинге и логах, оператор идёт искать
сбой; в тексте ошибки нет ни слова о том, что имя занято на диске. Плюс два
интерфейса к одной доменной операции расходятся в контракте.

*Предлагается.* В `web.editApp` добавить ветку, симметричную `api.updateApp`:
`errors.Is(err, files.ErrFileExists)` → `renderAppIn(w, r, app, http.StatusConflict,
"edit", "a directory with that name already exists on disk")`.

**В3. `scripts/smoke.sh` не знает про волну 5** — `scripts/smoke.sh:45-91`.

*Что не так.* Сквозной сценарий заканчивается на latest/скачивании: `PATCH`,
`DELETE` версии и `DELETE` приложения в нём нет. Волна добавила три маршрута в
API и три в UI и не тронула smoke.

*Чем грозит.* Smoke — единственная проверка на **собранном бинарнике**: всё
остальное гоняется через `httptest` внутри процесса. Регрессия в новых
маршрутах на реально запущенном сервере ничем автоматическим не ловится — её
поймает только следующий ручной прогон вроде этого.

*Предлагается.* Дописать в конец, перед graceful shutdown, блок: `PATCH`
переименования, проверка `200` на `/download/{новое}/…` и `404` на
`/download/{старое}/…`, `DELETE` версии + `[ ! -e "$DATA/{app}/{version}" ]`,
`DELETE` приложения + `[ ! -e "$DATA/{app}" ]`, повторный `DELETE` → `404`.
Файл принадлежит не QA — оформить задачей.

## Рекомендации

1. Завести задачу на В1 (гонка переименования и загрузки) — это единственная
   находка, которая портит данные пользователя, пусть и в узком окне. До
   исправления ограничение описано в `docs/api.md`.
2. Закрыть В2 одной веткой `errors.Is(err, files.ErrFileExists)` в
   `web.editApp` — правка на три строки, убирает 5xx на пользовательской
   коллизии и выравнивает UI с API.
3. Дописать волну 5 в `scripts/smoke.sh` (В3): без этого новые маршруты не
   проверяются ни одной автоматической проверкой на собранном бинарнике.
4. Обновить доску `docs/plans/state/app-artifactory-status.md` до волны 5 —
   сейчас она вводит в заблуждение любого, кто придёт в проект после.
5. Мелочь для следующего касания файлов: ранний выход в `web.editApp` при
   отсутствии изменений и единообразие с `files.Remove` в вопросе подчистки
   опустевших каталогов.
