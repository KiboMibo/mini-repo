## Резюме

Сценарий пользователя — распространение многофайловых приложений архивами —
проверен на собранном бинарнике целиком, а не по отчётам. Собран настоящий
многофайловый релиз (`bin/run.sh` + 200 KB бинарных данных + `conf/app.conf` +
`README.txt`), упакован в `.tar.gz` и `.zip`, залит через API и через UI-форму,
скачан, распакован и сверен **пофайлово** по sha256. Расхождений нет: архив
возвращается байт в байт, права на файлы внутри переживают круг-трип.

Ломающее изменение проверено в его настоящей постановке: **собран бинарник
до T23** (`git archive f2f722f`), им создана легаси-установка, где архив лёг под
старым умолчательным именем `myapp-1.1.0` — то есть без расширения, ровно та
болезнь, ради которой дефолт убрали. Затем на этом же data-dir поднят новый
бинарник: **легаси-версии скачиваются под прежними именами, байт в байт**,
миграции и перезаливки не требуют.

Отдельно проверено то, ради чего писался текст ошибки: строка `curl` из тела
`400 filename_required` **скопирована из вывода и выполнена буквально** — она
работает и даёт `201`. Отказ действительно чинится по своему тексту.

Блокирующих находок нет. Одна важная: **NUL-байт в `?filename=` даёт `500`
вместо `400`** — единственное место, где пользовательский ввод в этой области
уходит в «внутреннюю ошибку». Данные при этом не теряются и система
восстанавливается сама.

`go test -count=1 ./...`, `go vet ./...` и `bash scripts/smoke.sh` — зелёные.

## Находки

### 1. NUL-байт в `?filename=` даёт `500` вместо `400` — важная

**Где:** `internal/naming/naming.go:129` (`ValidateFilename`), проявляется в
`internal/api/api.go:611` → `internal/files/files.go` (`Commit` → `os.Link`).

**Что не так.** `ValidateFilename` не отвергает управляющие символы. NUL проходит
валидацию, тело выкачивается целиком, а падает уже файловая система:

```
PUT /api/apps/myapp/versions/3.1.0?filename=a%00b.tar.gz
→ 500 {"error":"internal","message":"internal error"}
лог: link …/.tmp/upload-1311105650 …/myapp/3.1.0/a b.tar.gz: invalid argument
```

**Чем грозит.** Клиентская ошибка приезжает как «внутренняя»: в журнале это
выглядит сбоем сервиса, а не негодным запросом, и в мониторинге неотличимо от
настоящей поломки. Ровно тот класс, который проект уже закрыл для пароля
(`MaxPasswordBytes` заведён с комментарием «без проверки это 500 на
пользовательском вводе») и для имени файла — но только для пустого и
пробельного. Тело при этом выкачивается целиком до отказа: на 2-гигабайтном
архиве это 2 ГБ трафика и диска ради `500`.

**Границы (проверено).** Данные не теряются и не портятся: версия в БД не
создаётся (`GET` → `404`), временный файл убирается, `.tmp` пуст. Пустой каталог
версии, оставшийся после неудачного `os.Link`, **не мешает** — повторная заливка
той же версии с нормальным именем даёт `201`. Traversal невозможен (NUL не
разделитель пути), инъекции в заголовок нет. UI-путь на том же вводе отдаёт
`400`, а не `500` — расходится только API.

**Что предлагается.** Отвергать управляющие символы в `ValidateFilename` рядом с
проверкой на пробельное имя — тем же `invalid_filename` (400). Это одна строка
в единственной точке валидации, и она чинит оба интерфейса разом. Дефект
не внесён волной 7 (`ValidateFilename` и чтение имени из query существовали
до T23), но лежит ровно в переписанном ею пути и найден на приёмке этой волны.

### 2. `smoke.sh` не проверяет ключевой сценарий волны — архивы — замечание

**Где:** `scripts/smoke.sh`.

**Что не так.** Скрипт проверяет обязательность `?filename=` (в том числе пустое
значение и самодостаточность текста отказа) — это хорошо и добавлено вовремя.
Но заливает он `printf 'binary-one'`, то есть десяток байт, и ни одного архива:
сквозной сценарий «многофайловый релиз ушёл и вернулся целым» в smoke не
представлен. Пробельное значение (`?filename=%20`) — правка F18 — тоже не
проверяется.

**Чем грозит.** Smoke — это то, что гоняют перед выкаткой вместо полного набора.
Он останется зелёным, если сломается именно то, ради чего делалась волна.
В `internal/integration/r7_archive_test.go` сценарий покрыт хорошо, так что
дыра не в покрытии, а в быстрой предвыкаточной проверке.

**Что предлагается.** Добавить в `smoke.sh` два шага: заливку `.tar.gz` с
несколькими файлами внутри со сверкой sha после скачивания и `?filename=%20` в
список отказов рядом с уже существующим `?filename=`.

### 3. Одна и та же ошибка ФС даёт `400` в UI и `500` в API — замечание

**Где:** `internal/web/web.go:550` (default → `400 «upload failed»`) против
`internal/api/api.go` (`uploadErr` default → `internalErr` → `500`).

**Что не так.** Нераспознанная ошибка публикации в UI объявляется клиентской
(`400`), в API — серверной (`500`). На NUL-имени это видно прямо: UI `400`,
API `500`.

**Чем грозит.** Само по себе безобидно (тексты в обоих случаях без внутренних
подробностей, путь ФС уходит только в лог), но `400 «upload failed»` в UI
скрывает настоящие сбои сервера от мониторинга: реальная поломка диска покажется
ошибкой пользователя. Инвариант «одна операция — одно право в обоих интерфейсах»
в CLAUDE.md есть, аналогичного про коды ошибок — нет.

**Что предлагается.** Решение оставить за архитектурой пары `api`/`web` (в
CLAUDE.md уже зафиксировано, что `api.userWriteErr` и `web.userWriteErr` —
пара, коды обязаны совпадать; здесь такой пары нет). Как минимум — зафиксировать
осознанность расхождения комментарием.

## Что обновлено в документации

Сверялось по коду (`internal/api/api.go`, `internal/web/templates/app.html`,
`internal/naming/naming.go`, `internal/config/config.go`), а не по отчётам задач.

**`docs/api.md`**

- Таблица кодов: `filename_required` теперь покрывает **пробельное** значение
  (было «нет параметра или он пустой» — формулировка, которую F18 отметил как
  неполную); `invalid_filename` уточнён как «передан и непробельный, но не
  basename».
- Описание `?filename=`: добавлены обрезка краёв перед проверкой, законность
  пробелов **внутри** имени и разбор трёх случаев, дающих `filename_required`,
  с объяснением, почему пробельное значение — не придирка (`?filename=$ARTIFACT`
  с незаданной переменной в CI).
- Раздел «Совместимость» переписан по пунктам: **что сломается** (клиент без
  параметра получает `400` и версию не создаёт, отказ до чтения тела), **как
  распознать** (`filename_required`, тело содержит готовый `curl`), **как
  чинится** (один параметр; прежнее имя можно передать явно), **чего изменение
  не касается** (залитые версии, `/download`, UI-загрузка).

**`README.md`**

- Новый раздел **«Многофайловые приложения (архивы)»**: версия — ровно один файл
  любого содержания; архив хранится и отдаётся байт в байт; обязательность имени
  с расширением и почему это критично именно на архивах; примеры заливки
  `.tar.gz` через API (`?filename=`) и через UI (имя берётся из выбранного
  файла); прямо сказано, что **сервис архивы не распаковывает, внутрь не
  заглядывает, список файлов не показывает и отдельный файл из архива скачать
  нельзя**; SHA-256 сверяет архив целиком. Раздел о размере: `APPREPO_MAX_UPLOAD`
  (2 GiB по умолчанию) в контексте больших сборок, поведение при превышении в
  обоих интерфейсах, как поднять лимит, потоковость загрузки.
- Раздел «Веб-UI» дополнен **прогрессом загрузки**: полоса, процент и объём,
  кнопка отмены, смена надписи на «finishing on the server…» после ухода тела,
  честный текст при обрыве после отправки; отдельно сказано, что это
  прогрессивное улучшение и **без JavaScript форма работает как раньше**.
- Вводный абзац: версия — один файл, бинарник или архив.
- «Обновление существующей установки»: ломающее изменение вынесено наверх
  раздела — что сломается, как чинится, что уже залитые версии не затронуты,
  что UI не затронут, и совет пройтись по пайплайнам до обновления.
- В примеры curl добавлена заливка архива и пометка, что `?filename=` обязателен.

**`CLAUDE.md`**

- Новый инвариант: `?filename=` обязателен, значение **обрезается до** проверки
  на пустоту; зафиксирован порядок `TrimSpace → filename_required →
  ValidateFilename → invalid_filename`, запрет возвращать умолчательное
  `{app}-{version}`, законность пробелов внутри имени и требование к тексту
  `filename_required` оставаться самодостаточным (он уходит в лог CI).
- Инвариант о порядке частей multipart дополнен: порядок держится **разметкой
  формы** в `app.html`, а `FormData` обходит поля в порядке разметки, поэтому у
  XHR порядок частей тот же; второго места, где он задаётся, нет.
- Новый инвариант про inline-скрипт: никаких внешних ресурсов и CDN, форма
  обязана оставаться рабочей без JS, скрипт не вправе обещать «ничего не
  сохранено» после ухода тела и переходить может только по своему origin.

**Проверка на расхождения после четырёх задач.** Сверены все зарегистрированные
маршруты с `docs/api.md` — задокументированы все 19 (`/api/*` и `/download`),
пропусков нет. Переменные окружения в коде и в документации совпадают
(`APPREPO_ADDR`, `DATA_DIR`, `DB`, `BASE_URL`, `MAX_UPLOAD`, `PASSWORD`).
Устаревших утверждений о необязательности `?filename=` в документации не
осталось. Утверждение README о потоковой загрузке сверено с `files.Prepare`
(`io.Copy` + `io.TeeReader` во временный файл) — верно.

**Готово с замечаниями.**

Заявленное волной сделано и работает на собранном сервисе: архивы ходят через

До релиза стоит закрыть находку 1 (`500` на NUL в имени файла) — она дешёвая,
чинится одной строкой в единственной точке валидации, и это единственное место
в области волны, где пользовательский ввод выглядит сбоем сервиса. Находки 2 и 3
можно взять в следующую волну.
