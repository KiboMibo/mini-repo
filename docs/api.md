# apprepo — HTTP API

Описание сверено с кодом `internal/api/api.go`, `internal/api/users.go`,
`internal/auth/auth.go`, `internal/auth/roles.go`, `internal/naming/naming.go` и
`internal/platform/platform.go` (волна 6 с исправлениями F12–F15, волна 7 и
волна 8: роли и права, управление учётками, правила имени и пароля, строгий
`Content-Type`, обязательный `?filename=` при заливке версии, платформа
версии). Все примеры — рабочие curl-команды: каждая прогнана на собранном
сервисе, а не написана по памяти.

## Аутентификация

Все маршруты `/api/…` и `/download/…` требуют **HTTP Basic Auth**. Анонимного
доступа нет. Учётки заводятся из CLI (`apprepo user add <name> -role <role>`),
через API (`POST /api/users`) или в веб-интерфейсе (`/users`).

Без корректных кредов — `401` с заголовком `WWW-Authenticate: Basic realm="apprepo"`
и JSON-телом (в том числе для `/download/…`):

```json
{"error":"unauthorized","message":"authentication required"}
```

Заблокированная учётка (`disabled`) неотличима от неверного пароля: тот же `401`.
Блокировка действует немедленно — сессии пользователя удаляются, а следующий
запрос по Basic Auth уже не проходит.

Имя учётки — `^[a-zA-Z0-9][a-zA-Z0-9._-]{0,63}$`, пробелы по краям обрезаются;
это одно и то же правило (`naming.NormalizeUsername`) при создании и при поиске,
во всех трёх интерфейсах. Двоеточие запрещено не из вкусовщины: Basic кодирует
пару как `user:password`, поэтому учётка с двоеточием в имени не смогла бы войти
по Basic никогда. В базе, пережившей обновление со старой версии, такие имена
ещё могут встретиться — см. раздел «Обновление существующей установки» в README.

> Basic Auth передаёт пароль в открытом виде — в проде сервис обязан стоять
> за reverse-proxy с TLS (см. README).

### Требования к паролю

Одна политика на все три интерфейса (API, веб-интерфейс, CLI): **от 8 до 72
байт**. Нижняя граница — потому что ограничения частоты входа нет и цена
перебора равна стоимости bcrypt; верхняя — предел bcrypt, который длинный вход
отвергает, а не обрезает. Других требований (классы символов, словари,
несовпадение с именем) нет намеренно.

Нарушение — всегда **`400 validation`** с человеческим текстом в `message`
(`password must be at least 8 bytes, got 5`), а не `500`. Проверка стоит на
всех маршрутах, задающих пароль: `POST /api/users`,
`POST /api/users/{username}/password`, `POST /api/me/password` — и на их
аналогах в UI и в `apprepo user add` / `apprepo user password`.

## Роли и права

У каждой учётки ровно одна **глобальная роль**. Роль читается из БД на каждом
запросе: смена роли действует немедленно, перелогин не нужен.

Роли по возрастанию полномочий: `deployer` < `developer` < `maintainer` < `admin`.

| Право | Что открывает | `deployer` | `developer` | `maintainer` | `admin` |
|---|---|:---:|:---:|:---:|:---:|
| `PermRead` | GET-запросы API и скачивание | ✔ | ✔ | ✔ | ✔ |
| `PermVersion` | залить/удалить версию, закрепить latest, проставить платформу | — | ✔ | ✔ | ✔ |
| `PermApp` | создать/переименовать/удалить приложение | — | — | ✔ | ✔ |
| `PermUserAdmin` | управление учётками | — | — | — | ✔ |
| `PermUI` | вход в веб-интерфейс | — | ✔ | ✔ | ✔ |

`deployer` — машинная учётка для CI и прямых ссылок: читает и качает по API,
но в веб-интерфейс не допускается вовсе (`PermUI` у роли нет). Свой пароль он
меняет через `POST /api/me/password` — это единственный доступный ему путь.

Матрица прав живёт в одном месте — `rolePerms` в `internal/auth/roles.go`;
маршруты навешивают право через `Auth.Require`.

### Маршрут → требуемое право

| Маршрут | Право |
|---|---|
| `GET /api/apps` | `PermRead` |
| `POST /api/apps` | `PermApp` |
| `GET /api/apps/{name}` | `PermRead` |
| `PATCH /api/apps/{name}` | `PermApp` |
| `DELETE /api/apps/{name}` | `PermApp` |
| `GET /api/apps/{name}/versions` | `PermRead` |
| `GET /api/apps/{name}/versions/{version}` | `PermRead` |
| `PUT /api/apps/{name}/versions/{version}` | `PermVersion` |
| `PATCH /api/apps/{name}/versions/{version}` | `PermVersion` |
| `DELETE /api/apps/{name}/versions/{version}` | `PermVersion` |
| `GET /api/apps/{name}/latest` | `PermRead` |
| `POST /api/apps/{name}/latest` | `PermVersion` |
| `GET /api/users` | `PermUserAdmin` |
| `POST /api/users` | `PermUserAdmin` |
| `PATCH /api/users/{username}` | `PermUserAdmin` |
| `POST /api/users/{username}/password` | `PermUserAdmin` |
| `DELETE /api/users/{username}` | `PermUserAdmin` |
| `GET /api/me` | — (любая роль) |
| `POST /api/me/password` | — (любая роль) |
| любой другой путь/метод под `/api/` | `PermRead` → `404 not_found` |
| `GET /download/{name}/{version}` | `PermRead` |
| `GET /healthz` | без аутентификации |

Закрепление latest намеренно требует `PermVersion`, а не `PermApp`: это про
релиз версии, а не про карточку приложения, и `developer` двигает latest и так
— заливка версии со старшим semver делает её latest автоматически.

`PATCH …/versions/{version}` (простановка платформы руками) требует того же
`PermVersion`, что заливка и удаление версии: кто выпускает версию, тот и правит
её метку. Отдельного права под платформу нет.

Нехватка права — `403`:

```json
{"error":"forbidden","message":"insufficient permissions"}
```

## Формат ошибок

Все ошибки API — JSON-объект `{"error":"<код>","message":"<текст>"}`.
Неизвестный путь или метод внутри `/api/` тоже отвечает JSON (`not_found`),
а не текстовым 404/405.

| Код | HTTP | Когда |
|---|---|---|
| `unauthorized` | 401 | нет/неверные креды Basic Auth; учётка заблокирована |
| `forbidden` | 403 | у роли нет требуемого права |
| `invalid_password` | 403 | неверный `current_password` в `POST /api/me/password` (отдельно от `forbidden`: это не нехватка права) |
| `validation` | 400 | битое JSON-тело запроса; имя учётки не проходит `^[a-zA-Z0-9][a-zA-Z0-9._-]{0,63}$` (пробелы по краям обрезаются до проверки); пароль вне 8–72 байт (в том числе пустой); неизвестная роль |
| `invalid_name` | 400 | имя приложения не проходит `^[a-zA-Z0-9][a-zA-Z0-9._-]{0,63}$` или равно `latest` |
| `invalid_version` | 400 | не strict semver (допускается префикс `v`) |
| `filename_required` | 400 | у `PUT …/versions/{version}` нет параметра `?filename=`, он пустой или состоит из одних пробельных символов (`?filename=%20`, `?filename=` + таб) — см. ниже: дефолта больше нет |
| `invalid_filename` | 400 | `?filename=` передан и непробельный, но это не имя файла: содержит управляющий символ (вся категория Unicode `Cc` — C0, `DEL`, C1), длиннее 255 байт, содержит `/` или `\`, равен `.` или `..` |
| `platform_required` | 400 | у `PUT …/versions/{version}` нет `?platform=`, и платформу не удалось прочитать из самого файла (архив, скрипт, машина вне словаря) — см. «Платформа версии» |
| `invalid_platform` | 400 | значение платформы не из словаря: `?platform=` у `PUT` или поле `platform` в теле `PATCH …/versions/{version}` |
| `platform_mismatch` | 409 | переданная платформа противоречит той, что прочитана из залитого файла; версия не создаётся |
| `not_found` | 404 | нет приложения/версии/маршрута; latest у приложения без версий |
| `already_exists` | 409 | дубль имени приложения, пары app+version или имени пользователя; **либо** путь в data-dir занят посторонним объектом (см. ниже); **либо** приложение переименовали/удалили во время загрузки |
| `last_admin` | 409 | операция оставила бы установку без единого активного администратора |
| `self_delete` | 409 | попытка удалить собственную учётку |
| `hash_mismatch` | 422 | клиентский `X-Checksum-Sha256` не совпал с содержимым |
| `too_large` | 413 | тело больше `-max-upload` (дефолт 2 GiB) |
| `unsupported_media_type` | 415 | непустое тело без `Content-Type: application/json` на маршруте, разбирающем JSON (см. ниже) |
| `internal` | 500 | внутренняя ошибка |

### 415 `unsupported_media_type`: тело обязано быть `application/json`

Маршруты, разбирающие JSON, принимают **только** `Content-Type:
application/json` (параметр `charset` допустим, регистр значения не важен).
Всё остальное — включая отсутствующий и неразбираемый заголовок — даёт **415**.
Тела в примерах ниже поэтому всегда отправляются с явным
`-H 'Content-Type: application/json'`.

Зачем: `/api/` защищён только Basic Auth — сессионной куки здесь нет, значит
`SameSite` не участвует и своей защиты от CSRF у API нет. Браузер, у которого в
кэше лежат Basic-креды к этому origin, приложит их к запросу со стороннего
сайта. Единственный барьер — preflight, а без него кросс-сайтовый запрос может
нести только `Content-Type` из CORS-safelist: отсутствующий, `text/plain`,
`application/x-www-form-urlencoded`, `multipart/form-data`. Тело при этом
произвольное (`fetch`/`sendBeacon` шлют любые байты), поэтому запрещать типы по
списку бесполезно — работает только требование `application/json`, которого в
safelist нет: запрос с ним требует preflight, а его сервис не проходит.

Исключений два, и оба важны для скриптов:

- **Пустое тело** заголовка не требует, поэтому `PATCH /api/apps/{name}` и
  `PATCH /api/users/{username}` без тела («ничего не менять») работают как
  прежде.
- **Загрузка бинарника рубежа не касается.** `PUT /api/apps/{name}/versions/{version}`
  принимает сырые байты, а не JSON, и разбором `Content-Type` не занимается
  вовсе: заливка с `--data-binary` без заголовка (или с любым другим значением)
  как работала, так и работает. Ломать существующие CI-пайплайны не пришлось.
  Скачивание (`GET /download/…`) и все `GET`-маршруты тела не имеют и рубежа
  тоже не видят.

Имя приложения в пути (`{name}`) проверяется тем же `naming.ValidateAppName` до
похода в БД, но невалидное имя даёт **404 `not_found`**, а не 400: такого
приложения не может существовать. 400 `invalid_name` возвращают только те
маршруты, где имя приходит в теле (`POST /api/apps`, `PATCH /api/apps/{name}`).

**То же правило у имени учётки в пути** (`{username}` в `/api/users/…`): оно
прогоняется через `naming.NormalizeUsername` (пробелы по краям обрезаются), и
негодное имя даёт **404 `not_found`**, а не 400 — завести такое имя нельзя,
значит и учётки с ним быть не может. `400 validation` про имя возвращает только
`POST /api/users`, где имя приходит в теле.

Исключение: `GET /download/…` отвечает на ошибки **plain text** (кроме 401 от
middleware, который JSON). Невалидная строка версии в download-пути даёт 404
(«version not found»), а не 400.

### 409 `already_exists`: не только дубли

С волны 5 тот же код возвращается, когда **путь в data-dir занят посторонним
объектом** — не каталогом приложения. Data-dir хранит не только каталоги
приложений: рядом лежат файл БД `apprepo.db`, его `-wal`/`-shm` и служебный
`.tmp`. Регулярка имени (`^[a-zA-Z0-9][a-zA-Z0-9._-]{0,63}$`) разрешает точку и
дефис, поэтому имя вроде `apprepo.db-wal` проходит валидацию и указывает на
чужой файл; в `{data-dir}/{app}` может оказаться и подложенный симлинк.

Поэтому каждая мутирующая операция `internal/files` (запись, перенос, удаление)
проверяет **тип** цели, а не только её имя (`os.Lstat`; симлинк каталогом не
считается). Если по пути лежит что-то, кроме настоящего каталога, операция
отказывается и **на диске ничего не трогает** — это `409 already_exists` с
`message`, который начинается на `storage path is not an application directory`:

| Операция | `message` |
|---|---|
| `PUT /api/apps/{name}/versions/{version}` | `…, nothing was written to disk` |
| `PATCH /api/apps/{name}` (переименование) | `…, nothing was renamed on disk` |
| `DELETE /api/apps/{name}`, `DELETE …/versions/{version}` | `…, nothing was removed from disk` |

Сам путь клиенту не отдаётся — он уходит только в серверный лог. Отсутствие
каталога ошибкой не считается: у приложения без версий каталога ещё нет.

Практическое следствие: 409 на `DELETE` означает **не** «ничего не удалилось».
Строка в БД к этому моменту уже удалена (порядок «БД → диск», см. ниже), не
удалось только вычистить диск; повторный `DELETE` вернёт уже `404`. Такой ответ
— сигнал оператору разобрать data-dir руками, а не клиенту повторить запрос.

### Идемпотентность удаления

- Повторный `DELETE` того, чего уже нет, возвращает `404 not_found`, а не 500 и
  не 204: маршрут сначала резолвит объект в БД.
- На уровне диска удаление идемпотентно: отсутствующий каталог — не ошибка.
  Если каталог версии или приложения исчез мимо сервиса, `DELETE` всё равно
  отвечает `204` и просто убирает строку.
- `DELETE` приложения без версий (каталога на диске ещё нет) — тоже `204`.

## Объект версии

Один и тот же во всех ответах:

```json
{
  "version": "1.2.3",
  "filename": "myapp-linux-amd64",
  "size_bytes": 12345678,
  "sha256": "ab…ef",
  "platform": "linux/amd64",
  "created_at": "2026-08-06T12:00:00Z",
  "download_url": "http://repo.example.com/download/myapp/1.2.3",
  "is_latest": true
}
```

- `version` — канонический semver без префикса `v` (даже если заливали `v1.2.3`);
- `sha256` — hex в нижнем регистре, всегда посчитан сервером;
- `platform` — под что собран файл (см. «Платформа версии»); **поле есть всегда**,
  у версии с неизвестной платформой оно равно пустой строке, а не `null` и не
  отсутствует;
- `created_at` — RFC 3339, UTC;
- `download_url` — абсолютная ссылка от `-base-url`;
- `is_latest` — совпадает ли версия с текущим latest (учитывая закрепление).

## Платформа версии

`platform` отвечает на вопрос «под какую ОС и архитектуру собран этот файл».
Значение каноническое и хранится строкой; ни фильтрации по нему, ни выбора
версии по платформе в API пока нет — это метка, которую видно в объекте версии
и в веб-интерфейсе.

### Словарь допустимых значений

| Значение | Смысл |
|---|---|
| `os/arch` | обычная пара, например `linux/amd64`, `darwin/arm64`, `windows/386` |
| `any` | файл от ОС и архитектуры не зависит: jar, набор скриптов, набор конфигов |
| `darwin/universal` | macOS universal binary (fat Mach-O) — несколько срезов в одном файле |
| `""` (пустая строка) | неизвестно: версия залита до появления платформы либо её не удалось определить и никто не проставил руками |

Допустимые `os`: `linux`, `darwin`, `windows`, `freebsd`.
Допустимые `arch`: `amd64`, `arm64`, `386`, `arm`, `riscv64`, `ppc64le`, `s390x`.
Имена совпадают с `GOOS`/`GOARCH`, чтобы строку из репозитория можно было
подставить в скрипт сборки без перевода.

Значение **канонизируется**: регистр приводится к нижнему, пробелы по краям
обрезаются (`?platform=Linux%2FAMD64` и `?platform=linux/amd64%0A` дают
`linux/amd64`). Всё остальное — `400 invalid_platform`: голая архитектура
(`amd64`), пустая половина (`linux/`), третий элемент, неизвестное имя.

`any` и `darwin/universal` — особые. `any` **только проставляется руками**:
определить «независимость от платформы» по файлу нельзя, а выдавать «не
опознано» за «переносимо» значит врать. `darwin/universal`, наоборот, в
нормальной работе только определяется по файлу — но через API его принимает и
`?platform=`, и `PATCH`.

### Что определяется само, а что нет

Платформа читается **из самого файла** — из заголовка, по его формату
(`internal/platform`):

- **голый исполняемый файл** — ELF (Linux, FreeBSD), Mach-O (macOS), PE
  (Windows), включая fat Mach-O → `darwin/universal`;
- **архив** (`.tar.gz`, `.zip`), скрипт, jar, любой не-исполняемый формат —
  **не определяется**, читать нечего. Сервис внутрь архива не заглядывает;
- исполняемый файл под машину вне словаря (mips, x32 ABI) — тоже «не опознано»;
- у Windows требуется **настоящий исполняемый файл**: DOS-заголовок `MZ` плюс
  сигнатура `PE\0\0`. Голый COFF-объектник (`.obj`) без `MZ` не опознаётся —
  исполняемых файлов Windows без `MZ` не бывает;
- `.class` Java не опознаётся, хотя начинается той же магией `0xcafebabe`, что и
  fat Mach-O: у настоящего universal binary каждый срез обязан быть Mach-O, и
  проверка это ловит.

**Читается только заголовок.** Всё, что нужно определению, лежит в первых
байтах файла: класс, порядок байт, OS/ABI и машина у ELF, тип процессора у
Mach-O, машина COFF у PE. Таблицы секций, загрузочные команды и таблицы символов
не читаются вовсе, поэтому **стоимость разбора не зависит от размера файла** —
меньше килобайта чтения и десятки микросекунд что на однострочной программе, что
на 55-мегабайтном universal binary. Размер и урезанность (`-ldflags="-s -w"`)
на определение не влияют никак.

Из этого же следует, чего сервис **не** делает: он не проверяет, что файл
целиком корректен. Заголовок с честной машиной, за которым лежит мусор или
намеренно испорченные таблицы, определится по заголовку — это метка «под что
собрано», а не валидация артефакта. Проверка целостности — это `sha256`.

### Как платформа попадает в версию

1. **Автоматически при заливке** — `PUT` без `?platform=` берёт то, что прочитано
   из файла.
2. **Явно при заливке** — `?platform=` у `PUT`.
3. **Руками потом** — `PATCH /api/apps/{name}/versions/{version}`; там же она
   сбрасывается обратно в «неизвестно».
4. **Автоматически при старте сервиса** — backfill проходит по версиям с пустой
   платформой и пробует определить её по файлу на диске (см. README, раздел
   «Обновление существующей установки»).

## Маршруты

Далее `BASE=http://localhost:8080`, `CRED=alice:s3cret-pass`. Пароль в примерах
не короче 8 байт не случайно — короче сервис завести не даст (см. «Требования
к паролю»).

### GET /api/apps — список приложений

`200` → массив объектов приложения, сортировка по имени:

```json
[{"name":"myapp","description":"demo","versions_count":2,
  "latest":{…объект версии…},"created_at":"2026-08-06T12:00:00Z"}]
```

`latest` — объект версии или `null`, если версий нет.

```sh
curl -u $CRED $BASE/api/apps
```

### POST /api/apps — создать приложение

Тело: `{"name":"myapp","description":"demo"}` (description необязателен;
JSON-тела ограничены 1 MiB). `201` + объект приложения (у только что созданного
`versions_count` = `0`, `latest` = `null`), `409 already_exists` при дубле,
`400 invalid_name`.

```sh
curl -u $CRED -X POST $BASE/api/apps \
  -H 'Content-Type: application/json' -d '{"name":"myapp","description":"demo"}'
```

### GET /api/apps/{name} — приложение с версиями

`200` → объект приложения + `"versions":[…]` (semver по убыванию); `404` если нет.

```sh
curl -u $CRED $BASE/api/apps/myapp
```

### PATCH /api/apps/{name} — переименовать / изменить описание

Тело: `{"name":"newname","description":"new text"}`. **Оба поля необязательны и
различают «не передано» и «передано пустым»:** отсутствующее поле не меняется,
`{"description":""}` описание стирает, `{"name":""}` — `400 invalid_name`.
Пустое тело (или `{}`) — `200` без изменений.

`200` → тот же формат, что и `GET /api/apps/{name}` (объект приложения плюс
`versions`), уже с новым именем: `download_url` во всех версиях пересчитан.

| Код | Когда |
|---|---|
| `400 invalid_name` | новое имя не проходит `^[a-zA-Z0-9][a-zA-Z0-9._-]{0,63}$` или равно `latest` |
| `400 validation` | битое JSON-тело |
| `404 not_found` | приложения нет (или имя в пути невалидно) |
| `409 already_exists` | имя занято другим приложением; каталог `{data-dir}/{новое-имя}` уже существует; путь источника или приёмника занят посторонним объектом |
| `500 internal` | сбой БД или ФС |

**Переименование ломает старые ссылки.** Каталог `{data-dir}/{старое-имя}`
переезжает в `{data-dir}/{новое-имя}`, а вместе с ним меняются и адреса:
`/download/старое-имя/…` и `/api/apps/старое-имя` начинают отдавать `404`.
Алиасов и редиректов со старого имени нет — это осознанное решение. Всё, что
раздаёт ссылки на скачивание (CI, инсталляторы, документация), надо обновить.

Порядок операций — БД, затем диск: сначала переименовывается строка (`UNIQUE`
на `apps.name` не даёт двум приложениям занять одно имя), затем каталог. Если
каталог переименовать не удалось, имя в БД откатывается обратно, и приложение
остаётся под старым именем.

> **Переименование во время чужой загрузки безопасно — проигрывает загрузка.**
> Перенос каталога и публикация залитого файла идут под одним замком по имени
> приложения, поэтому `PATCH` проходит целиком, а `PUT`, чьё тело ещё лилось,
> получает `409 already_exists` и ничего не оставляет на диске (см.
> `PUT /api/apps/{name}/versions/{version}`).

```sh
# имя и описание разом
curl -u $CRED -X PATCH $BASE/api/apps/myapp \
  -H 'Content-Type: application/json' -d '{"name":"myapp2","description":"renamed"}'
# только описание
curl -u $CRED -X PATCH $BASE/api/apps/myapp2 \
  -H 'Content-Type: application/json' -d '{"description":"just a new text"}'
```

### DELETE /api/apps/{name} — удалить приложение

Удаляет приложение со **всеми** его версиями (в БД — одним `DELETE` с
`ON DELETE CASCADE`) и рекурсивно сносит каталог `{data-dir}/{name}` вместе с
файлами, в том числе не учтёнными в БД. Подтверждения на уровне API нет — оно
есть только в UI. Операция необратима, soft-delete нет.

| Код | Когда |
|---|---|
| `204` | удалено, тело пустое |
| `404 not_found` | приложения нет (в том числе при повторном удалении) |
| `409 already_exists` | путь занят посторонним объектом — строка удалена, диск не тронут |
| `500 internal` | сбой БД, или строка удалена, а каталог снести не удалось |

```sh
curl -u $CRED -X DELETE $BASE/api/apps/myapp2 -o /dev/null -w '%{http_code}\n'
```

### DELETE /api/apps/{name}/versions/{version} — удалить версию

Удаляет одну версию и её каталог `{data-dir}/{name}/{version}` с файлом.
`{version}` принимает и `1.2.3`, и `v1.2.3`. Приложение остаётся, даже если
удалена последняя версия (его каталог остаётся пустым).

Если удалялась закреплённая latest-версия, закрепление снимается автоматически
(`ON DELETE SET NULL`), и latest снова резолвится как максимальный semver.

| Код | Когда |
|---|---|
| `204` | удалено, тело пустое |
| `400 invalid_version` | строка версии не semver |
| `404 not_found` | нет приложения или версии (в том числе при повторном удалении) |
| `409 already_exists` | путь занят посторонним объектом — строка удалена, диск не тронут |
| `500 internal` | сбой БД, или строка удалена, а каталог снести не удалось |

```sh
curl -u $CRED -X DELETE $BASE/api/apps/myapp/versions/1.2.3 -o /dev/null -w '%{http_code}\n'
```

### GET /api/apps/{name}/versions — список версий

`200` → массив объектов версии, semver по убыванию.

```sh
curl -u $CRED $BASE/api/apps/myapp/versions
```

### GET /api/apps/{name}/versions/{version} — конкретная версия

`{version}` принимает и `1.2.3`, и `v1.2.3`. `200` → объект версии;
`404 not_found`; `400 invalid_version`.

```sh
curl -u $CRED $BASE/api/apps/myapp/versions/1.2.3
```

### PUT /api/apps/{name}/versions/{version} — залить бинарник

Тело запроса — **сырые байты файла** (не multipart).

- `X-Checksum-Sha256` (заголовок, опционально) — ожидаемый SHA-256 hex,
  регистр не важен; при несовпадении файл не сохраняется → `422 hash_mismatch`.
  Сервер в любом случае сам считает и сохраняет хеш.
- `?filename=` (**обязательно**) — имя файла, под которым версия ляжет на диск и
  будет отдана `/download` в `Content-Disposition`. Расширение указывайте сами:
  `myapp-1.2.3.tar.gz`, `myapp-linux-amd64`. Значение **обрезается по краям**
  перед проверкой, поэтому `?filename=%20myapp-1.2.3.tar.gz%20` сохранится как
  `myapp-1.2.3.tar.gz`; пробелы **внутри** имени законны и сохраняются как есть
  (`my app-1.2.3.tar.gz`).
- Параметр считается непереданным в трёх случаях, и все три дают один и тот же
  `400 filename_required`: параметра нет вовсе, он пустой (`?filename=`) и он
  состоит из одних пробельных символов (`?filename=%20`, одиночный таб или
  перевод строки). Последнее — не придирка, а самый частый способ выстрелить
  себе в ногу: `?filename=$ARTIFACT` с незаданной переменной в CI даёт именно
  пробелы, и принять такое означало бы `201` с файлом, у которого имя из
  пробелов. Переданное непробельное, но негодное имя — `400 invalid_filename`
  (два разных кода намеренно: «не передал» и «передал мусор» чинятся
  по-разному).
- **Управляющие символы в имени запрещены целиком** — вся категория Unicode
  `Cc`: C0 (`\0`, `\n`, `\r`, `\t`, `\b`), `DEL` и C1 (например `U+0085`).
  Такое имя — `400 invalid_filename`. Граница проходит по категории, а не по
  списку: `NUL` файловая система не принимает вовсе, перевод строки уезжает в
  `Content-Disposition` и в журнал, а имя с `\b` в терминале оператора выглядит
  не тем, что лежит на диске. Разграничение с предыдущим пунктом простое:
  значение сначала обрезается по краям, поэтому **одиночный** таб или перевод
  строки — это `filename_required` (после обрезки не осталось ничего), а
  управляющий символ **внутри** непустого имени (`a\nb.tar.gz`) —
  `invalid_filename`.
- `?platform=` (**необязательно**) — под что собран файл: пара `os/arch`, `any`
  или `darwin/universal` (словарь и правила канонизации — в разделе «Платформа
  версии»). Параметр считается непереданным, если его нет, он пуст или состоит
  из пробельных символов: `?platform=$VAR` с незаданной переменной уходит в
  автоопределение, а не в отказ по мусору. Подробности поведения — ниже,
  в «Платформа при заливке».
- **Отказ приходит до чтения тела.** Имя проверяется раньше, чем сервер
  начинает принимать байты, поэтому негодный `?filename=` не стоит клиенту
  загрузки: на теле в 50 МБ отправляется 0 байт. На диске и в БД не остаётся
  ничего. То же и для мусора в `?platform=`: `400 invalid_platform` приходит до
  первого байта тела.
- Не-ASCII имена законны: `приложение-1.0.0.tar.gz` сохранится как есть и
  уедет в `Content-Disposition` по RFC 5987 (`filename*=utf-8''…`). Пробелы
  внутри имени тоже законны — такое имя квотируется (`filename="my app.tar.gz"`).
- Ответы: `201` + объект версии; `409 already_exists` (дубль версии —
  обычно отклоняется до чтения тела; при двух одновременных загрузках одной
  версии проигравший тоже получает 409, файл победителя не затрагивается;
  тем же кодом отвечает занятый посторонним объектом путь в data-dir и
  приложение, переименованное или удалённое во время загрузки, — см. ниже);
  `404` нет приложения; `400 invalid_version` / `400 filename_required` / `400 invalid_filename`;
  `400 platform_required` / `400 invalid_platform` / `409 platform_mismatch`;
  `413 too_large`; `422 hash_mismatch`.
- Перезаписать существующую версию нельзя. Чтобы заменить содержимое, сначала
  удалите версию (`DELETE /api/apps/{name}/versions/{version}`), потом залейте
  заново — номер версии освободится.

**Платформа при заливке.** Сервер сначала пробует прочитать платформу из
залитого файла (по временному файлу, **до** публикации: отказ не создаёт ни
каталога версии, ни файла в нём), потом сверяет прочитанное с `?platform=`.
Веток ровно три:

| `?platform=` | Прочитано из файла | Результат |
|---|---|---|
| не передан | `linux/amd64` | `201`, `platform` = `linux/amd64` |
| не передан | ничего (архив) | **`400 platform_required`**, ничего не сохранено |
| `any` / `linux/amd64` / … | ничего (архив) | `201`, `platform` = переданное |
| `linux/amd64` | `linux/amd64` | `201`, значения совпали |
| `darwin/arm64` | `linux/amd64` | **`409 platform_mismatch`**, ничего не сохранено |
| мусор (`amd64`, `linux/`) | — | **`400 invalid_platform`**, тело не читается вовсе |

Расхождение — отказ, а не переопределение: молча разъехавшиеся метка и
содержимое обнаружит не тот, кто залил, а тот, кто скачает артефакт. Из этого
следует и неочевидное: **настоящий бинарник нельзя пометить `any`** —
`?platform=any` на ELF-файле даёт `409`, потому что файл платформо-зависим.
Если определение всё-таки ошиблось, версия заливается без `?platform=` и
правится потом через `PATCH`.

Ошибка чтения файла равнозначна «не опознано» и уходит в серверный лог; заливку
она не отменяет. Обрезанный, пустой или битый файл — тоже просто «не опознано»:
разбор читает поля по фиксированным смещениям и проверяет длину, падать ему не
на чем.

Тексты `platform_required` и `platform_mismatch` самодостаточны и рассчитаны на
лог CI: они называют оба значения, перечисляют словарь и содержат готовую строку
`curl`.

```sh
# голый бинарник — параметр не нужен, платформа читается из файла
curl -u $CRED -X PUT "$BASE/api/apps/myapp/versions/1.2.3?filename=myapp-linux-amd64" \
  --data-binary @myapp-linux-amd64
# архив — параметр обязателен
curl -u $CRED -X PUT "$BASE/api/apps/myapp/versions/1.2.3?filename=myapp-1.2.3.tar.gz&platform=linux/amd64" \
  --data-binary @myapp-1.2.3.tar.gz
# архив, который от платформы не зависит (jar, скрипты)
curl -u $CRED -X PUT "$BASE/api/apps/tools/versions/1.0.0?filename=tools-1.0.0.jar&platform=any" \
  --data-binary @tools-1.0.0.jar
```

**Совместимость (ломающее изменение): архив теперь нельзя залить без платформы.**
Раньше платформы не было вовсе, и `PUT` принимал любой файл. Теперь запрос без
`?platform=`, платформу которого не удалось прочитать из содержимого, отвечает
`400 platform_required` и версию **не создаёт**.

- **Что сломается.** Всё, что заливает по API **не бинарники**: архивы
  (`.tar.gz`, `.zip`), jar'ы, наборы скриптов, — то есть многофайловые
  приложения из README. Голых исполняемых файлов изменение не касается: их
  платформа читается сама, и такие пайплайны не правятся ни одной строкой.
- **Как распознать.** В ответе `"error":"platform_required"`, HTTP 400. Отказ
  приходит после того, как тело выкачано (платформа решается по временному
  файлу), но на диске и в БД не остаётся ничего — ни каталога версии, ни файла,
  ни строки.
- **Как чинится — одной строкой в URL.** Тело и заголовки менять не нужно:
  добавьте `&platform=linux/amd64` (или ту пару, под которую собран артефакт)
  либо `&platform=any`, если содержимое от ОС и архитектуры не зависит.
- **Чего изменение не касается.** Уже залитые версии: их платформа остаётся
  пустой, пока её не проставят руками или не подберёт стартовый backfill; на
  скачивание и `Content-Disposition` она не влияет никак. Веб-форма загрузки
  ведёт себя так же, как API (те же `400` и `409`), но платформа там выбирается
  из выпадающих списков.

**Совместимость (ломающее изменение).** Раньше `?filename=` был необязателен и
имя по умолчанию собиралось как `{name}-{version}` — без расширения, из-за чего
залитый архив скачивался файлом, который система не опознаёт. Дефолт убран:
запрос без параметра теперь отвечает `400 filename_required`, а не `201`.

- **Что сломается.** Любой клиент, заливавший версию без `?filename=`: скрипт
  CI, шаг деплоя, прямой `curl` из инструкции. Раньше он получал `201` и версию
  с именем `{name}-{version}`, теперь получает `400` и версию **не создаёт**.
  Отказ происходит до чтения тела, так что на диске и в БД не остаётся ничего —
  сломанный пайплайн падает, а не заливает половину.
- **Как распознать.** В ответе `"error":"filename_required"`, HTTP 400. Тело
  ошибки самодостаточно: оно называет прежнее умолчательное имя для этой
  пары приложение+версия, объясняет, почему дефолт убран, и содержит готовую
  строку `curl` с правильным `?filename=` — её можно скопировать из лога CI
  прямо в скрипт.
- **Как чинится.** Добавлением одного параметра в URL, менять тело и заголовки
  не нужно:
  `curl -X PUT "$BASE/api/apps/myapp/versions/1.2.3?filename=myapp-1.2.3.tar.gz" --data-binary @myapp-1.2.3.tar.gz`.
  Если имя раньше устраивало и расширение не нужно, достаточно передать прежнее
  умолчательное значение явно: `?filename=myapp-1.2.3`.
- **Чего изменение не касается.** Уже залитые версии сохраняют имена, с
  которыми были залиты (в том числе прежние умолчательные `{name}-{version}`):
  хранилище, `/download` и `Content-Disposition` не затронуты, перезаливать и
  переименовывать ничего не нужно. Загрузка через веб-форму тоже не затронута —
  там имя берётся из самого выбранного файла, а не из `?filename=`.

Угадывать имя по `Content-Type` или по сигнатуре содержимого сервис не пытается:
молчаливо неверное имя хуже явного отказа.

**Переименование и удаление во время загрузки.** Файл публикуется под замком по
имени приложения, с перепроверкой строки в БД: если к этому моменту `PATCH` уже
переименовал приложение или `DELETE` его снёс, публикация отклоняется с
`409 already_exists` и `message` `app was renamed or removed while the upload was
in flight, nothing was written to disk` — ни временного файла, ни каталога на
диске не остаётся. Удаление, успевшее пройти уже после перепроверки, — редкий
случай: он отдаёт `500`, версия не создаётся, лишних файлов в data-dir тоже не
появляется.

```sh
curl -u $CRED -X PUT "$BASE/api/apps/myapp/versions/1.2.3?filename=myapp-linux-amd64" \
  -H "X-Checksum-Sha256: $(sha256sum myapp-linux-amd64 | cut -d' ' -f1)" \
  --data-binary @myapp-linux-amd64
```

### PATCH /api/apps/{name}/versions/{version} — проставить платформу руками

Единственное изменяемое поле версии. Нужен там, где определить платформу по
файлу нельзя (архив, jar) и её не указали при заливке, и там, где определение
ошиблось.

Тело: `{"platform":"linux/amd64"}`. Поле **необязательно и различает «не
передано» и «передано пустым»**, как `PATCH /api/apps/{name}`:

| Тело | Что происходит |
|---|---|
| `{"platform":"darwin/arm64"}` | платформа ставится (значение канонизируется) |
| `{"platform":"any"}` | версия помечается как не зависящая от платформы |
| `{"platform":""}` или строка из пробелов | платформа **сбрасывается** в «неизвестно» |
| `{}` или пустое тело | ничего не меняется, `200` |

Файл при этом не перечитывается: `PATCH` верит человеку. Проставить можно любое
значение из словаря, в том числе противоречащее содержимому, — это и есть
запасной выход для случая, когда определение ошиблось.

`200` → объект версии (уже с новым значением `platform`).

| Код | Когда |
|---|---|
| `400 invalid_platform` | значение не из словаря |
| `403 forbidden` | у роли нет `PermVersion` (например, `deployer`) |
| `404 not_found` | нет приложения или версии (в том числе если имя/версия в пути невалидны) |
| `415 unsupported_media_type` | непустое тело без `Content-Type: application/json` |
| `500 internal` | сбой БД |

```sh
# архив, залитый как any, оказался всё-таки платформо-зависимым
curl -u $CRED -X PATCH $BASE/api/apps/myapp/versions/1.2.3 \
  -H 'Content-Type: application/json' -d '{"platform":"linux/amd64"}'
# сбросить обратно в «неизвестно»
curl -u $CRED -X PATCH $BASE/api/apps/myapp/versions/1.2.3 \
  -H 'Content-Type: application/json' -d '{"platform":""}'
```

### GET /api/apps/{name}/latest — текущая latest-версия

Latest = закреплённая версия, если закреплена, иначе максимальный semver
(prerelease меньше релиза: `1.9.0-rc.1` < `1.9.0`). `200` → объект версии;
`404 not_found`, если версий нет.

```sh
curl -u $CRED $BASE/api/apps/myapp/latest
```

### POST /api/apps/{name}/latest — закрепить/снять latest

Тело: `{"version":"1.2.3"}` — закрепить конкретную версию;
`{"version":"auto"}` — снять закрепление (вернуть максимум semver).
`200` → объект получившейся latest-версии (или `null`, если версий нет);
`404 not_found` — закрепляемая версия не существует.

```sh
curl -u $CRED -X POST $BASE/api/apps/myapp/latest \
  -H 'Content-Type: application/json' -d '{"version":"1.2.3"}'
curl -u $CRED -X POST $BASE/api/apps/myapp/latest \
  -H 'Content-Type: application/json' -d '{"version":"auto"}'
```

## Учётные записи (`PermUserAdmin`, только `admin`)

Объект пользователя — один и тот же во всех ответах; **хеш пароля наружу не
уходит никогда**:

```json
{"username":"ci","role":"deployer","disabled":false,"created_at":"2026-08-07T13:26:48Z"}
```

- `role` — одна из `deployer`, `developer`, `maintainer`, `admin`;
- `disabled` — учётка заблокирована (существует, но войти нельзя);
- `created_at` — RFC 3339, UTC.

Всем пяти маршрутам ниже нужна роль `admin`; остальным ролям — `403 forbidden`.

### GET /api/users — список учёток

`200` → массив объектов пользователя, сортировка по `username`.

```sh
curl -u $CRED $BASE/api/users
```

### POST /api/users — создать учётку

Тело: `{"username":"ci","password":"…","role":"deployer"}` — **все три поля
обязательны**, роли по умолчанию тут нет (она есть только у `apprepo user add`
для самого первого пользователя).

| Код | Когда |
|---|---|
| `201` | создано, тело — объект пользователя |
| `400 validation` | `username` пустой или не проходит проверку имени; пароль короче 8 или длиннее 72 байт (в том числе пустой); неизвестная роль (в `message` перечислены допустимые); битый JSON |
| `409 already_exists` | пользователь с таким именем уже есть |

```sh
curl -u $CRED -X POST $BASE/api/users \
  -H 'Content-Type: application/json' -d '{"username":"ci","password":"s3cret-pass","role":"deployer"}'
```

### PATCH /api/users/{username} — сменить роль и/или заблокировать

Тело: `{"role":"developer","disabled":true}`. **Оба поля необязательны:**
отсутствующее не меняется, пустое тело (или `{}`) — `200` без изменений.

Блокировка (`"disabled":true`) — это «закрыть доступ, не удаляя учётку»:
строка остаётся, история и имя заняты, но вход закрывается **немедленно** —
сессии пользователя удаляются, а Basic Auth начинает отвечать `401`.
Разблокировка (`"disabled":false`) возвращает доступ с тем же паролем.

| Код | Когда |
|---|---|
| `200` | изменено, тело — объект пользователя |
| `400 validation` | неизвестная роль, битый JSON |
| `404 not_found` | нет такого пользователя |
| `409 last_admin` | это последний активный админ (см. ниже) |

```sh
curl -u $CRED -X PATCH $BASE/api/users/ci \
  -H 'Content-Type: application/json' -d '{"role":"developer"}'
curl -u $CRED -X PATCH $BASE/api/users/ci \
  -H 'Content-Type: application/json' -d '{"disabled":true}'    # заблокировать
curl -u $CRED -X PATCH $BASE/api/users/ci \
  -H 'Content-Type: application/json' -d '{"disabled":false}'   # вернуть доступ
```

### POST /api/users/{username}/password — сброс пароля админом

Тело: `{"password":"…"}`. Текущий пароль **не спрашивается** — это админский
сброс для «забыл пароль». Все сессии пользователя гасятся, старый пароль
перестаёт работать сразу.

| Код | Когда |
|---|---|
| `204` | пароль заменён, тело пустое |
| `400 validation` | пароль вне 8–72 байт (в том числе пустой) |
| `404 not_found` | нет такого пользователя |

```sh
curl -u $CRED -X POST $BASE/api/users/ci/password \
  -H 'Content-Type: application/json' -d '{"password":"new-s3cret-pass"}'
```

### DELETE /api/users/{username} — удалить учётку

Удаление необратимо; сессии уходят вместе с учёткой (`ON DELETE CASCADE`).

| Код | Когда |
|---|---|
| `204` | удалено, тело пустое |
| `404 not_found` | нет такого пользователя |
| `409 self_delete` | это ваша собственная учётка |
| `409 last_admin` | это последний активный админ |

```sh
curl -u $CRED -X DELETE $BASE/api/users/ci -o /dev/null -w '%{http_code}\n'
```

### Защита последнего администратора

Установка не должна остаться без того, кто может заводить учётки, поэтому
**последнего активного админа нельзя разжаловать, заблокировать и удалить** —
все три операции отвечают `409 last_admin`:

```json
{"error":"last_admin","message":"the last enabled admin cannot be demoted, disabled or deleted"}
```

Детали, которые важны на практике:

- «Активный» = `role=admin` и `disabled=false`. Заблокированный админ установку
  управляемой не делает и в счёт не идёт, поэтому удалить или разжаловать его
  можно свободно.
- Проверка и сама запись идут в одной транзакции (`BEGIN IMMEDIATE`), так что
  два одновременных разжалования не могут оставить ноль админов: второе
  получит `409`.
- Правило одинаково во всех трёх интерфейсах — API, веб и CLI (`apprepo user
  role|disable|delete` печатают `refused: no active administrator would be left
  in the system` и выходят с кодом 1). Обойти его, чтобы «починить» установку,
  нельзя — сначала выдайте роль `admin` другой учётке.
- Понизить **себя** можно, если активный админ в системе не один: `403` вы
  получите уже на следующем запросе к `/api/users`.
- Удалить себя нельзя никогда — `409 self_delete`, независимо от числа админов.

## Своя учётка (любая роль)

Эти два маршрута права не требуют вовсе: узнать себя и сменить свой пароль
должен уметь кто угодно, включая `deployer`, которого не пускают в интерфейс.

### GET /api/me — кто я

`200` → `{"username":"ci","role":"deployer"}`. Удобно для проверки кредов из CI.

```sh
curl -u $CRED $BASE/api/me
```

### POST /api/me/password — сменить свой пароль

Тело: `{"current_password":"…","new_password":"…"}`. Текущий пароль проверяется.
После смены все сессии пользователя гасятся, и старый пароль сразу перестаёт
работать.

| Код | Когда |
|---|---|
| `204` | пароль заменён, тело пустое |
| `400 validation` | `new_password` вне 8–72 байт (в том числе пустой) |
| `403 invalid_password` | `current_password` не совпал |

> Обратите внимание: HTTP-код у неверного текущего пароля тот же, что у
> нехватки права (403), но код ошибки в теле разный — `invalid_password`
> против `forbidden`: вердикты разные и лечатся по-разному.

```sh
curl -u $CRED -X POST $BASE/api/me/password \
  -H 'Content-Type: application/json' \
  -d '{"current_password":"s3cret-pass","new_password":"new-s3cret-pass"}'
```

### GET /download/{name}/{version} — скачать бинарник

`{version}` — конкретная версия (`1.2.3` / `v1.2.3`) или литерал `latest`
(файл отдаётся напрямую, без редиректа). Заголовки ответа:

- `Content-Disposition: attachment; filename=…` (не-ASCII — по RFC 5987);
- `X-Checksum-Sha256: <hex>`;
- `Content-Length`; поддерживаются Range-запросы (`http.ServeContent`).

Требуется `PermRead`, то есть скачивать может **любая роль**, включая `deployer`:
прямые ссылки — его основной сценарий, интерфейс ему для этого не нужен.

Ошибки — plain text: `404` нет приложения/версии, `500` файл потерян на диске.

Ссылка привязана к текущему имени приложения: после `PATCH` с новым `name`
адреса `/download/старое-имя/…` отдают `404` — постоянных алиасов нет.
Удалённая версия (и все версии удалённого приложения) тоже отдают `404`.

```sh
curl -u $CRED -O -J $BASE/download/myapp/1.2.3
curl -u $CRED -O -J $BASE/download/myapp/latest
```

### GET /healthz — проверка живости

Без аутентификации, `200` → `ok`. Для проб systemd/балансировщика.
