# CLAUDE.md — карта проекта apprepo

Репозиторий бинарников приложений: Go + stdlib `net/http`, SQLite (чистый Go,
без CGO), файлы на диске. Один бинарник `apprepo` с подкомандой `serve` (дефолт)
и группой `user` (`add`, `list`, `role`, `password`, `disable`, `enable`,
`delete`). Доступ разграничен глобальными ролями (см. «Роли и права»).
План и контракты: `docs/plans/2026-08-06-app-artifactory.md`
(схема БД, сигнатуры, маршруты, коды ошибок — фиксированы, не менять без плана).

## Команды

```sh
make build            # go build -o apprepo ./cmd/apprepo
make test             # go test ./...
go vet ./...
bash scripts/smoke.sh # сквозной curl-сценарий на временном каталоге (нужен свободный порт от 18080)
```

Тесты лежат рядом с кодом (`internal/<pkg>/*_test.go`), интеграционные —
`internal/integration/`. Внешних сервисов не нужно: SQLite и файлы — во
временных каталогах (`t.TempDir()`), HTTP — `httptest`. Тесты с wazero
небыстрые (первый прогон пакета ~секунды) — это нормально. `-short` пропускает
два тяжёлых теста: большой файл в `internal/files` (`TestSaveLargeFileStreams`)
и сборку бинарника в `internal/integration` (`TestUserAddCLI`).

Сеть при сборке: среда выпускает наружу только github.com, поэтому в `go.mod`
стоят `replace` `golang.org/x/*` → `github.com/golang/*`. Не удалять, пока
живёшь в этой песочнице; `GOPROXY=direct`, `GOSUMDB=off`.

## Роли и права

Четыре глобальные роли по возрастанию полномочий: `deployer` < `developer` <
`maintainer` < `admin`; у учётки ровно одна. Пять прав:

| Право | Что открывает | deployer | developer | maintainer | admin |
|---|---|:---:|:---:|:---:|:---:|
| `PermRead` | GET по API, `/download` | ✔ | ✔ | ✔ | ✔ |
| `PermVersion` | залить/удалить версию, закрепить latest, проставить платформу | — | ✔ | ✔ | ✔ |
| `PermApp` | создать/переименовать/удалить приложение | — | — | ✔ | ✔ |
| `PermUserAdmin` | управление учётками | — | — | — | ✔ |
| `PermUI` | вход в веб-интерфейс | — | ✔ | ✔ | ✔ |

Матрица «маршрут → право» — в `docs/api.md`. Роль `deployer` машинная (CI и
прямые ссылки), `PermUI` у неё нет намеренно.

## Инварианты (нарушение = баг)

- **Матрица прав живёт ровно в одном месте — `rolePerms` в
  `internal/auth/roles.go`.** Второй копии нет нигде: маршруты вешают право
  через `Auth.Require`, шаблоны спрашивают `.Can.App`/`.Can.Version`/… (список
  собирается в `web.baseView` из `Role.Can`), справка CLI берёт имена ролей из
  `auth.AllRoles()`. Сравнивать имя роли строкой (`if role == "admin"`) в
  `api`/`web`/шаблонах нельзя — при добавлении роли такие места разъезжаются
  молча. Неизвестная роль не даёт ничего: `Role.Can` падает закрыто.
  Единственное исключение — `store.roleAdmin`: на нём держится защита
  последнего админа, а импортировать `auth` в `store` нельзя (циклическая
  зависимость, `auth` уже импортирует `store`).
- **Роль читается из БД на каждом запросе**, а не из сессии или куки:
  `RequireSession`/`RequireBasic` кладут в контекст свежий `store.User`, и
  `Require` смотрит его роль. Следствие, на которое можно опираться: смена
  роли действует немедленно, без перелогина; кешировать роль в сессии нельзя.
- **Право на UI-маршруте вешается только через `web.guard`** (`RequireSession`
  → `Require(PermUI)` → `Require(конкретное право)`). Новый маршрут мимо
  `guard`/`form` — дыра: `deployer` попадёт в интерфейс. Исключения ровно два и
  оба намеренные: `POST /logout` (без `PermUI`, иначе `deployer` не погасил бы
  сессию со страницы-объяснения) и `/login`.
- **Одна операция — одно право в обоих интерфейсах.** `PATCH /api/apps/{name}` и
  `POST /apps/{name}/edit` требуют одного и того же; таблица пар — в отчёте
  `docs/reports/F11-2026-08-06.md`. Асимметрия допустима только там, где она
  объяснена комментарием в коде: чтение (`PermRead` в API против `PermUI` на
  страницах) и смена своего пароля (`/api/me/password` без права, `POST
  /password` в UI под `PermUI`).
- **Последнего активного админа нельзя разжаловать, заблокировать и удалить.**
  Проверка одна на всех — `guardLastAdmin` внутри `store.writeTx`
  (`BEGIN IMMEDIATE`, поэтому две одновременные операции сериализуются и не
  могут оставить ноль админов) → `store.ErrLastAdmin`. Вызывающие мапят её:
  `api` → `409 last_admin`, `web` → страница с `409`, CLI → `refused: no active
  administrator would be left in the system`, exit 1. «Активный» = `role=admin`
  и `disabled=0`; заблокированный админ не в счёт. Дублировать проверку в
  хендлерах не надо и обходить её нельзя. Отдельно от неё: удаление **своей**
  учётки запрещено всегда (`409 self_delete` в API, аналогичный отказ в UI).
- **Смена пароля и блокировка гасят сессии пользователя** (`DELETE FROM
  sessions WHERE user_id` в `SetUserPassword`/`SetUserDisabled`). На это
  опираются UI (после смены своего пароля — редирект на `/login?m=password-changed`)
  и требование «блокировка закрывает доступ мгновенно». Убирать нельзя.
- **Миграция БД идёт автоматически в `store.Open`** — `migrateUsers` досоздаёт
  колонки `role`/`disabled`, которых нет в базе, созданной до появления ролей,
  `migrateVersions` — колонку `platform` (обе поверх общего `addColumns`).
  Идемпотентна (`pragma_table_info` → `ALTER TABLE` только недостающих).
  Существующие учётки получают `role='admin'` из `DEFAULT`: до ролей все
  пользователи могли всё, миграция сохраняет поведение. **Умолчания заданы
  дважды — в `schema.sql` и в `migrateUsers`; менять надо в обоих местах.**
  Отката нет; в README это отражено требованием снять копию файла БД перед
  обновлением.
- **Имя учётки проходит `naming.NormalizeUsername` на КАЖДОМ пути — и при
  создании, и при поиске.** API (`createUser`, `mustUser`), UI (`createUser`),
  CLI (`userAdd`, `mustUser`). Обрезка пробелов без проверки — или проверка без
  обрезки — даёт две визуально одинаковые учётки, из которых блокировка попадёт
  только на одну. Своего `strings.TrimSpace` рядом с формой не заводить.
  Негодное имя в **теле** — 400 `validation`; негодное имя в **пути** — 404
  (как у имени приложения): завести его нельзя, значит и учётки с ним нет.
  Двоеточие запрещено отдельным пунктом: Basic кодирует `user:password`, и
  учётка с двоеточием не смогла бы войти по Basic никогда.
  Единственное место без нормализации — форма входа (`auth.authenticate`
  сверяет имя как есть): иначе учётки со старыми именами перестали бы входить.
- **Политика пароля — `naming.ValidatePassword` (8–72 байта), одна на три
  интерфейса.** Нижняя граница — потому что ограничения частоты входа нет;
  верхняя — предел bcrypt, который длинный вход отвергает ошибкой, а не
  обрезает (без проверки это 500 на пользовательском вводе). Вызывается в
  `api.hashPassword`, в `web.createUser`/`resetUserPassword`/`changeOwnPassword`
  и в `cmd.readPassword`. Классы символов и словари не добавлять — решение
  принято осознанно (R6-sec).
- **Учётки со старыми именами отбираются одним `naming.LegacyUsername`** —
  и предупреждением в CLI (`legacyNames` в `cmd/apprepo/main.go`), и пометкой на
  `/users` (`legacyNames` в `internal/web/users.go`). Критерий — «имя не совпадает
  со своей нормальной формой», а не «имя невалидно»: `"admin "` нормализуется в
  чужое `admin`. Имена показываются в кавычках (`strconv.Quote`) — без них
  `"admin "` неотличим от `admin`. Расходиться этим двум спискам нельзя
  (R6-sec круг 3). Внутри списка случаи разделены вторым предикатом —
  `naming.BrokenBasicUsername` (двоеточие): имя с пробелом или не-ASCII оставляет
  учётку рабочей (мешает только адресация по имени), а имя с двоеточием по Basic
  не входит вовсе и на `/users` метится отдельным значком `broken name`; обещать
  такой учётке «they still work and can sign in» нельзя (F16).
  Автоматически переименовывать такие учётки нельзя: это молча
  сломает Basic-креды в чужих пайплайнах, а смены имени учётки в продукте нет.
- Учётки наружу отдаются только через `api.userJSON` (`username`, `role`,
  `disabled`, `created_at`) — `password_hash` в ответы и в вывод CLI не попадает
  ни при каких условиях.
- Запись в таблицу учёток, не нашедшая строки, — `store.ErrNoUser`, и это 404,
  а не 500: учётку мог удалить другой админ между чтением и записью
  (`api.userWriteErr`, `web.userWriteErr` — пара, коды обязаны совпадать).
- **Класс кода ответа на одну и ту же ошибку обязан совпадать в API и UI.**
  `api.uploadErr` и `web.uploadError` — такая же пара, как `userWriteErr`:
  нераспознанный сбой публикации — **500 с записью в лог** в обоих интерфейсах
  (в UI через `h.serverError`), негодное тело запроса — **4xx** в обоих
  (`web.multipartError`: 400 на неразбираемый multipart, 413 на превышение
  лимита). Расхождение здесь не косметика: прежние 400 «upload failed» в UI
  выдавали поломку диска за ошибку пользователя и прятали её от мониторинга,
  тогда как та же ошибка ФС в API давала 500 (R7-qa, находка 3; F19). Текст
  внутренней ошибки (пути ФС, SQLite) при этом по-прежнему уходит только в
  серверный лог — клиенту фиксированная формулировка.
- **`Detect` читает только заголовок, и стоимость разбора не должна зависеть от
  размера файла.** Это и есть рубеж против враждебного файла — не лимит поверх
  разбора, а сам способ разбора. Читается префикс `headerBytes = 96` плюс
  точечные чтения по смещениям (заголовки срезов fat, 6 байт COFF PE) — меньше
  килобайта на файл любого размера; замерено 96–144 байта и десятки микросекунд
  что на 29-мегабайтной сборке, что на 256-мегабайтной ELF-бомбе.
  **Разборщиков `debug/elf`, `debug/macho`, `debug/pe` в продакшн-пути нет и
  возвращать их нельзя** (F22): они доверяют заголовку и вычитывают по нему
  таблицы целиком — на враждебном ELF это давало 2,4 GB аллокаций и 8 секунд
  (R8-sec S1), а введённый против этого бюджет чтения в 1 MiB (F21) заодно убил
  определение настоящих Mach-O и PE крупнее ~15 MB, потому что таблица символов
  у них ~5 % файла (R8-qa, находка 1). Бюджета больше нет как понятия — отделять
  честный файл от враждебного по объёму чтения незачем, когда объём фиксирован.
  В тестах `debug/*` оставлены **эталоном**: `TestDetectionConstantsMatchStdlib`
  сверяет с ними каждое смещение и каждый номер машины, потому что в коде это
  теперь литералы.
  Три числа из файла, которым нельзя верить, ограничены явно: `nfat_arch`
  потолком `maxFatArch = 32`, каждый срез fat обязан начинаться магией Mach-O
  (иначе Java `.class` с той же магией `0xcafebabe` выдавался бы за
  `darwin/universal`), а чтение по `e_lfanew` и по смещению среза за концом
  файла — штатный случай, `prefix` возвращает прочитанное.
  Прочие рубежи `Detect` не менялись и остаются: `O_NONBLOCK` при открытии
  (без него backfill на подложенном FIFO не возвращался никогда, R8-sec S3),
  отказ разбирать нерегулярный файл и `recover()` — последний теперь страховка,
  а не основная защита.
  `MemoryMax=1G` и `GOMEMLIMIT=768MiB` в `deploy/apprepo.service` остаются
  страховкой на случай будущей ошибки: строки парные, поднимаешь одну — поднимай
  и вторую (и код-блок юнита в README).
  Следствие, о котором стоит помнить: **определение не валидирует файл**.
  Заголовок с честной машиной, за которым лежат испорченные таблицы,
  определится по заголовку — это метка «под что собрано», а не проверка
  целостности; целостность проверяет `sha256`.
- **Платформа определяется по временному файлу, ДО публикации, в обоих
  интерфейсах** (`api.resolvePlatform` и `web.saveUpload` вызывают
  `platform.Detect(up.Path())` до `up.Commit`). Порядок обязателен: отказ не
  должен создавать ни каталога версии, ни файла в нём, а окно между `Commit` и
  `CreateVersion` не должно растягиваться на время разбора — на 200 MiB оно
  доходило до секунд, и удаление приложения внутри него давало 500 с
  `FOREIGN KEY constraint failed` (R8-sec S2). Отказавшая ветка обязана убрать
  временный файл (`up.Discard()` / `h.discardUpload`).
- **Вердикт по платформе одинаков в API и UI** — частный случай инварианта о
  классах кодов: не определилось и не указано → **400** (`platform_required` /
  тот же текст на странице), указанное спорит с содержимым → **409**
  (`platform_mismatch`), мусор в значении → **400** (`invalid_platform`).
  UI раньше отвечал `303` и молча брал платформу из файла — расхождение нашёл
  R8-test, закрыл F21. Правишь одну ветку — правь парную.
  Расхождение метки и содержимого — отказ, а не переопределение: его
  обнаруживает не тот, кто залил, а тот, кто скачал артефакт.
- **Словарь платформ живёт ровно в одном месте — `knownOS`/`knownArch` в
  `internal/platform/platform.go`.** UI берёт списки через `KnownOS()`/
  `KnownArch()` (копии, `slices.Clone` — вызывающий не должен мочь испортить
  словарь), шаблон перечислением их не дублирует, всё, что уходит из `Detect`,
  прогоняется через `canonical` → `Parse`. `Any` и `Universal` в `knownOS`/
  `knownArch` НЕ входят намеренно: иначе в выпадающих списках завелись бы
  бессмысленные пары вроде `linux/universal`. В разметку они тоже не пишутся
  литералами — оба идут через `web.specialPlatforms` (`view.PlatformSpecial`),
  и это проверяется тестами `TestTemplatesHaveNoPlatformLiterals` и
  `TestSpecialPlatformsRendered` (F22). Пустая строка допустима везде и означает
  «неизвестно», но `Parse` её не принимает — сброс идёт мимо `Parse`, прямым
  `store.SetVersionPlatform(id, "")`.
- **Все внешние имена проходят `internal/naming` до касания ФС/БД.**
  `files.Save`/`Remove` валидируют повторно сами — это осознанное дублирование,
  не убирать. Версия в `files` обязана быть уже канонической.
- Версии хранятся каноничным semver без `v`; сортировка и выбор latest — через
  `Masterminds/semver` в Go, никогда строкой в SQL.
- Latest = override (apps.latest_override_version_id), иначе максимум semver.
  Отдельного поля «is_latest» в БД нет — резолвится на лету.
- Загрузка: сначала файл (temp → атомарно-эксклюзивный `os.Link`, проигравший
  гонки получает `files.ErrFileExists` → 409, файл победителя не трогается),
  потом строка в БД; при ошибке вставки файл подчищается (`files.Remove`).
  Перезапись существующего файла запрещена.
- **`files`: мутирующая операция трогает только настоящий каталог внутри `Root`.**
  `Save`, `RenameApp`, `RemoveApp`, `RemoveVersion` перед записью, переносом и
  удалением проверяют **тип** цели через `isDir` (`os.Lstat`, поэтому симлинк
  каталогом не считается — даже указывающий на каталог), а не только имя.
  Отсутствие каталога — не ошибка (`(false, nil)`: приложение ещё без версий,
  удалять нечего); присутствующий не-каталог — `files.ErrNotDirectory`, и на
  диске не трогается ничего. Вызывающие (`api`, `web`) мапят его в **409**
  (`already_exists`, текст начинается на `storage path is not an application
  directory`), а не в 500: это коллизия, а не сбой. Зачем: `Root` — это
  data-dir, где рядом с каталогами приложений лежат `apprepo.db`, `-wal`,
  `-shm`, `.tmp`, а `naming.ValidateAppName` разрешает точку и дефис — имя
  `apprepo.db-wal` валидно и указывает на чужой файл. Рубеж добавлять в любую
  новую мутирующую ФС-операцию пакета; убирать нельзя (F7/F8/F9, R5-sec ×3).
- **`files`: всё, что двигает каталог приложения или публикует в него файл, идёт
  под замком по имени приложения.** Замок берут внутри себя `Upload.Commit`,
  `RenameApp` (оба имени, в отсортированном порядке — иначе встречные
  переименования дают дедлок), `RemoveApp`, `RemoveVersion`; снаружи брать не
  надо и забыть нельзя. **Держать его на время стриминга тела запрещено:** тело
  качается в `Prepare` без замка, под замком — только короткая публикация, там
  же `Commit(check)` перепроверяет, что приложение ещё под тем же именем (F10).
- Деструктивные операции (переименование, удаление приложения, удаление версии)
  журналируются в `api` и `web` с именем пользователя из `auth.CurrentUser`
  (`user %q deleted app %q` и т.п.); неудачная чистка диска после удаления
  строки логируется отдельной строкой. В журнал идёт только имя — пароли,
  хеши и токены не логируются.
- Порядок деструктивных операций — БД, затем диск: осиротевший каталог
  безвреден, строка без файлов — нет. Неудача на диске после успешного
  переименования строки компенсируется откатом имени в БД.
- `store`: «не найдено» — это `(nil, nil)`, не ошибка; дубли — `store.ErrExists`.
- Ошибки API — всегда JSON `{"error","message"}` (коды — в docs/api.md);
  `/download` может отвечать plain text (кроме 401).
- **Непустое JSON-тело принимается только с `Content-Type: application/json`**
  (`notJSON` в `internal/api/api.go`, вызывается первой строкой `decodeJSON` —
  единственной точки разбора JSON в пакете, поэтому забыть рубеж на новом
  маршруте нельзя). Всё прочее, включая отсутствующий и неразбираемый
  заголовок, — 415: `/api/` защищён только Basic Auth, куки нет, `SameSite` не
  участвует, и единственный барьер против кросс-сайтовой записи с кэшированными
  кредами — то, что `application/json` не входит в CORS-safelist и требует
  preflight. Белый список, а не денилист по типам: тело кросс-сайтового запроса
  произвольно (`fetch`/`sendBeacon`), так что запрещать `text/plain` и
  `multipart/form-data` бесполезно (F12 → R6-sec круг 2 → F14). Ослаблять
  нельзя; пустое тело — единственное исключение (`PATCH` без полей).
- Тела запросов ограничены: JSON — 1 MiB, загрузки — `cfg.MaxUploadBytes`
  через `http.MaxBytesReader`.
- **`?filename=` у `PUT /api/apps/{name}/versions/{version}` обязателен, и его
  значение обрезается по краям ДО проверки на пустоту.** Порядок обязателен
  именно такой: `strings.TrimSpace` → пусто? → `filename_required` (400) →
  `naming.ValidateFilename` → `invalid_filename` (400). Умолчательного
  `{app}-{version}` больше нет и возвращать его нельзя: на архиве оно давало имя
  без расширения, то есть молча непригодный файл вместо явного отказа (T23).
  Проверка на пустоту без обрезки — дыра, а не придирка: `?filename=$ARTIFACT` с
  незаданной переменной в CI даёт строку из пробелов, и без `TrimSpace` это был
  бы `201` с именем файла из пробелов (F18). Обрезаются только края — пробелы
  ВНУТРИ имени законны (`app v1.tar.gz`) и уже залитые версии не трогаются.
  Два кода намеренно разные: «не передал» и «передал мусор» чинятся по-разному.
  Текст `filename_required` рассчитан на лог CI и обязан оставаться
  самодостаточным (прежнее умолчательное имя + готовая строка `curl`) — это
  единственное, что видит сломавшийся пайплайн.
- **`naming.ValidateFilename` отвергает управляющие символы целой категорией
  `unicode.IsControl` (Cc: C0, `DEL`, C1), а не перечислением.** Список
  исключений здесь ошибочен по построению: законного имени файла с управляющим
  символом внутри не бывает, а пропущенный символ стоит дорого — `NUL` роняет
  `os.Link` в «invalid argument», и клиентский ввод приезжает **500-й** уже
  после того, как тело выкачано целиком (R7-qa, находка 1; F19). Не-ASCII имена
  под запрет НЕ попадают и попасть не должны: `приложение-1.0.0.tar.gz` законно
  и уезжает в `Content-Disposition` по RFC 5987. Проверка работает только на
  входе — уже залитые версии со старыми именами не перепроверяются и
  продолжают скачиваться.
- **Имя файла проверяется до чтения тела, и этот порядок менять нельзя.** В
  `putVersion` вся валидация (`ValidateVersion`, `filename_required`,
  `ValidateFilename`, ранняя проверка дубля) стоит выше `fs.Prepare`: отказ
  негодному запросу обязан стоить клиенту ноль байтов загрузки, иначе на
  двухгигабайтном архиве `400` обходится в два гигабайта трафика и диска.
  Проверено тестом, который меряет прочитанные байты, — не переставляй
  валидацию под чтение тела ради «единого места обработки ошибок».
- В multipart-форме загрузки поле `file` обязано идти последним: хендлер
  читает части потоково и к моменту файла должен уже иметь
  csrf_token/version/sha256/платформу.
  **Порядок держится разметкой формы** в `internal/web/templates/app.html`
  (`csrf_token`, `version`, `sha256`, `platform_os`, `platform_arch`, `file`) —
  переставить поля местами значит сломать загрузку, а не поменять вид.
  Половинки платформы добавлены волной 8 и встали **перед** `file` не случайно:
  `web.saveUpload` разбирает их до чтения тела (`platformField`), чтобы негодная
  пара стоила клиенту ноль байтов загрузки — тот же порядок, что у имени файла. То же и для отправки скриптом: `FormData`
  обходит поля в порядке разметки, поэтому у `XMLHttpRequest` порядок частей тот
  же, что у обычной браузерной отправки; отдельного места, где этот порядок
  задавался бы ещё раз, нет и заводить не надо (T22).
- **Inline-скрипт прогресса загрузки (`app.html`) не должен обзаводиться
  внешними ресурсами.** Ни `src=`, ни CDN, ни npm-зависимостей: весь JS в UI —
  встроенный, шаблоны уезжают в бинарник через `embed`, и установка обязана
  работать без выхода в интернет. Скрипт — прогрессивное улучшение: он
  перехватывает `submit` и шлёт ту же `FormData` тем же адресом через XHR
  (ради `upload.onprogress`, которого нет у `fetch`). **Форма обязана
  оставаться рабочей без JS** — не вешать на неё `onsubmit`, не переносить
  обязательные поля в скрипт, не делать `action` вычисляемым. Отдельно:
  скрипт не вправе утверждать «ничего не сохранено» после того, как тело ушло
  целиком (сервер уже мог опубликовать версию), и переходить по `responseURL`
  можно только если он своего origin (F18, R7-sec).
- UI POST — только с CSRF-токеном (кука `apprepo_csrf` + hidden input).
- Секреты (пароли, хеши, токены сессий) не логируются. Тексты внутренних
  ошибок (пути ФС, SQLite) — только в серверный лог, клиенту фиксированное
  «internal error»; информативными остаются только 4xx-валидации.
- Файлы БД (`apprepo.db`, `-wal`, `-shm`) — 0600 (chmod в `store.Open`);
  каталоги данных из `app.New` — 0700; в systemd-юните `UMask=0077`.
- Путь data-dir задан дважды: `ReadWritePaths=` в `deploy/apprepo.service`
  и `APPREPO_DATA_DIR` в env-файле — systemd не раскрывает переменные в своих
  директивах; расхождение = падение старта с `status=226/NAMESPACE`. Менять
  обе строки разом (и код-блок юнита в README). То же и для `APPREPO_DB`, если
  БД вынесена из data-dir: её каталог — отдельный путь в `ReadWritePaths=`
  (через пробел), иначе он read-only и старт падает уже на открытии БД
  (`unable to open database file`, `status=1/FAILURE`).
- Ошибка `store.Open` называет файл БД (`open database <path>: …`) — вызывающие
  путь не дублируют.

## Конфигурация

| Флаг | Env | Дефолт |
|---|---|---|
| `-addr` | `APPREPO_ADDR` | `:8080` |
| `-data-dir` | `APPREPO_DATA_DIR` | `/opt/apps` |
| `-db` | `APPREPO_DB` | `{data-dir}/apprepo.db` |
| `-base-url` | `APPREPO_BASE_URL` | `http://localhost:8080` |
| `-max-upload` | `APPREPO_MAX_UPLOAD` | `2147483648` |

В тестах и локально никогда не использовать `/opt/apps` — только временные
каталоги.
